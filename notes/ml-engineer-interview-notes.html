Interview map — what they actually test

In short This is a map of what an applied LLM interview round tests after a model exists. The tests cover three skills: define a technique in a few lines, defend a system design, and debug broken PyTorch code calmly. The interviewers want precise answers, not a full lecture. A short answer with one number or one failure mode beats a long one.

Picture it

  • Real example: a bank builds a KYC pipeline. A scanner reads ID cards (OCR), an LLM extracts fields, a reviewer checks doubtful cases, and a server answers requests all day.
  • The interview mirrors that pipeline. It asks about the parts that come after training: serving, tuning, retrieval, agents, and evaluation.
  • Round 1 is a PyTorch debug round, about 10 minutes. You read broken code and name the bug class: shape, device, dtype, mode, or gradient.
  • Round 2 is system design, about 5 to 15 minutes. You draw boxes for a use case such as document extraction or support chat, and you name the failure points.
  • Round 3 is LLM techniques, about 30 minutes. This is the longest round. Typical terms: KV cache, quantization, LoRA, speculative decoding, RAG, agents, MCP (a standard way for a model to call outside tools).
  • Past candidates heard feedback like: you know the basics, now learn what comes after the model is built.
  • A good answer has three parts. Give the definition in one line. Give when you use it in one line. Give one trade-off in one line. Then stop.
  • If the interviewer pushes, add one number or one failure mode. Example: INT4 weights use about 4 times less memory than FP16 weights.
  • Silence after your answer is fine. The interviewer will ask a follow-up if they want more.

How it works

  • Each round tests a different memory. Debug tests habits, design tests structure, and techniques test exact definitions.
  • A definition answer must say what is stored, what is computed, and what is saved. Example for KV cache: it stores old keys and values, so the model does not recompute them for each new token.
  • A design answer follows a fixed order: input, processing, storage, model call, check of output, human review, monitoring. Draw it left to right.
  • A debug answer follows a fixed order: read the error, guess the class, check one tensor shape or device, fix the root cause, run one batch again.
  • Numbers prove you understand. Example: a 7B model in FP16 needs about 14 GB just for weights. Say this before someone asks.
  • Name the two sides of every trade-off. Example: bigger batches raise throughput but also raise wait time for each user.

When it matters

  • Teams that ship models need people who know the cost after training. Serving cost often exceeds training cost within months.
  • Short, exact answers show that you have used the idea. Long answers often show that you have only read about it.
  • The same three habits work in real jobs: define clearly, design with failure in mind, debug with a hypothesis.

Watch out

  • Do not dump everything you know about transformers when the question names one term. One candidate talked about building from scratch when asked about quantization. The interviewer cut the answer off.
  • Do not say I would use a framework without saying what the loop underneath does. Frameworks hide the idea. The interviewer asks about the idea.
  • Do not learn new topics on the morning of the interview. Revise only the one-line answers.
  • Do not guess when you do not know. Say what you know, name the part you are unsure about, and reason from first principles.

Suggested study order

In short Study the post-build topics first, then RAG, agents and system design, then the foundations. This order matches how often each area appears in interviews. The goal is spoken answers that take 20 seconds or less. Reading alone is not enough. You must say each answer aloud.

Picture it

  • Real example: a hospital team must ship a note-summary tool next week. They first learn how to serve and tune a model, because that decides cost and speed. They study the deep math later.
  • Block A is post-build LLM techniques. Topics: inference vs training, decoding, KV cache, batching, quantization, LoRA. Plan about one day.
  • Block B is RAG, agents, MCP and human review, plus design templates. Draw the boxes by hand. Plan about one day.
  • Block C is foundations: attention and the transformer block. This block gives you the why behind block A. Plan about half a day to one day.
  • Block D is reference material: loss functions, optimizers, evaluation. Open it only when a why question needs it.
  • Rough interview weight: about half on post-build LLM techniques, a quarter on design, and a quarter on debug and foundations.
  • Daily loop: read one topic, close it, say the definition aloud, then say one number and one failure mode.
  • Tick a topic as understood only when you can explain it to a friend without notes.
  • On the last morning, reread only the one-line summary boxes. Do not open new material.

How it works

  • Spaced repetition works because memory fades. Review a topic after one day, then three days, then on the last morning.
  • Speaking aloud forces you to find gaps. If you stall at a word, that word is the gap.
  • Group topics by cause. Memory tricks: gradient checkpointing, LoRA, quantization. Speed tricks: KV cache, batching, speculative decoding. Quality tricks: SFT, DPO, distillation.
  • Draw each pipeline once with a pen. Hand drawing shows which box you forget.
  • Keep a short list of numbers: 2 bytes per FP16 weight, 0.5 byte per INT4 weight, 0.5 MB of KV cache per token for a 7B model with full heads.

When it matters

  • Time is short. A plan that matches interview weight gives the most points per hour.
  • Foundations alone do not pass an applied round. Techniques alone fail the why questions. The order links them.
  • Calm, rehearsed answers reduce stress, and stress is the main cause of rambling.

Watch out

  • Do not read in a passive way. Reading ten topics once is weaker than saying three topics three times.
  • Do not start with the hardest math. It uses time and gives little interview value for applied roles.
  • Do not skip the debug round. It is short but it is easy to lose points through panic.
  • Do not cram on the last morning. New facts push out old ones and raise anxiety.

Debug round — the ideas behind every bug

In short A debug round shows you broken training or inference code. You must find the bug class, fix the root cause, and prove the fix. The classes are shape, loss, device, dtype, mode, and gradient. You win by reasoning aloud with a hypothesis. You lose by changing lines at random.

Picture it

  • Real example: a warehouse OCR model reads labels at 95 percent in training and 40 percent in the live app. The training loop used eval mode in one place and train mode in another. The live app also fed images with a different pixel scale. Two small mismatches caused the drop.
  • Technical example: a batch has 2 sequences, 5 tokens each, and hidden size 16. A linear layer built for hidden size 768 receives size 16 on the last axis. The error says the shapes do not multiply. The cause is an embedding size that differs from the layer size.
  • Shape bug: a layer expects a certain last dimension. The data has a different one. A wrong reshape can also scramble batch and time axes without any error, which is worse.
  • Loss bug: the cross-entropy loss expects raw scores (logits) and integer class labels. If you pass probabilities, the loss applies softmax twice and learning becomes slow.
  • Device bug: the model lives on the GPU while the batch stays on the CPU, or the reverse. The error names two devices.
  • Dtype bug: labels are floats where integers are needed, or half precision overflows. Loss turns into not-a-number.
  • Mode bug: dropout and batch normalization act differently in training and in evaluation. If you forget eval mode at test time, results are noisy and lower.
  • Gradient bug: gradients add up across steps unless you clear them. A detached tensor or a no-gradient block cuts the graph, so some weights never update.
  • Sequence bug: one layer expects batch first and another expects time first. Shapes can still fit, so the model trains but learns nonsense.

How it works

  • Shape trace: write the shape after every line. Use tiny numbers like batch 2, time 5, hidden 16, vocabulary 100. The bug shows up where your expected shape and the real shape differ.
  • Language-model loss: logits have shape batch x time x vocabulary. Labels have shape batch x time. You flatten both so that each token is one row. Row count must match.
  • Mode flags change what layers do. Dropout drops units at random only in training mode. Batch normalization uses batch statistics in training and stored running statistics in evaluation.
  • Mixed precision: half-precision numbers have a small range. Small gradients can round to zero and big values can overflow. A loss scale multiplies the loss up before backward, then divides gradients back. A wrong or missing loss scale gives zero updates or not-a-number values.
  • Gradient flow: each update needs a path from the loss back to the weight. Frozen weights, detached tensors, and no-gradient blocks break that path.
  • Fast check of the whole pipeline: overfit one tiny batch. If loss does not fall to near zero, the bug is in code, not in data size.

When it matters

  • Most real training failures are small plumbing errors. Skill in fast triage saves days of GPU time.
  • Interviewers judge your reasoning, not your speed. Saying the layer expects 768 but got 512, so the embedding size is wrong, shows the skill.
  • The same checks apply to production. A silent shape or mode bug can degrade a live model for weeks.

Watch out

  • Do not fix the next error message without finding the cause. This creates a chain of patches.
  • Do not make random edits. State one hypothesis, test it, and then move on.
  • Do not trust that no error means no bug. A swapped axis often runs without any error.
  • Do not forget to retrace one batch after the fix. The fix may only move the error to the next layer.

1. Inference vs training

In short Training changes the weights. Inference keeps the weights fixed and only produces answers. Training needs much more memory per parameter than inference. Sort every speed or memory trick into one of these two sides first. This makes most interview answers easy.

Picture it

  • Real example: a fraud team trains a model on last year of card payments. That is training. Then the model scores each new payment in 20 milliseconds. That is inference.
  • Training loop: show data, run a forward pass, measure the error (the loss), run a backward pass to find how each weight should change, then update the weights. This repeats millions of times.
  • Inference loop: take the input, run a forward pass, return the result. No loss. No backward pass. No update.
  • During training the framework keeps the activations (the middle results of each layer). The backward pass needs them to compute gradients.
  • The optimizer keeps extra numbers per weight. Adam keeps two: a running mean of gradients and a running mean of squared gradients.
  • Technical example: training a 7B model with mixed precision and Adam needs about 16 bytes per parameter. That is 2 for BF16 weights, 2 for gradients, and 12 for FP32 master weights plus two Adam values. The total is about 112 GB before activations.
  • Inference of the same model in FP16 needs 2 bytes per parameter. That is about 14 GB for weights, plus the KV cache.
  • The goals differ. Training wants high throughput and stable learning. Inference wants low delay, high requests per second, and low cost.
  • Inference is also not free of state. A chat model keeps a KV cache that grows with every token.

How it works

  • Forward pass: inputs flow through layers. Each layer multiplies by its weights and passes the result on. Output is a prediction.
  • Backward pass: the loss flows back. Each layer uses its stored activations and the incoming signal to produce a gradient for its weights.
  • Update step: the optimizer reads the gradient and its own stored values, then writes new weights. Weights are the only thing that changes.
  • Inference code should switch to evaluation mode and turn off gradient tracking. This stops the framework from storing activations and stops dropout from acting.
  • Classify the tricks: gradient checkpointing, LoRA and QLoRA save training memory. KV cache, quantization, batching and speculative decoding speed up inference.

When it matters

  • Cost planning differs. Training is a one-time or periodic bill. Inference is a bill that grows with every user.
  • Memory math decides hardware. A 7B model trains on many GPUs but serves on one.
  • Knowing the side lets you pick the right fix. Out-of-memory while training needs checkpointing. Slow answers in production need batching or quantization.

Watch out

  • Do not say inference also learns. It does not, unless you build online learning on purpose.
  • Do not forget evaluation mode and no-gradient mode at inference. You waste memory and get wrong dropout behavior.
  • Do not count only weights when you plan memory. Add activations for training and the KV cache for inference.
  • Do not mix up the side. LoRA does not speed up inference by itself unless you merge it; it mainly saves training memory.

2. Tokens, logits, softmax → next-token prediction

In short Text is cut into tokens, which are small pieces of words, and each token becomes an integer ID. The model outputs one raw score, called a logit, for every token in its vocabulary. Softmax turns these scores into probabilities that add up to one. The model never outputs words directly. It outputs a distribution, and a decoding rule picks the next token.

Picture it

  • Real example: a support chatbot sees the text 'My card was decl'. The tokenizer cuts it into pieces such as 'My', ' card', ' was', ' decl'. Each piece maps to an ID.
  • Rule of thumb: one token is about 0.75 English words. Code, numbers and rare languages cost more tokens per word.
  • The model reads all tokens and builds a vector at the last position. A final layer turns that vector into one logit per vocabulary entry.
  • Technical example: with a vocabulary of 128,000 tokens, the model produces 128,000 logits at each step. Each logit is a real number and can be negative.
  • Tiny example with three tokens and logits 4, 2 and 1. Softmax gives about 0.84, 0.11 and 0.04. The biggest score gets a much bigger share.
  • A decoding rule picks one token from this distribution. The token is added to the text. The model then runs again on the longer text.
  • During training the target is the true next token. The loss is the negative log of the probability the model gave to that true token. A probability of 0.9 gives a small loss. A probability of 0.01 gives a large loss.
  • At each position of a training text, the model predicts the next token. A text of 1,000 tokens gives 1,000 training signals at once.
  • Logits are cheap to inspect. Many safety and format tools edit logits before softmax, for example to ban a token or force valid JSON.

How it works

  • Tokenizer: a fixed table learned from data. It maps text pieces to IDs and back. It does not change during model use.
  • Embedding table: each ID selects one row, a vector of numbers. The model works on these vectors, not on IDs.
  • Output layer: it multiplies the final vector by a matrix with one row per vocabulary entry. Each product is the logit for that token.
  • Softmax in words: raise e to the power of each logit so all values are positive, then divide by the sum. Formula: $p_i = e^{z_i} / \sum_j e^{z_j}$.
  • Log-probabilities are used in practice. Multiplying many small probabilities underflows to zero. Adding their logs does not.
  • The loop of predict, pick, append is called autoregressive generation. Each step depends on all earlier steps.

When it matters

  • Every sampling control works at this step. Temperature, top-k and top-p all edit logits or probabilities.
  • Token count sets cost and limits. Providers charge per token, and the context window is counted in tokens.
  • Tokenization explains odd failures. A model may miscount letters in a word because it sees pieces, not letters.

Watch out

  • Do not say the model outputs words. It outputs a distribution. The decoder chooses.
  • Do not call logits probabilities. Logits can be negative and do not add up to one.
  • Do not forget that the vocabulary is large. Softmax over 128,000 entries at every step is a real cost.
  • Do not assume tokens equal words. Budget for about 1.3 tokens per English word, and more for other scripts.

3a. Greedy decoding

In short Greedy decoding picks the single most likely token at every step. It is fast and gives the same answer each time. It can repeat itself and miss better full sentences. Use it when you want a stable and exact result, such as field extraction or classification.

Picture it

  • Real example: a bank KYC tool reads an ID and must output the name field exactly. Creative variation would be a bug. Greedy decoding gives one stable answer.
  • At every step the decoder looks at the probabilities for all tokens and takes the arg max, which means the largest one.
  • The chosen token is appended. The model runs again. The loop stops at an end token or a length limit.
  • Same prompt and same weights give the same text. This helps tests and audits.
  • Technical example: the next-token probabilities are 0.40 for 'A' and 0.60 for 'B'. Greedy takes 'B'. After 'B' the best next token has only 0.30. The full path scores 0.18. After 'A' the best next token has 0.90. That path scores 0.36. Greedy never sees it.
  • This is the short-sighted problem. A locally best step can lead to a worse whole answer.
  • Long outputs can loop. The text repeats a phrase because the same context keeps giving the same top token.
  • Setting temperature to zero in most tools means greedy decoding.

How it works

  • No random numbers are used. The only inputs are the weights and the text so far.
  • Per step cost is one forward pass. Greedy adds no extra work for choosing.
  • The method needs no sorting. A single scan for the largest value is enough.
  • Greedy does not find the most likely full sequence. Finding it exactly would need to test all paths, which is too expensive. Beam search tests a few.
  • Rules like repetition penalty edit logits before the pick. They help against loops but also change meaning if too strong.

When it matters

  • Structured output needs stable output. JSON, SQL, field extraction and labels work well with greedy.
  • Repeatable output helps debugging. You can replay a failure with the same text.
  • It is the cheapest decoding rule. It is a good baseline before you try anything else.

Watch out

  • Do not say greedy gives the best sentence. It gives the best next token at each step.
  • Do not use it for open chat or story writing. Text turns flat and repetitive.
  • Do not expect bit-exact repeats on a busy GPU. Floating-point order and batch mix can still flip a near tie.
  • Do not forget loops. Set a length limit and stop tokens.

3b. Temperature

In short Temperature divides the logits before softmax. A low value makes the top token dominate. A high value spreads probability to many tokens. It changes how random the output is. It does not change what the model knows.

Picture it

  • Real example: a SQL assistant needs the same correct query each time. A brainstorming tool for marketing slogans needs variety. The first uses temperature near 0. The second uses 0.8 to 1.0.
  • Think of temperature as a confidence dial on the distribution.
  • Technical example with logits 4, 2 and 1. At temperature 1 the probabilities are about 0.84, 0.11 and 0.04.
  • At temperature 0.5 the logits become 8, 4 and 2. The probabilities are about 0.98, 0.02 and 0.002. The top token almost always wins.
  • At temperature 2 the logits become 2, 1 and 0.5. The probabilities are about 0.63, 0.23 and 0.14. The weak tokens now appear often.
  • The order of tokens never changes. The best token stays best. Only the gap between tokens changes.
  • As temperature goes to zero, the result approaches greedy decoding.
  • As temperature goes very high, all tokens approach equal chance, and the text becomes noise.

How it works

  • What moves: each logit is divided by T. This is a scalar operation on a vector of vocabulary size.
  • What is compared: after softmax, the sampler draws a token in proportion to its probability.
  • Formula: $p_i = e^{z_i/T} / \sum_j e^{z_j/T}$. Dividing by a small T makes big gaps even bigger before the exponent.
  • Nothing in the model weights is updated. Temperature is a run-time setting only.
  • Temperature works together with top-k, top-p or min-p. Temperature changes the shape. The filters cut the tail.

When it matters

  • It is the first knob in every product that uses an LLM. Correct values reduce errors in extraction and reduce dull text in chat.
  • Higher temperature raises the chance of wrong facts, because unlikely tokens are chosen more often.
  • Teams often set different values per task in the same product.

Watch out

  • Do not say temperature makes the model smarter or dumber. It only changes sampling.
  • Do not expect temperature zero to give bit-exact repeats on GPUs. Floating-point order and batching can change results.
  • Do not raise temperature to fix repeated text without checking top-p. A wide tail at high T creates nonsense.
  • Do not forget that some APIs forbid zero and expect a tiny value instead.

3c. Top-k, top-p (nucleus), min-p sampling

In short Top-k, top-p and min-p cut the long tail of unlikely tokens before sampling. The model then samples only from the kept tokens, after rescaling their probabilities to add up to one. Top-k keeps a fixed count. Top-p keeps a count that adapts to the model's confidence. Min-p keeps tokens close to the best one.

Picture it

  • Real example: a chat assistant writes a reply to an upset customer. Without a cut, a rare token like a random foreign word can appear with small probability and ruin the sentence. A tail filter removes it.
  • Tiny distribution: tokens with probabilities 0.50, 0.25, 0.12, 0.06, 0.04 and 0.03.
  • Top-k with k equal to 3 keeps the first three. Their sum is 0.87. After rescaling they become about 0.57, 0.29 and 0.14.
  • Top-p with p equal to 0.9 sorts tokens and adds probabilities until the sum reaches 0.9. The sums are 0.50, 0.75, 0.87, 0.93. So four tokens stay.
  • Min-p with value 0.2 sets a threshold of 0.2 times the top probability, which is 0.10. Tokens with at least 0.10 stay. That keeps three tokens.
  • When the model is sure, for example the top token has 0.95, top-p keeps one or two tokens, but top-k with 40 keeps 40.
  • When the model is unsure, many tokens have small shares. Top-k with 40 may cut good options, while top-p keeps more.
  • Typical engine order: logits, then temperature, then top-k, then top-p or min-p, then sample.
  • Typical settings: top-p 0.9 to 0.95 for chat. Top-k 40 is a common older default.

How it works

  • Top-k sorts the probabilities and zeroes everything below the k-th place.
  • Top-p sorts the probabilities from large to small, finds the smallest set whose sum reaches p, and zeroes the rest.
  • Min-p compares each probability with the top one. It keeps token i only when $p_i \ge m \cdot p_{max}$. The rule scales with confidence.
  • After zeroing, the engine divides each kept value by the sum of kept values. This is renormalization.
  • Min-p stays stable at high temperature. A flat distribution has a low top probability, so the threshold is low, and more tokens stay. A peaked one has a high threshold.

When it matters

  • These filters control the balance of safety and variety in generated text.
  • They cost almost nothing next to the forward pass, so there is no reason to skip them.
  • Interviewers like to ask the difference between top-k and top-p. The answer is fixed count versus adaptive count.

Watch out

  • Do not forget that top-p of 1.0 and top-k of 0 means no filtering in most engines.
  • Do not assume the same order in every engine. Applying top-p before temperature gives a different set than after.
  • Do not combine very small k with very small p without need. The result is almost greedy.
  • Do not use these filters to fix wrong facts. They remove odd tokens but cannot add knowledge.

3d. Beam search

In short Beam search keeps the B best partial sentences at every step instead of one. It scores each by the sum of log-probabilities and returns the best finished one. It suits tasks with one right answer, such as translation or OCR. It costs about B times more than greedy and gives bland text in open chat.

Picture it

  • Real example: a warehouse OCR model reads a serial number from a blurry label. One wrong early character ruins everything. Beam search keeps several candidate readings and picks the best whole string.
  • Greedy keeps one path. Beam search with width 4 keeps four paths alive.
  • At each step every path is extended by every possible next token. That gives B times vocabulary-size candidates.
  • The engine scores all candidates and keeps only the best B overall. The other candidates are dropped.
  • Technical example: path A starts with probability 0.4, path B with 0.6. Greedy keeps only B and ends at a total of 0.18. Beam search with width 2 keeps both. Path A reaches 0.36. Beam search finds the better full sentence.
  • Scores are sums of log-probabilities. A product of many small numbers underflows. A sum of logs does not.
  • Every extra token adds a negative number to the sum. So short sentences have an unfair advantage. A length penalty divides the score by a power of the length to fix this.
  • Cost grows with B. Width 5 costs about five times the compute and memory of greedy for the cache.
  • Beam search is deterministic. Same input gives the same output.

How it works

  • State stored: for each beam, the token list, the total log-score, and its KV cache entries.
  • Compared: the scores of B times V candidates. The engine takes a top-B selection across all of them.
  • Updated: when beams share a prefix, the cache can be shared or copied. When a beam is dropped, its cache is freed.
  • A beam that emits the end token moves to a finished list. Search stops when the best finished score cannot be beaten by any live beam, or at a length limit.
  • Formula: score of a sentence is $\sum_t \log p(y_t | y_{<t})$, divided by length to a power alpha.

When it matters

  • It treats decoding as a search over whole sequences, not a single choice. This is a key idea.
  • It raises accuracy for tasks like translation, speech and OCR, where output must match one truth.
  • It shows the trade-off between quality and cost clearly, which is easy to explain in an interview.

Watch out

  • Do not confuse beam search with sampling. It is deterministic and it does not add variety.
  • Do not use large beams for chat. The text gets generic and repetitive.
  • Do not forget length normalization. Without it, short outputs win.
  • Do not forget the memory cost. Each beam holds its own cache, so large beams cut your batch size.

4. Prefill vs decode; TTFT, TPS, inter-token latency

In short Prefill reads the whole prompt in one parallel pass. Decode then makes one token per step. Prefill is limited by compute. Decode is limited by memory bandwidth. Time to first token (TTFT) mostly reflects queue wait plus prefill. Inter-token latency reflects decode.

Picture it

  • Real example: a support chat sends a 3,000-token policy document plus a short question. The user waits for the first word. Then the answer streams out. The wait is prefill. The streaming speed is decode.
  • Prefill: all prompt tokens enter the model together. The GPU does large matrix multiplications and stays busy with math. It also builds the KV cache.
  • Decode: each step handles one new token. The GPU must read all the weights and the whole KV cache from memory to produce that single token. Math units mostly wait for data.
  • TTFT is the time from request to first output token. It includes waiting in the queue, then prefill.
  • Inter-token latency (ITL), also called time per output token, is the gap between two output tokens. It sets how smooth the stream feels.
  • Tokens per second can mean per user or for the whole server. Always say which one.
  • Percentiles matter. p50 is the middle case. p99 is the slow one that one user in a hundred sees. Service promises are often made at p95 or p99.
  • Technical example: a 14 GB model on a GPU with 2 TB per second memory bandwidth reads 14 GB in 7 ms. So one sequence can decode at most about 140 tokens per second, whatever the compute speed.
  • Prefill example: a 2,000-token prompt on a 7B model needs about 28 teraflops of math. A modern data-center GPU does this in roughly 0.1 to 0.2 seconds.

How it works

  • Total latency is about TTFT plus (output tokens minus one) times ITL.
  • Prefill is parallel across tokens, so cost grows with prompt length but uses the hardware well.
  • Decode is serial across tokens, because each token needs the previous one. This cannot be parallelized inside one request.
  • Batching helps decode. One read of the weights serves every request in the batch, so more users share the same memory cost.
  • Long prompts can block decode steps of other users. Chunked prefill splits a big prompt into pieces to avoid this.

When it matters

  • Users judge a chat by TTFT first and by streaming speed second.
  • Each fix targets one phase. Long prompts need prefill fixes like prefix caching. Slow streaming needs decode fixes like quantization or speculative decoding.
  • Capacity planning needs both numbers. Mixing them leads to wrong GPU counts.

Watch out

  • Do not mix up the phases. Long prompts hurt TTFT. Long answers hurt total time.
  • Do not quote only the average. Tail latency decides user trust.
  • Do not assume bigger batches are free. Throughput rises, but each user may wait longer.
  • Do not state decode is compute-bound. At small batch it is memory-bandwidth-bound.

5. KV cache

In short The KV cache stores the keys and values of all past tokens. Each new token then computes only its own key and value and reuses the rest. This avoids repeating work at every step. The cost is memory. The cache grows with sequence length and with the number of users, and it can exceed the weights.

Picture it

  • Real example: a legal assistant answers questions about a 20-page contract kept in the prompt. Without a cache, each new word would re-read the whole contract through every layer. With the cache, the contract is processed once.
  • In attention, each token makes a query, a key and a value. The query asks what matters. Keys are labels. Values are the content to mix.
  • A new token's query is compared with the keys of all earlier tokens. The resulting weights mix their values.
  • In a causal model, earlier tokens never change. Their keys and values stay the same forever. So the model computes them once and stores them.
  • Without the cache, token 1,000 recomputes keys and values for 999 earlier tokens. Total work over the answer grows with the square of length.
  • With the cache, each step computes one new key and one new value per layer, then reads the stored ones.
  • Technical example: Llama-2-7B has 32 layers, 32 heads and head size 128, in FP16. Per token it stores 2 (key and value) x 32 x 4096 x 2 bytes, which is about 0.5 MB.
  • A 4,000-token chat then uses about 2 GB of cache for one user. Thirty users use 60 GB, more than four times the 14 GB of weights.
  • Only keys and values are cached. Queries are used once and then dropped.

How it works

  • Stored: for each layer, a key tensor and a value tensor for every token so far, usually per attention head.
  • Compared: the new query against all stored keys, to produce attention weights.
  • Updated: at each step, one new key and value per layer are appended. Nothing old is edited.
  • Size formula: 2 x layers x KV heads x head size x tokens x batch x bytes per number.
  • During prefill the cache is filled in one pass for the whole prompt. During decode it grows by one entry per layer per step.

When it matters

  • The cache sets the limit on batch size and context length. This is why many serving fixes target it.
  • Fixes include fewer KV heads (GQA), paged storage (PagedAttention), lower precision for the cache, and prefix sharing.
  • A stored cache for a shared system prompt can be reused across users to cut TTFT.

Watch out

  • Do not use the cache in training. Training processes the full sequence in parallel and does not need it.
  • Do not say the cache stores queries. It stores keys and values only.
  • Do not forget the cache when you size GPUs. Weights alone understate the need.
  • Do not assume the cache is free to keep. A long idle chat holds memory that other users could use.

6. PagedAttention (vLLM)

In short PagedAttention stores the KV cache in small fixed-size blocks that need not sit next to each other in memory. It works like virtual memory in an operating system. A table maps each request's logical blocks to physical blocks. This removes wasted space, so the server fits more requests at once and gains throughput.

Picture it

  • Real example: a chat service gets many requests. Some users send two words and get a short reply. Others paste a long report. The server cannot know the final length in advance.
  • Naive servers reserve one big contiguous slab per request, sized for the maximum length. Most of the slab stays empty.
  • Technical example: a 7B model needs about 0.5 MB per token. A request reserves 4,096 tokens, which is 2 GB. If it only uses 300 tokens, about 150 MB is used and about 1.85 GB is wasted.
  • Measured waste in older systems was often 60 to 80 percent of KV memory. This was due to reserved space, gaps between slabs, and size rounding.
  • vLLM cuts the cache into blocks of, for example, 16 tokens. For this 7B model a block is about 8 MB.
  • A block is given to a request only when the request needs it. Blocks can sit anywhere in GPU memory.
  • A block table per request lists which physical block holds each group of 16 tokens.
  • Waste per request is at most one half-filled block, less than 16 tokens, instead of thousands.
  • Reported gains are about 2 to 4 times higher throughput than earlier servers at the same latency.

How it works

  • Stored: a pool of equal-size physical blocks on the GPU, plus a block table in the scheduler for each request.
  • The attention kernel follows the table. It reads keys and values block by block instead of from one slab.
  • Updated: when a request fills its last block, the allocator hands it a free block and adds a table entry. When it ends, all its blocks return to the pool.
  • Sharing: requests with the same prefix, such as one system prompt, point to the same blocks. Copy-on-write makes a private copy only when one request must change a shared block.
  • Beam search and parallel sampling also use sharing. Branches share the prompt blocks.

When it matters

  • More free memory means more concurrent requests, so lower cost per token.
  • Prefix sharing cuts TTFT for repeated prompts, such as a long policy or tool list.
  • It makes continuous batching practical, because requests of different lengths join and leave without moving memory.

Watch out

  • Do not say PagedAttention speeds up one request. It improves memory use, which raises batch size and throughput.
  • Do not confuse it with FlashAttention. One manages cache storage. The other reduces memory traffic inside the attention math.
  • Do not ignore block size. Very small blocks raise table overhead. Very large blocks bring waste back.
  • Do not forget that the kernel must support the table. Plain attention kernels cannot read paged blocks.

7. Continuous batching

In short Continuous batching lets the server add new requests and remove finished ones at every decode step. This keeps the GPU busy. It replaces the old method of waiting for the whole batch to finish. It is one of the biggest levers for lowering the cost per token in LLM serving.

Picture it

  • Real example: a bank's support bot gets a steady flow of questions. Some answers are 20 tokens long. Others are 400 tokens. Users arrive at random times.
  • Static batching starts a fixed group together. The group ends only when the longest answer ends. Slots of short answers sit idle.
  • Technical example: a batch of 8 starts. Seven requests finish after 50 tokens. One needs 500 tokens. For 450 more steps, seven of eight slots do nothing, so the GPU uses about 12 percent of its slots.
  • Continuous batching, also called in-flight batching, schedules at every step. The moment a request emits its end token, its slot goes to a waiting request.
  • New requests need a prefill pass first. Engines can mix prefill chunks with ongoing decode steps in the same iteration.
  • Decode is memory-bound. One read of the weights serves every request in the batch. So extra requests add almost no time per step until compute becomes the limit.
  • Throughput can rise several times against static batching. Exact gains depend on length mix and load.
  • Late requests no longer wait for a whole batch to end. Their queue time drops.

How it works

  • The scheduler loop runs once per decode step. It checks which requests finished, frees their cache blocks, and admits waiting requests if memory allows.
  • Each step builds a batch of tokens from many requests. Each request has its own length and its own cache position.
  • A flexible cache is needed, because requests join and leave at different lengths. PagedAttention solves this.
  • Policies decide who goes first: first come first served, priority, or shortest job. If memory runs out, the engine can pause a request and swap or drop its cache.
  • Chunked prefill limits how many prompt tokens enter one step, so long prompts do not stall decoding for others.

When it matters

  • GPU time is the main cost of serving. Higher utilization cuts the bill directly.
  • It improves fairness. Short requests are not trapped behind long ones.
  • Common engines such as vLLM, TGI and TensorRT-LLM use it, so it is expected knowledge.

Watch out

  • Do not confuse it with dynamic batching. Dynamic batching waits a few milliseconds to group requests, then runs the whole forward pass for the group.
  • Do not assume a bigger batch always wins. Past the compute limit, each user gets slower.
  • Do not forget memory limits. Admitting too many requests can exhaust the KV cache.
  • Do not skip the tail latency check. Heavy load can push p99 up even while average throughput looks good.

8. Quantization (PTQ vs QAT; INT8/INT4; weights vs activations; calibration)

In short Quantization stores numbers in fewer bits, such as INT8 or INT4 instead of FP16. This cuts memory and speeds up memory-bound inference, with a small loss in accuracy. Each stored number is a small integer plus a scale that maps it back to a real value.

Picture it

  • Real example: a startup wants to run a 70B model for a document assistant. In FP16 the weights need 140 GB, which is two or more big GPUs. In INT4 they need about 35 GB plus scales, which fits one 48 GB or 80 GB GPU.
  • An FP16 number takes 2 bytes. INT8 takes 1 byte. INT4 takes half a byte.
  • The idea: find the range of a group of weights, split that range into a small grid, and store each weight as the nearest grid point. Rounding adds a small error.
  • Technical example: weights range from minus 0.8 to 0.8. With INT8 symmetric, the scale is 0.8 divided by 127, about 0.0063. A weight of 0.5 is stored as 79 and read back as about 0.4977.
  • With INT4 the scale is 0.8 divided by 7, about 0.114. The same 0.5 is stored as 4 and read back as 0.457. The error is bigger.
  • PTQ, post-training quantization, converts a finished model. A small calibration set of a few hundred samples helps choose ranges. Examples: GPTQ, AWQ.
  • QAT, quantization-aware training, simulates rounding during training, so the model learns to cope. It gives better results at very low bits but costs training time.
  • Weight-only quantization (for example 4-bit weights with 16-bit math) saves memory and bandwidth. It helps decode most.
  • Weight-and-activation quantization (INT8 for both) can use fast integer math units. It helps prefill and throughput, but activations have outliers that make it harder.

How it works

  • Stored: the integer codes, plus a scale per group, and sometimes a zero-point, which is an offset for asymmetric ranges.
  • Compared: calibration runs real inputs and records value ranges, so the scale fits real traffic.
  • At run time, a kernel reads the small integers, multiplies by the scale (dequantizes), and does the math, often in FP16.
  • Granularity: one scale per tensor is cheap but coarse. One per channel is better. One per group of, say, 128 weights is common for 4-bit. The extra cost is about 0.125 bit per weight.
  • Outliers: one huge value stretches the range, so all other values use fewer grid steps. Methods like AWQ and SmoothQuant protect or rescale the important channels.
  • Symmetric formula: scale equals max absolute value divided by $2^{b-1}-1$. The worst rounding error per weight is half a scale.

When it matters

  • It decides whether a model fits on your hardware at all.
  • Decode is limited by memory reads, so fewer bytes per weight give more tokens per second.
  • It also frees memory for KV cache, which allows more users per GPU.

Watch out

  • Do not say INT4 makes math four times faster. Weight-only INT4 mainly saves memory bandwidth. Math is often still FP16.
  • Do not use calibration data that differs from real traffic. Ranges will be wrong for your domain.
  • Do not skip evaluation after quantizing. Measure task accuracy and perplexity, and check rare cases like numbers and code.
  • Do not forget the scales. Real size is a little above the pure bit count.

9. GQA / MQA / MLA — shrinking the KV cache

In short Multi-head attention gives every query head its own key and value head. Multi-query attention (MQA) lets all query heads share one key-value head. Grouped-query attention (GQA) sits between them: groups of query heads share one key-value head. Fewer key-value heads mean a smaller KV cache and faster decode. Multi-head latent attention (MLA) goes further by storing a compressed vector instead.

Picture it

  • Real example: a company serves a chat model to 500 users at once. The KV cache, not the weights, fills the GPU. A model with GQA fits several times more users in the same memory.
  • In standard multi-head attention (MHA) with 32 heads, there are 32 query heads, 32 key heads and 32 value heads.
  • MQA keeps 32 query heads but only one key head and one value head. The cache shrinks 32 times. Some quality loss appears.
  • GQA keeps 32 query heads and, for example, 8 key-value heads. Each group of 4 query heads shares one pair. The cache shrinks 4 times with quality close to MHA.
  • Technical example: Llama-3-8B has 32 layers, 8 key-value heads and head size 128. Per token it stores 2 x 32 x 8 x 128 x 2 bytes, which is 128 KB. A full-head version would need 512 KB. At 8,000 tokens the cache is 1 GB instead of 4 GB.
  • Llama-2-70B and many other recent models use GQA. Mistral and Qwen families also use it.
  • MLA, used in DeepSeek models, compresses keys and values of each token into one small latent vector. The model stores that vector and expands it when needed. The DeepSeek-V2 paper reports a cache cut of more than 90 percent.
  • Queries still differ per head. That is why quality stays close to the full version.

How it works

  • What changes: the number of key and value projection matrices. Query projections stay the same.
  • In GQA each query head looks up the key-value head of its group. The same stored keys and values are read by several query heads.
  • The saved memory is in the cache and in the memory traffic per decode step. Less data is read per token.
  • Models are often trained with GQA from the start. Converting an MHA model afterward is possible by averaging heads and doing a short extra training.
  • MLA stores a latent vector. At attention time the model projects it back to keys and values, or folds the projection into the query math to avoid the expansion.

When it matters

  • Decode speed depends on memory reads. Smaller cache means faster steps.
  • More context or more users fit on one GPU.
  • Quality loss is small, so this is a cheap win. That is why most new open models use GQA.

Watch out

  • Do not say GQA reduces query heads or model width. It reduces only key-value heads.
  • Do not think MQA and GQA change the weights memory much. Savings are mostly in the cache.
  • Do not forget the quality side of MQA. One shared head can hurt accuracy on hard tasks.
  • Do not mix the acronyms with other terms. Grid, greedy and gradient checkpointing are different things from GQA.

10. FlashAttention (IO-aware attention)

In short FlashAttention computes exact attention in small tiles inside the fast on-chip memory of the GPU. It never writes the full score matrix to slow memory. The result is the same as normal attention, but with much less memory traffic. The bottleneck in attention is moving data, not multiplying numbers.

Picture it

  • Real example: a team trains a model on 8,000-token contracts. Normal attention runs out of memory. With FlashAttention the same job fits and runs faster.
  • A GPU has HBM, a large but slower main memory, and SRAM, a tiny but very fast memory on the chip. Reads and writes to HBM often cost more time than the math.
  • Normal attention builds the full score matrix, one score for every pair of tokens. It writes it to HBM, reads it back for softmax, writes the result, then reads it again to mix the values.
  • Technical example: for 8,192 tokens the score matrix has about 67 million entries per head. In FP16 that is about 134 MB per head per layer. With 32 heads it is about 4.3 GB per layer for one sequence.
  • FlashAttention splits queries, keys and values into tiles that fit in SRAM. It loads a tile, computes scores, applies softmax, mixes values, and then moves to the next tile.
  • The problem is that softmax needs the sum over all scores in a row. Tiles see only part. The fix is online softmax.
  • Online softmax keeps a running maximum and a running sum for each row. When a new tile has a larger maximum, the old partial results are rescaled.
  • All steps are fused into one kernel, so intermediate results stay in SRAM.
  • Memory use for attention falls from the square of the length to linear in the length.

How it works

  • Moves: tiles of Q, K and V go from HBM to SRAM. Only the final output goes back to HBM, plus small per-row statistics.
  • Stored: per row, a running maximum and a running sum. These are tiny.
  • Compared: each query tile is compared with each key tile, one pair at a time.
  • Updated: the output tile is rescaled and added to when a new key tile arrives, so it ends exact.
  • Backward pass: the score matrix is not saved. It is recomputed tile by tile from stored statistics. Extra math is cheaper than extra memory traffic.
  • FlashAttention is exact. It is not sparse and not approximate.

When it matters

  • It makes long context affordable in training and in prefill.
  • Reported speed gains are about 2 to 4 times for long sequences.
  • It is default in modern stacks, so you will meet it in every serious setup.

Watch out

  • Do not call it approximate attention. The output equals standard attention up to normal rounding.
  • Do not expect it to fix decode. Decode is limited by KV cache reads, which needs other tools such as PagedAttention and split-key decoding.
  • Do not forget that the number of math operations stays roughly the same. The win is fewer memory reads and writes.
  • Do not confuse it with PagedAttention. They solve different problems and work together.

11. Gradient checkpointing (activation checkpointing)

In short Gradient checkpointing saves only some activations during the forward pass and recomputes the others during the backward pass. It trades extra compute for lower memory. It applies to training only.

Picture it

  • Real example: a hospital team fine-tunes a model on long clinical notes of 8,000 tokens. The job runs out of GPU memory at batch size 1. With checkpointing it fits, and they train slower but successfully.
  • Backpropagation needs the activations of each layer from the forward pass. These are the middle results.
  • Normally the framework keeps all of them until the backward pass uses them. For long sequences and many layers, they take more memory than the weights.
  • With checkpointing, the framework saves the input of only some blocks, for example each transformer block's input.
  • During the backward pass, when it needs the missing activations of a block, it re-runs the forward pass of that block from the saved input.
  • Technical example: a 32-layer model stores 32 block inputs instead of all internal results of every layer. Activation memory drops by a large factor, often 3 to 10 times depending on settings.
  • The price is about one extra forward pass. Backward costs about twice a forward pass, so one step goes from about 3 units of work to about 4. That is roughly 25 to 35 percent slower.
  • With the square-root rule, n layers with about the square root of n checkpoints use memory proportional to the square root of n.
  • Result: you can use longer sequences or larger batches on the same GPU.

How it works

  • Stored: only checkpoint tensors. Everything else inside a block is thrown away after the forward pass.
  • Recomputed: the forward math of each block, right before its backward step.
  • Updated: gradients come out the same as without checkpointing, up to rounding. Randomness such as dropout must replay with the same random state to match.
  • Weights, gradients and optimizer states are not affected. They still use their full memory.
  • Choice of checkpoint points sets the balance. More checkpoints use more memory and less recompute.

When it matters

  • It is the first fix to try when training hits out-of-memory with long inputs.
  • It is standard in fine-tuning recipes with LoRA and QLoRA.
  • It lets small teams train on a single GPU what would need several.

Watch out

  • Do not apply it to inference. There is no backward pass, so there is nothing to save.
  • Do not expect it to cut weight or optimizer memory. Only activations shrink.
  • Do not forget the speed cost. Training takes roughly a third longer.
  • Do not forget the dropout replay. If random state is not restored, gradients become wrong.

12. Speculative decoding

In short Speculative decoding uses a small, fast draft model to guess several next tokens. The large model then checks all the guesses in one parallel pass. It keeps the correct ones and fixes the first wrong one. The output has the same distribution as the large model alone. Only the speed changes.

Picture it

  • Real example: a code assistant writes boilerplate such as imports and function headers. Many of those tokens are easy to guess. A small model guesses them cheaply and the big model confirms them in bulk.
  • Plain decode is slow because the big model makes one token per expensive step, and each step reads all its weights.
  • A draft model, perhaps 10 to 20 times smaller, generates k tokens one by one. Each draft step is cheap.
  • The big model then runs once over the prompt plus the k drafted tokens. This looks like prefill, so it is parallel and costs about the same as one normal step.
  • At each drafted position, the big model gives its own probability. The system compares it with the draft's probability.
  • Accepted tokens stay. At the first rejected token, the system samples a replacement from the big model's adjusted distribution and drops the rest of the draft.
  • Technical example: k equals 4 and each guess is accepted with chance 0.8. Expected tokens per big-model pass are about (1 minus 0.8 to the fifth) divided by 0.2, which is about 3.4.
  • After the cost of draft steps, the real speed-up is often 2 to 3 times.
  • Variants: a separate draft model, extra prediction heads on the big model (Medusa, EAGLE), and prompt lookup, which copies phrases from the prompt.

How it works

  • Stored: caches for both models. The big model's cache must roll back for rejected tokens.
  • Compared: for each drafted token, the ratio of big-model probability to draft probability decides acceptance. If the big model likes it at least as much, accept it. Otherwise accept with chance equal to the ratio.
  • This rejection rule is what keeps the final distribution exactly equal to the big model's.
  • Decode is memory-bound, so checking k tokens costs almost the same as checking one. That is why the trick works.
  • Acceptance rate depends on how well the draft matches the big model. Same model family and similar training data help.

When it matters

  • It lowers latency for single users without hurting quality. This suits chat and code tools.
  • It needs no retraining of the big model in the draft-model version.
  • It works best at low load, where the GPU has free compute. At high load the free compute is gone.

Watch out

  • Do not confuse it with distillation. The big model still runs at every step.
  • Do not use a weak draft model. Low acceptance wastes work and can make decoding slower.
  • Do not forget the memory cost. You must hold a second model or extra heads.
  • Do not claim it changes the output quality. With correct rejection sampling it does not.

13. Knowledge distillation

In short Distillation trains a small student model to copy a large teacher model. The student learns from the teacher's full output probabilities, not only from the right answer. It gives a faster and cheaper model that keeps most of the teacher's quality.

Picture it

  • Real example: a bank uses a large model to classify support emails into 40 categories. It is accurate but slow and costly. The team trains a small model on the large model's outputs and runs that in production.
  • A normal label says only: this image is a cat. A teacher's soft label says: 70 percent cat, 25 percent dog, 5 percent car.
  • The soft label carries dark knowledge. It tells the student that cats look more like dogs than like cars.
  • A temperature above 1 softens the teacher's distribution, so small probabilities become easier to see and learn from.
  • The student's loss mixes two parts: how far its softened output is from the teacher's, and the normal loss on true labels.
  • Technical example: DistilBERT is about 40 percent smaller and about 60 percent faster than BERT, and keeps about 97 percent of its language-understanding score.
  • For LLMs, a common method is sequence-level distillation. The teacher writes answers or reasoning steps for many prompts, then the student is fine-tuned on that text.
  • A second LLM method matches the teacher's token probabilities at each position, which gives richer signal than text alone.
  • The student can have a different and smaller architecture than the teacher.

How it works

  • Stored: teacher outputs, either live or saved offline for each training example.
  • Compared: student distribution against teacher distribution, using KL divergence, a measure of how different two distributions are.
  • Updated: only the student's weights. The teacher is frozen.
  • Formula: loss equals alpha times $T^2$ times KL of softened outputs, plus (1 minus alpha) times cross-entropy on true labels. The $T^2$ factor keeps gradient size stable when T changes.
  • Data matters. The student only learns the behavior shown in the prompts you give the teacher.

When it matters

  • It cuts serving cost and latency, and it makes edge and on-device use possible.
  • It can pass reasoning style from a strong model to a small one.
  • It is a clear alternative when quantization alone does not shrink the model enough.

Watch out

  • Do not confuse it with quantization. Distillation builds a new smaller model. Quantization keeps the same model with fewer bits.
  • Do not expect the student to beat the teacher on hard tasks. It usually trails on rare cases.
  • Do not forget license limits. Some providers forbid using their outputs to train competing models.
  • Do not train on teacher mistakes without filtering. The student copies errors too.

14. Pretraining vs continued pretraining vs SFT vs RLHF/DPO

In short Pretraining teaches a model language and world knowledge from raw text. Supervised fine-tuning (SFT) teaches it to follow instructions from example answers. RLHF and DPO then adjust the model toward answers people prefer. Each stage uses a different data type and a different loss, and each answers a different need.

Picture it

  • Real example: an insurance company wants a claims assistant. Pretraining gives general language. SFT teaches the company's reply format and tool calls. Preference tuning teaches the model to prefer polite, safe and clear answers.
  • Pretraining: predict the next token over trillions of raw tokens. It builds grammar and facts. It is the most expensive stage and runs on thousands of GPUs.
  • Continued pretraining: more next-token training on domain text such as legal, medical or telecom documents. It adds vocabulary and knowledge.
  • SFT: train on pairs of instruction and ideal answer. The loss counts only the answer tokens, not the prompt tokens.
  • Technical example: a typical SFT set has 10,000 to 100,000 good examples. Pretraining uses billions of times more tokens.
  • RLHF, reinforcement learning from human feedback: people rank pairs of answers. A reward model learns to predict the ranking. The LLM is then optimized with PPO, a reinforcement learning method, to raise reward.
  • A KL penalty keeps the tuned model close to the SFT model. Without it the model finds odd answers that fool the reward model.
  • DPO, direct preference optimization, skips the reward model. For each pair it raises the probability of the chosen answer and lowers that of the rejected one, relative to a frozen reference copy.
  • DPO is simpler and more stable than PPO. It needs a preference dataset and two copies of the model in memory.

How it works

  • Pretraining loss: negative log-probability of each true next token, averaged over the text.
  • SFT loss: the same loss, masked so that only response tokens count.
  • Reward model: usually the LLM with a scalar output head, trained so the chosen answer scores above the rejected one.
  • DPO compares log-probability ratios between the current model and the reference for the chosen and rejected answers. A scale beta controls how far the model may move from the reference.
  • Order in practice: pretrain, optional continued pretrain, SFT, then preference tuning.
  • Facts that change often belong in retrieval, not in weights.

When it matters

  • The stage you pick decides cost, data need and risk. SFT with LoRA is cheap. Pretraining is not.
  • SFT changes behavior and format well. Preference tuning changes tone, safety and ranking of good answers.
  • Many teams use SFT for behavior and RAG for facts, which is a common interview answer.

Watch out

  • Do not use SFT to inject changing facts. The model learns style faster than knowledge, and facts go stale. Use RAG.
  • Do not over-train on narrow data. The model can forget general skills. This is catastrophic forgetting.
  • Do not forget the KL leash in RLHF. Without it, the model learns to exploit the reward model.
  • Do not say DPO needs no data. It needs good preference pairs, and noisy pairs hurt.

15. LoRA (Low-Rank Adaptation)

In short LoRA freezes the original weights and trains two small matrices whose product is added to each chosen weight. Only the small matrices are trained and saved. This cuts trainable parameters and optimizer memory by a large factor. It lets you tune a big model on one GPU.

Picture it

  • Real example: a company serves 50 customers with one base model. Each customer needs its own tone and format. The team trains one small LoRA adapter per customer and swaps adapters at request time.
  • Full fine-tuning updates every number in every weight matrix. For a 7B model that means 7 billion trainable values and a very large optimizer state.
  • LoRA assumes that the change needed for a new task is simple. It lives in a few directions, a low-rank space.
  • The update is written as the product of two thin matrices, B and A, with a small inner size r called the rank. Typical r is 4 to 64.
  • A starts with random values. B starts at zero. So the product is zero, and at step 0 the model equals the base model.
  • Technical example: one weight matrix is 4,096 by 4,096, which has about 16.8 million numbers. With r equal to 8, A and B hold 8 x (4,096 + 4,096) which is 65,536 numbers. That is about 0.4 percent.
  • For a 7B model with r equal to 16 on query and value projections, the adapter has about 8 million values. In FP16 the file is about 17 MB, versus about 14 GB for the model.
  • LoRA is usually applied to attention projections, and often to the feed-forward layers too.
  • After training you can merge: add the product into the base weight. Then there is no extra delay at inference. Or keep adapters apart and swap them.

How it works

  • Frozen: all base weights. No gradients and no optimizer values are kept for them.
  • Trained: A and B in each adapted layer. Gradients and Adam values exist only for these.
  • Forward pass: output equals base weight times input, plus (alpha divided by r) times B times A times input. Formula: $h = W_0 x + (\alpha / r) B A x$.
  • Alpha is a scale. Dividing by r keeps the update size similar when you change r.
  • Memory saved: gradients and optimizer states for the base model. Activations are still needed, so gradient checkpointing still helps.
  • QLoRA goes one step further. It stores the frozen base in 4-bit and trains LoRA adapters in higher precision. A 7B base then needs about 4 GB.

When it matters

  • A single consumer or mid-range GPU can fine-tune a 7B model.
  • Small adapter files are easy to store, version and ship per customer.
  • One base model can serve many adapters, which saves GPU memory.

Watch out

  • Do not say LoRA shrinks the base model memory. It does not. QLoRA does that by quantizing the base.
  • Do not set r too small or pick too few target layers. The model underfits.
  • Do not forget alpha when you change r. Learning behavior shifts.
  • Do not expect LoRA to add many new facts. It is best for behavior, format and style.

16. QLoRA

In short QLoRA fine-tunes a large model on a small GPU. It stores the frozen base weights in 4 bits and trains small LoRA adapters in 16-bit precision. The base model never changes. Only the adapters learn, so the optimizer state stays tiny.

Picture it

  • Think of a 500-page reference book printed in tiny font to save paper. You keep the book unchanged and clip a few sticky notes on top. QLoRA works the same way: the book is the 4-bit base and the sticky notes are the adapters.
  • A team wants a legal-clause classifier from a 7B model. Full fine-tuning needs about 16 bytes per parameter for weights, gradients, and Adam states. That is roughly 112 GB. QLoRA needs about 4 to 6 GB for the model plus some activations, so one 24 GB card is enough.
  • The 65B case from the QLoRA paper: 16-bit weights alone take 130 GB. Full fine-tuning with Adam takes more than 780 GB. With 4-bit weights the base takes about 33 GB, so one 48 GB GPU can train it.
  • A 7B Llama with LoRA rank 16 on all linear layers has about 40M trainable parameters. In BF16 that is about 80 MB. Adam adds two FP32 states per parameter, so about 320 MB more.
  • Most training memory then comes from activations, not weights. Gradient checkpointing trades extra compute for lower activation memory.
  • Training speed is lower than plain LoRA by roughly 20 to 40 percent. Each step must dequantize the 4-bit weights before every matrix multiply.
  • Failure example: you train a QLoRA adapter, then merge it straight into the 4-bit weights. The rounding error in the merge changes outputs. Quality drops by a visible margin.

How it works

  • Storage: each base weight becomes a 4-bit code. The weights are cut into blocks of 64 values. Each block keeps one scale constant (the absmax of the block) so the codes can map back to real numbers.
  • NF4 (NormalFloat 4) uses 16 code levels placed at quantiles of a normal distribution. Pretrained weights look bell-shaped. So NF4 puts more levels near zero, where most weights sit. This gives lower error than evenly spaced INT4.
  • Double quantization: the scale constants cost 32 bits per 64 weights, which is 0.5 bits per weight. QLoRA quantizes these scales again to 8 bits in groups of 256. This saves about 0.37 bits per weight. On a 65B model this is about 3 GB.
  • Forward pass: the code loads a block of 4-bit weights, dequantizes it to BF16, and runs the matrix multiply. It then discards the BF16 copy. No full BF16 copy of the model ever exists.
  • Backward pass: gradients pass through the frozen dequantized weights to reach the adapters. The code does not compute or store weight gradients for the base.
  • Update: the optimizer changes only LoRA matrices A and B in BF16 or FP32. The adapted layer computes $Wx + (\alpha/r)BAx$, where W is the dequantized frozen weight.
  • Paged optimizers allocate optimizer state in unified memory. When GPU memory spikes, for example on a long batch, the driver pages state to CPU RAM and back. This avoids out-of-memory crashes.

When it matters

  • It is the default recipe when the interviewer says 'one GPU, big model, limited budget'. You must state the memory numbers to show you understand the trade.
  • It shows the split between storage dtype (4-bit) and compute dtype (BF16). Many candidates mix these up.
  • The paper showed QLoRA matches 16-bit full fine-tuning quality on several benchmarks. It is therefore a quality-preserving method, not just a hack.
  • It leads to follow-up questions on quantization error, adapter merging, and inference format.

Watch out

  • Merge error: do not merge adapters into the 4-bit base. Reload the base in BF16, merge, then re-quantize if needed. Then re-evaluate.
  • Compute dtype: FP16 compute can overflow in some layers. Use BF16 compute where the GPU supports it.
  • Training format is not serving format. The NF4 base is a training aid. For serving, many teams use AWQ, GPTQ, GGUF, or FP8 instead.
  • Out-of-memory still happens with long sequences. Activations scale with batch size and sequence length. Lower the sequence length or turn on gradient checkpointing.
  • Always mask prompt tokens in the loss for instruction data. Otherwise the model also learns to predict the prompt.

17. PEFT family (adapters, prefix/prompt tuning)

In short PEFT (parameter-efficient fine-tuning) trains a tiny set of new or selected parameters. The base model stays frozen. The family includes adapters, prefix tuning, prompt tuning, LoRA, IA3, and BitFit. Each method differs in where it adds trainable parameters and what it costs at inference.

Picture it

  • One company serves 50 customers from one base model. Each customer gets a small adapter file of 20 to 100 MB instead of a 14 GB model copy. The server swaps adapters per request. Storage drops from 700 GB to under 5 GB.
  • Adapters (Houlsby style) insert a small bottleneck MLP inside each layer. It maps d to r, applies a nonlinearity, maps back to d, and adds a residual. For BERT-base with d=768 and r=64, one adapter has about 98K weights. Two per layer across 12 layers gives about 2.4M, which is about 2 percent of 110M.
  • Prefix tuning learns key and value vectors that sit in front of the real tokens at every layer. For a 7B Llama with 20 prefix tokens, 32 layers, and d=4096, that is 20 x 2 x 32 x 4096, about 5.2M parameters.
  • Prompt tuning is simpler. It learns only soft input embeddings. With 20 tokens and d=4096 that is about 82K parameters. It matches full fine-tuning only for very large models, at around 10B parameters and up.
  • IA3 learns scaling vectors that multiply the keys, the values, and the FFN activations. It trains about 0.01 percent of the parameters. BitFit trains only bias terms, about 0.1 percent.
  • LoRA adds a low-rank update to weight matrices. After training you can merge it into the base weights, so inference adds zero latency.
  • Failure example: a prompt-tuning run on a 350M model with a default learning rate stays at the base loss. Small models need a large learning rate and good initialization. Full LoRA works with far less tuning.
  • Rule of thumb: LoRA is the default. Adapters suit multi-task setups. Prefix and prompt tuning suit cases where you must not touch any weights.

How it works

  • What is stored: for adapters, two small matrices per insertion point. For prefix tuning, a table of shape (prefix_len, layers x 2 x d). For prompt tuning, a table of shape (prompt_len, d). For IA3, vectors of size d or ffn_dim.
  • What is compared: the training loss on the downstream task. The gradient flows through the frozen model to the new parameters. Frozen weights get no gradient update.
  • Prefix tuning changes the attention keys and values. Each real token can attend to the learned prefix. The prefix is not a text token. It lives directly in key/value space at each layer.
  • Prompt tuning injects soft vectors only at the input layer. Later layers receive them through normal computation. This is why it needs a big model to work well.
  • Adapter at inference: the extra layers run in sequence, so each layer adds latency. LoRA avoids this by merging $W' = W + BA$. IA3 can also fold its scales into existing weights.
  • Optimizer memory shrinks with trainable count. Adam stores 8 extra bytes per trainable parameter in FP32. With 40M trainable parameters that is 320 MB. With 7B it would be 56 GB.

When it matters

  • Interviewers ask you to compare methods by trainable count, inference latency, and context cost. Have one number for each.
  • Multi-tenant serving is a real use case. One base model plus many hot-swappable adapters cuts cost sharply.
  • It tests whether you know why LoRA won: no inference cost, simple, and works across model sizes.
  • It separates a reasoned answer from a memorized list.

Watch out

  • Prefix tokens use context window space and attention compute. A 100-token prefix costs 100 tokens of your context limit.
  • Adapters add serial layers and latency. At small batch sizes this is visible.
  • Prompt tuning is unstable on small models. It is also sensitive to the initialization and the learning rate.
  • Fewer trainable parameters does not mean lower training memory. Activations still dominate for long sequences.
  • Adapters trained on one base checkpoint do not transfer to another base. Version the base and the adapter together.

18. Serving stack: batch vs online; API servers (concepts)

In short Online serving answers one user request in real time behind an API. Batch serving processes a large dataset offline to maximize throughput and lower cost. LLM serving adds special problems: a growing KV cache, token-by-token decoding, and continuous batching.

Picture it

  • A chat assistant is online serving. A user waits and watches tokens appear. A nightly job that summarizes 2 million support tickets is batch serving. Nobody waits. Cost per token matters more than latency. Providers often price batch jobs at about half the online price.
  • Online latency has two parts. TTFT (time to first token) is dominated by prefill, where the model reads the whole prompt in parallel. TPOT (time per output token) is dominated by decode, where it produces one token per step.
  • Decode is memory-bound. A 7B model in FP16 is 14 GB. A GPU with 2 TB/s memory bandwidth reads all weights in about 7 ms. So one stream cannot exceed about 140 tokens per second, whatever the FLOPs.
  • Batching fixes this. If 32 requests decode together, the same 14 GB read serves 32 tokens. Throughput rises almost 32 times while per-token latency rises only a little.
  • The KV cache stores keys and values for every past token. For Llama-2-7B it is 2 x 32 layers x 4096 x 2 bytes, about 0.5 MB per token. A 4,000-token chat takes 2 GB. Forty such chats take 80 GB.
  • Continuous batching (iteration-level scheduling) lets new requests join the running batch at every step. Static batching waits for the slowest request, so short answers sit idle. Continuous batching can lift throughput several times.
  • PagedAttention (vLLM) stores the KV cache in fixed-size blocks, like OS memory pages. This removes fragmentation. Without it, 60 to 80 percent of KV memory can be wasted on reserved but unused space.
  • The API layer sits in front: authentication, rate limits, request queue, streaming over server-sent events, timeouts, health checks, and autoscaling on queue depth.
  • Failure example: a cold start. A new replica must load 14 GB of weights and warm up. That takes 30 to 90 seconds. Autoscaling that reacts only after the queue grows will miss the traffic spike.

How it works

  • Prefill: the server runs the full prompt through the model once. It writes K and V for every prompt token into the cache. This step is compute-bound.
  • Decode: each step takes the last token, computes its Q, K, V, appends K and V to the cache, and attends over the whole cache. The step is memory-bound.
  • The scheduler keeps a queue of waiting requests and a set of running ones. At each step it checks free KV blocks. It admits a new request only if enough blocks exist.
  • When memory runs out, the scheduler preempts a request. It either swaps its blocks to CPU or drops them and recomputes later.
  • Streaming sends each token as it is sampled. The client sees output while decode continues. A client disconnect should cancel the request and free its blocks.
  • Batch serving writes results to storage, retries failed rows, and checkpoints progress. It sorts inputs by length to cut padding waste.

When it matters

  • You must say which metric you optimize: p99 latency, throughput, or cost. They conflict.
  • KV cache math is a common interview question. Be ready to compute it from layers, heads, head dimension, and dtype.
  • Serving cost often exceeds training cost over a product's life. Good batching changes the unit economics.
  • It shows you know decode is bandwidth-bound, which explains quantization, GQA, and speculative decoding.

Watch out

  • Head-of-line blocking: one 30,000-token prompt delays everyone else's prefill. Use chunked prefill or separate queues.
  • Unbounded queues turn overload into huge latency. Set a queue limit and return a 429 error.
  • KV cache out-of-memory is the most common crash. Cap max context and max concurrent sequences.
  • Measure p95 and p99, not the average. The tail is what users feel.
  • Do not benchmark with short, uniform prompts. Real traffic has mixed lengths.

19. Model formats: safetensors, ONNX, GGUF

In short A model format defines how weights are saved on disk. safetensors stores raw tensors safely. ONNX stores a portable compute graph. GGUF packs quantized models and metadata for llama.cpp. The format decides loading speed, safety, portability, and which runtime can run the model.

Picture it

  • Think of shipping furniture. safetensors is flat-pack parts with a clear label sheet. ONNX is a full instruction manual that any workshop can follow. GGUF is a compact kit with everything inside one box for a home garage.
  • Some classic weight files can run code when opened. A file from an unknown source can steal credentials at load time.
  • safetensors fixes that. The file starts with an 8-byte little-endian number giving the header length. A JSON header follows. It lists each tensor name, dtype, shape, and byte offsets. Raw bytes follow. No code runs on load.
  • Because offsets are known, the loader memory-maps the file. It can load one tensor without reading the rest. Large models are sharded into files like model-00001-of-00004.safetensors with an index JSON mapping names to shards.
  • ONNX stores a protobuf graph of operators (MatMul, Gelu, Softmax) with an opset version. onnxruntime, TensorRT, and mobile runtimes can run it without PyTorch. Protobuf has a 2 GB limit, so large weights go to external data files.
  • GGUF is one file with key-value metadata (architecture, context length, tokenizer, chat template) and tensors quantized in blocks. A 7B model is about 13.5 GB in FP16, about 7.2 GB in Q8_0, and about 4.1 GB in Q4_K_M.
  • Real example: a laptop app ships a Q4_K_M GGUF of a 7B model at 4.1 GB. It runs on a CPU with 8 GB RAM through memory mapping.
  • Failure example: you export a model with dynamic control flow to ONNX. The tracer freezes one branch and fixes shapes. Outputs are wrong for other input lengths.

How it works

  • safetensors stores per tensor: name, dtype (F16, BF16, F32), shape, and start and end byte offsets. It stores no graph and no code. The architecture must come from a separate config file.
  • ONNX stores nodes, edges, initializers (the weights), input and output shapes, and the opset. A runtime applies graph optimizations such as operator fusion and constant folding before running.
  • GGUF stores a header, a metadata table, tensor info (name, shape, quant type, offset), and aligned tensor data. Quantization is per block: for example Q4_0 groups 32 weights with one scale.
  • K-quants (Q4_K_M) use super-blocks of 256 weights with sub-block scales. 'M' means medium, a mix that keeps sensitive tensors at higher bit width.
  • Conversion steps: take a tensor-only weight file, rename tensors to the target runtime scheme, copy tokenizer data, and quantize blocks for a packed local format.
  • The tokenizer and chat template are not part of safetensors weights. They live in separate JSON files. GGUF embeds them.

When it matters

  • Format choice is a deployment decision: safety, hardware target, and runtime support all depend on it.
  • Interviewers test whether you know why some weight formats can run code on load, and why a tensor-only format became the safe default.
  • You should map format to runtime: safetensors with vLLM or Transformers, ONNX with onnxruntime or TensorRT, GGUF with llama.cpp or Ollama.

Watch out

  • Never open an untrusted classic weight file that can run code. Prefer a format that stores only tensors and a header.
  • ONNX export can fail or silently change behavior on unsupported operators and dynamic shapes. Compare outputs against PyTorch on several input lengths.
  • A GGUF with the wrong chat template produces poor answers even when the weights are correct.
  • Quantized formats lose precision. Evaluate the quantized model on your own task, not only on perplexity.
  • Mixing dtype assumptions, for example loading BF16 weights as FP16, can overflow. Check dtype in the header.

20. What is a language model?

In short A language model assigns a probability to the next token given all earlier tokens. It chains these predictions to score or generate whole sequences. Training teaches the model to give high probability to the real next token in text.

Picture it

  • Think of phone keyboard autocomplete. You type 'See you to' and it suggests 'morrow', 'night', and 'day'. An LLM does the same at a much larger scale, with thousands of tokens of context.
  • Concrete example: input 'The capital of France is'. The model outputs a probability for every token in a 32,000-token vocabulary. ' Paris' may get 0.92. ' Lyon' may get 0.01. All 32,000 probabilities sum to 1.
  • The chain rule gives the probability of a whole sentence: $P(x_1 \dots x_n) = \prod_t P(x_t \mid x_{<t})$. We multiply the per-token probabilities. In practice we add logs to avoid underflow.
  • Training loss is cross-entropy: the negative log probability of the true next token. At random initialization with 32,000 tokens the loss is about ln(32000) = 10.4. A well-trained 7B model reaches about 1.8 to 2.2 on general web text.
  • Perplexity is exp(loss). A loss of 2.0 gives perplexity 7.4. The model is as uncertain as if it chose among about 7 equally likely tokens at each step.
  • One training sequence of 2,048 tokens gives 2,048 training signals in one forward pass. Each position predicts the next token. Labels are the input shifted left by one.
  • Generation is a loop. Predict a distribution, pick a token, append it, and repeat. Greedy picks the top token. Temperature, top-k, and top-p add controlled randomness.
  • Failure example: greedy decoding on an open-ended prompt gets stuck in a repetition loop such as 'I think that I think that I think...'.

How it works

  • Input: token IDs. The model embeds them, runs transformer layers, and produces a hidden vector per position.
  • Output head: a matrix of size d_model x vocab (4096 x 32000 is 131M weights) turns the last hidden vector into logits, one score per token. Softmax turns logits into probabilities.
  • Training compares the logit distribution at each position with the true next token. The loss gradient updates all weights. Pretraining sees trillions of tokens.
  • Temperature divides logits before softmax. Low values sharpen the distribution. High values flatten it. Top-k keeps the k best tokens. Top-p keeps the smallest set whose probability sums to p.
  • Base model: trained only on next-token prediction. Instruction model: further tuned on instruction-response pairs and preference data, so it follows requests.
  • Teacher forcing: during training the model sees the true previous tokens, not its own earlier guesses.

When it matters

  • Every other topic builds on this. Attention, masking, and scaling laws all serve next-token prediction.
  • It explains hallucination: the model optimizes for plausible continuation, not for truth.
  • Perplexity and loss are the standard measures. You should know their meaning and limits.

Watch out

  • Fluent does not mean correct. A model gives high probability to plausible text even when the fact is wrong.
  • Exposure bias: training uses true history, but inference uses the model's own output. Errors can compound.
  • Perplexity depends on the tokenizer. You cannot compare perplexity between models with different vocabularies.
  • Low perplexity on web text does not guarantee good task accuracy.
  • Do not confuse a base model with a chat model. A base model may continue your question with more questions.

21. Tokenization & embeddings

In short Tokenization splits text into sub-word pieces and maps each to an integer ID. An embedding table then maps each ID to a learned vector. These vectors are the model's real input. Similar meanings end up near each other after training.

Picture it

  • Think of Lego bricks. Common words are single big bricks. Rare words are built from smaller bricks. 'unhappiness' may become 'un', 'happi', 'ness'. No word is ever unknown, because the smallest bricks are single bytes.
  • BPE (byte-pair encoding) starts with bytes or characters. It counts adjacent pairs in the training text. It merges the most frequent pair into a new token. It repeats until the vocabulary reaches the target size, for example 32,000 for Llama 2 or about 128,000 for Llama 3.
  • The embedding table has one row per token. With 32,000 tokens and d=4096 it has 131M weights. In FP16 that is 262 MB. A lookup copies one row. It is not a matrix multiply.
  • Token cost is real money and real context. English text averages about 1.3 tokens per word. Hindi or Tamil text can need 3 to 10 times more tokens with an English-centered tokenizer. The same question costs more and fits less context.
  • Failure example: a model fails at 'How many r letters are in strawberry?'. The tokenizer shows it 'str', 'aw', 'berry'. It never sees single letters.
  • Another failure: the number 12345 may split as '123' and '45', while 12346 splits as '1234' and '6'. Arithmetic becomes inconsistent because digit grouping changes.
  • After training, related tokens have close vectors. 'king' and 'queen' sit near each other. Direction can encode relations, but modern contextual models use the table only as the first layer.
  • Special tokens such as BOS, EOS, and role markers control the format. A wrong special token breaks chat behavior.

How it works

  • Stored: a vocabulary file (token string to ID) and a merge list or a unigram score table. Also stored: the embedding matrix E of shape (vocab, d).
  • Encoding steps: normalize text, pre-split into pieces, apply merges in priority order, and look up IDs. Decoding joins the token strings back to text.
  • Byte-level BPE (GPT-2 and later) works on UTF-8 bytes, so any input can be encoded. WordPiece (BERT) uses a ## continuation marker. SentencePiece treats text as a raw stream and marks spaces with a special symbol.
  • Embedding gradients are sparse. A batch updates only the rows of tokens it contains. Rare tokens get few updates and stay poorly trained.
  • Weight tying shares the input embedding matrix with the output head. This saves 131M parameters in the example above and often helps small models.
  • Vocabulary size trade-off: a larger vocabulary gives shorter sequences and cheaper attention. It also makes the embedding table and output softmax bigger.

When it matters

  • Many odd LLM failures trace to tokenization: spelling, arithmetic, and non-English quality.
  • Token count drives API cost and the usable context window. You must estimate it.
  • A tokenizer mismatch between training and serving silently ruins output. Interviewers like this bug.

Watch out

  • Always use the exact tokenizer that ships with the checkpoint. A different one gives garbage with no error.
  • Whitespace and casing change tokens. 'Hello' and ' Hello' are different IDs.
  • Glitch tokens exist: tokens seen in tokenizer data but almost never in model training. They can trigger strange outputs.
  • Truncating by characters instead of tokens can cut a multi-byte character or exceed the model limit.
  • Chat templates add tokens. Count them in the context budget.

22. Positional encoding & RoPE

In short Self-attention has no sense of order by itself. Positional encoding adds order information. RoPE (rotary position embedding) rotates query and key vectors by an angle that depends on position. With RoPE the attention score depends on the relative distance between two tokens.

Picture it

  • 'Dog bites man' and 'Man bites dog' have the same words. Without position information, attention sees the same set of tokens. The meaning is lost.
  • Early fix: learned absolute positions. GPT-2 stores a table of 1,024 rows, one vector per position, and adds it to the token embedding. It cannot handle position 1,025. There is no row.
  • Sinusoidal encoding from the original Transformer adds fixed sine and cosine waves of different frequencies. It needs no training but extrapolates poorly in practice.
  • RoPE treats each head vector as pairs of numbers. A head of size 128 gives 64 pairs. Each pair is rotated in its own 2D plane by angle $m \theta_i$, where m is the token position and $\theta_i = 10000^{-2i/d}$.
  • Low pairs rotate fast and capture fine local offsets. High pairs rotate slowly and capture long range. This is like a clock with a second hand, a minute hand, and an hour hand.
  • The key property: rotating q by position m and k by position n makes their dot product depend on m minus n. The model sees relative distance without a learned table.
  • Real example: Llama 2 was trained with 4K context. To serve 32K, teams scale positions down by 8, so position 32,000 acts like 4,000. This is position interpolation. A short fine-tune restores quality.
  • Failure example: you run a 4K-trained model at 16K with no change. Positions beyond training were never seen. Perplexity explodes and outputs turn to noise.

How it works

  • RoPE is applied to Q and K only. It is not added to the token embedding. V is untouched, so values carry content, not position.
  • Per position m, the code computes cos and sin of $m\theta_i$ for each pair. It multiplies each (q_{2i}, q_{2i+1}) pair by the 2x2 rotation matrix. It does the same for K.
  • Cached keys in the KV cache are stored already rotated. Each new token rotates with its own absolute position, and relative offsets still come out right.
  • The base 10000 sets the wavelength range. Llama 3 uses base 500000 to support longer context. Changing the base changes every rotation.
  • Extension methods: position interpolation squeezes all positions. NTK-aware scaling changes the base so high frequencies keep resolution. YaRN mixes both per frequency band and adds an attention temperature.
  • ALiBi is another option. It adds a linear distance penalty to attention scores and has no learned or rotated vectors.

When it matters

  • RoPE is the standard in Llama, Mistral, Qwen, and many others. Interviewers expect you to explain it.
  • Context extension is a hot practical topic. You should explain why naive extension fails.
  • It links to KV cache, long-context cost, and lost-in-the-middle behavior.

Watch out

  • A mismatch in RoPE layout, interleaved pairs versus first-half/second-half pairs, gives garbage output with a loaded checkpoint.
  • Wrong rope base or scaling in a converted model quietly reduces long-context quality.
  • A long advertised context window does not mean good use of it. Accuracy often drops for facts in the middle.
  • Interpolation reduces resolution for nearby tokens. Some fine-tuning is needed.
  • Absolute learned positions cannot extrapolate. Do not claim they can.

23. Self-attention (Q, K, V)

In short Self-attention lets each token build a new vector as a weighted mix of all visible tokens. Each token makes a query, a key, and a value. The query is compared with all keys to get weights, and those weights mix the values. The formula is $\text{softmax}(QK^T/\sqrt{d_k})V$.

Picture it

  • Think of a library. Your query is what you search for. Each book spine is a key. The book content is the value. You score every spine, pick the best matches, and blend their content into one answer.
  • Sentence: 'The animal did not cross the street because it was too tired.' The token 'it' makes a query. The key for 'animal' scores high against it. The new vector for 'it' then carries much of 'animal'.
  • Shapes: X has n tokens and d columns. Three learned matrices $W_Q$, $W_K$, $W_V$ (each d x d_k) produce Q, K, V. With n=4,096 and d_k=128, Q is 4,096 x 128.
  • The score matrix is $QK^T$, size n x n. For n=4,096 that is 16.8M scores per head. In FP16 that is 33 MB per head. With 32 heads, one layer would need about 1 GB if stored in full.
  • Why divide by $\sqrt{d_k}$: a dot product of d_k unit-variance numbers has variance d_k. At d_k=128 the std is about 11. Softmax on such large values becomes almost one-hot, and gradients vanish. Dividing restores variance 1.
  • Softmax per row turns scores into weights that sum to 1. The output row is the weighted sum of V rows. Each output is a vector of size d_k.
  • Cost grows as n squared. Doubling the context makes score computation and memory four times bigger. This is the main reason long context is expensive.
  • FlashAttention computes the same result in tiles that fit in fast on-chip SRAM. It never writes the full n x n matrix to GPU memory. It is faster and uses linear memory.
  • Failure example: padding tokens are not masked. A short sentence in a batch pays attention to pad vectors. Outputs shift depending on how much padding the batch has.

How it works

  • Learned parameters: $W_Q$, $W_K$, $W_V$, and an output projection $W_O$. Each is d x d in a standard layer. For d=4096, four matrices give about 67M weights per layer.
  • Step 1: multiply X by the three matrices. Step 2: compute scores QK^T and scale. Step 3: apply the mask. Step 4: softmax each row. Step 5: multiply by V. Step 6: apply $W_O$.
  • Query and key live in the same space so their dot product is meaningful. Value can carry different information. A token can be matched by one feature and contribute another.
  • Softmax is computed in FP32 or with a running max trick to avoid overflow. Subtracting the row maximum does not change the result.
  • In decoding, past K and V are cached. Only the new token computes its Q, K, V. Each step costs O(n) per head instead of O(n squared).
  • Attention weights are not a full explanation of model decisions. They show mixing, not causal importance.

When it matters

  • This is the core question in transformer interviews. Be ready to write the shapes by hand.
  • It explains the n squared cost, which drives FlashAttention, sparse attention, GQA, and KV cache design.
  • It supports follow-ups on masking, multi-head attention, and numerical stability.

Watch out

  • Forgetting the scale factor gives saturated softmax and training that stalls.
  • Forgetting the padding or causal mask leaks information or adds noise.
  • FP16 scores can overflow. Use a stable softmax and BF16 or FP32 accumulation.
  • Models often put large weight on the first token as an 'attention sink'. This is normal. Dropping it in long-context streaming breaks quality.
  • Do not say attention is O(n) in the KV-cached decode loop for total generation. Total cost over n steps is still O(n squared).

24. Multi-head attention

In short Multi-head attention runs several smaller attentions in parallel. Each head has its own Q, K, V projections. The outputs are concatenated and mixed by an output matrix. Different heads can track different relations at the same time, at the same total parameter cost.

Picture it

  • A reader of a legal contract tracks several things at once: who signs, which dates apply, and which clauses refer to others. One head cannot hold all of these in one set of weights. Several heads can split the job.
  • Llama-2-7B: d_model=4096 with 32 heads. Each head has dimension 128, so 32 x 128 = 4096. Each head attends over the same tokens but in its own 128-dimensional subspace.
  • Parameter count does not grow. One big attention uses $W_Q$ of size 4096 x 4096. Multi-head uses 32 slices of size 4096 x 128. The total is the same 16.8M weights per matrix.
  • Trained heads often specialize. Some track the previous token. Some link a verb to its subject. Some copy earlier tokens in repeated patterns (induction heads). Many are redundant, and some can be pruned with little loss.
  • Memory problem: every head has its own K and V in the cache. For Llama-2-7B this is about 0.5 MB per token. Large batches of long chats fill the GPU.
  • MQA (multi-query attention) uses one K and V head shared by all query heads. The cache shrinks by 32 times, with some quality loss.
  • GQA (grouped-query attention) is in the middle. Llama-2-70B uses 64 query heads and 8 KV heads. Each KV head serves 8 query heads. The cache is 8 times smaller than full multi-head with little quality loss.
  • Failure example: a team converts an MHA checkpoint to GQA by averaging KV heads and does not fine-tune. Quality drops. The paper recipe mean-pools heads and then trains for about 5 percent of the original compute.

How it works

  • Computation: project X to Q, K, V of size n x d. Reshape to (heads, n, d_head). Run attention per head. Reshape back to n x d. Multiply by $W_O$.
  • Head outputs are concatenated, not averaged. $W_O$ then mixes information across heads. Without it, heads would stay separate.
  • Attention scores are computed per head. The score tensor has shape (batch, heads, n, n). This tensor is why long context is memory-heavy without FlashAttention.
  • With GQA, K and V projection matrices are smaller: d x (kv_heads x d_head). At serve time the KV heads are broadcast to their query group.
  • Tensor parallelism splits heads across GPUs. Each GPU holds a subset of heads, and an all-reduce after $W_O$ combines the result. The head count, or KV head count, must divide evenly by the GPU count.
  • Each head works on a smaller dimension. Per-head cost is lower, so total compute is close to single-head attention at full width.

When it matters

  • Interviewers ask why multiple heads help and what MQA and GQA change. Give the cache-size numbers.
  • GQA is standard in modern open models, so serving cost questions lead here.
  • It tests understanding of reshape and tensor shapes, a common coding screen.

Watch out

  • A wrong reshape or transpose mixes heads or tokens. Shapes still match, so no error appears. Test with a tiny known example.
  • Too small a head dimension (below 64) limits what each head can represent.
  • Do not claim each head learns a clean human-readable role. Many heads are redundant or unclear.
  • MQA and GQA reduce KV memory, not the weights of the FFN. Total model size stays mostly the same.
  • Tensor-parallel sharding fails or wastes memory if heads do not divide by GPU count.

25. Transformer block (LayerNorm, residual, FFN)

In short A transformer block has an attention sub-layer and a feed-forward network (FFN) sub-layer. Each is wrapped with normalization and a residual (skip) connection. The model stacks dozens of these blocks. Attention mixes information across tokens. The FFN transforms each token on its own.

Picture it

  • Think of an assembly line with a conveyor belt that runs the full length. Each station reads the belt, computes a small change, and adds it back. The belt is the residual stream. No station replaces the product. Each station adds to it.
  • Pre-LN layout: $x = x + \text{Attn}(\text{Norm}(x))$, then $x = x + \text{FFN}(\text{Norm}(x))$. A final norm follows the last block.
  • Llama-7B numbers: d=4096, 32 layers. Attention has 4 x 4096 x 4096, about 67M weights. The SwiGLU FFN has three matrices of 4096 x 11008, about 135M weights. So the FFN holds about two thirds of block parameters.
  • Total: 32 blocks x about 202M = 6.5B. Add the 131M input embedding and the 131M output head, and you reach about 6.7B.
  • A classic FFN expands d to 4d, applies GELU, and projects back to d. Llama uses SwiGLU: two parallel up-projections, one gated by SiLU and multiplied elementwise, then a down-projection. Hidden size is about 8/3 d to keep the parameter count similar.
  • Researchers view the FFN as a key-value memory. Each hidden unit matches a pattern and writes a vector back to the stream. Many facts appear to be stored in FFN weights.
  • Residual connections give gradients a direct path through all 32 layers. Without them, a deep stack trains badly or not at all.
  • Failure example: a post-LN model with 48 layers and no learning rate warmup diverges in the first 1,000 steps. The loss jumps to NaN. Pre-LN with warmup trains stably.

How it works

  • LayerNorm subtracts the mean over the feature dimension, divides by the standard deviation, then scales and shifts with learned vectors of size d. RMSNorm skips the mean and shift. It divides by the root mean square and keeps only a scale. It is cheaper and works as well.
  • Normalization is per token, not per batch. So it works the same for batch size 1 at inference.
  • Pre-LN puts the norm before each sub-layer, inside the residual branch. The residual path stays clean. Post-LN puts the norm after the add. The original Transformer used post-LN, which needs careful warmup at depth.
  • Attention reads from other tokens and writes a vector. The FFN reads only its own token and writes a vector. Both writes add to the residual stream.
  • Dropout, if used, sits on branch outputs before the add. Large pretraining runs usually use none.
  • Activation memory per layer includes the normalized input, Q, K, V, the attention output, and FFN hidden states. Gradient checkpointing stores only block inputs and recomputes the rest.

When it matters

  • You should draw a block from memory and give parameter counts. This is a standard question.
  • It explains why quantization is hard: outlier channels in the residual stream.
  • It links to MoE, which replaces only the FFN.

Watch out

  • Missing the final norm before the output head hurts quality badly.
  • Post-LN at depth without warmup is unstable. Prefer pre-LN for new models.
  • FP16 can overflow in the residual stream when a few channels have very large activations. BF16 has a wider range.
  • Do not confuse LayerNorm with BatchNorm. BatchNorm depends on batch statistics and breaks for small or variable batches.
  • Counting parameters: do not forget the gated third matrix in SwiGLU.

26. Encoder vs decoder vs encoder–decoder

In short Encoder models read the full text in both directions to understand it. Decoder models generate text left to right. Encoder-decoder models read an input with an encoder and write a new output with a decoder. The choice depends on the task: understanding, generation, or sequence-to-sequence transformation.

Picture it

  • Sorting 10,000 support tickets into 12 categories is an understanding task. A small encoder like BERT-base (110M parameters) does it in a few milliseconds per ticket. A 70B decoder would work but cost far more.
  • Writing a reply to the ticket is generation. A decoder-only model such as Llama reads the prompt and writes the reply token by token.
  • Translating the ticket from German to English is sequence-to-sequence. T5 or Marian reads the German text with an encoder and writes English with a decoder.
  • BERT is trained with masked language modeling. It hides about 15 percent of tokens and predicts them using context on both sides. Every token sees every other token. Maximum length is 512 tokens.
  • A decoder-only model uses a causal mask. Token t sees only tokens up to t. It trains on next-token prediction. Every position gives a training signal.
  • In an encoder-decoder, the decoder has two attention parts. Self-attention is causal over its own outputs. Cross-attention takes queries from the decoder and keys and values from the encoder output.
  • Why decoder-only dominates now: one simple objective, easy scaling, in-context learning, and one KV cache. A prompt can describe almost any task.
  • Failure example: an embedding pipeline pools the [CLS] vector from a model trained for mean pooling. Retrieval quality falls sharply with no error.

How it works

  • Encoder-only: no causal mask. Output is one vector per token. For classification, use the [CLS] vector or a pooled average. For embeddings, use the pooling method the model was trained with.
  • Decoder-only: causal mask. Output at each position is a next-token distribution. The KV cache makes generation fast.
  • Encoder-decoder: the encoder runs once on the input. Its output stays fixed. Each decoder step uses it as K and V in cross-attention. The cache holds decoder self-attention K and V, plus the fixed encoder K and V per layer.
  • Cross-attention cost per step is proportional to the input length. A 4,000-token document adds 4,000 key comparisons for each output token.
  • Prefix-LM is a hybrid. The prompt part attends bidirectionally. The generated part is causal.
  • Fine-tuning data differs: encoders use labeled pairs. Decoders use text with a loss mask. Seq2seq uses input-output pairs.

When it matters

  • Interviewers ask which architecture fits which task and why. Use cost and latency in the answer.
  • Retrieval and reranking use encoders. Chat uses decoders. Knowing this shows system design skill.
  • It sets up the causal mask topic.

Watch out

  • Encoders cannot generate fluent text. Do not pick BERT for open-ended generation.
  • BERT-style models truncate at 512 tokens. A long document needs chunking.
  • Do not use a large decoder for simple classification if an encoder is accurate enough. It wastes money.
  • A pooling mismatch silently degrades embeddings.
  • Cross-attention models need to hold both encoder output and decoder cache in memory.

27. Causal masking

In short A causal mask stops each token from attending to later tokens. It adds minus infinity to those attention scores before softmax. The weight on future tokens becomes exactly zero. This lets the model train on a whole sentence in parallel while still learning left-to-right prediction.

Picture it

  • Think of an exam where each answer page is glued shut until you finish the question before it. You cannot peek at what comes next. The causal mask is the glue.
  • Training example: the sentence has 5 tokens. The mask is a 5 x 5 lower triangle. Row 3 can see positions 1, 2, and 3. In total 15 of 25 cells are visible. For n tokens, n(n+1)/2 cells are visible.
  • Without the mask, the model that predicts token 4 can see token 4 itself in its input. It copies the answer. Training loss drops near zero, but generation produces garbage, because future tokens do not exist at inference.
  • With the mask, one forward pass on a 2,048-token sequence gives 2,048 next-token predictions at once. This is the key training speedup over step-by-step RNN training.
  • At inference, the mask is implicit. The KV cache holds only past tokens. A new token attends to all of them. No future tokens exist, so nothing needs masking for the single new row.
  • During prefill the full prompt runs in parallel, so the causal mask is applied there. For a 1,000-token prompt, the mask hides 499,500 upper-triangle cells.
  • Failure example: batch generation with right padding. The model appends new tokens after pad tokens, and positions are wrong. Left padding with a correct attention mask fixes it.

How it works

  • The mask is an n x n matrix. Cells above the diagonal hold a very negative number (minus infinity or the dtype minimum). Cells on and below the diagonal hold 0.
  • It is added to the score matrix $QK^T/\sqrt{d_k}$ before softmax. Since $e^{-\infty}=0$, masked cells get zero weight. The row sum is taken only over allowed cells.
  • A padding mask is combined with the causal mask. A cell is allowed only if both permit it. Padding keys are blocked for all queries.
  • Labels are the input shifted by one position. The mask and the label shift do two different jobs. The mask hides inputs. The shift sets the target.
  • FlashAttention takes a causal flag and skips fully masked tiles. This saves about half the compute for long sequences.
  • Sliding window attention (Mistral) adds a second limit. Each token sees only the last W tokens, for example 4,096. Memory per layer then stays bounded.

When it matters

  • Interviewers use it to test if you understand training versus inference for decoders.
  • It explains why generation is sequential but training is parallel.
  • Off-by-one mask bugs are common in real code, so knowing the symptoms is useful.

Watch out

  • Off-by-one leak: allowing the diagonal plus one makes training loss fall to near zero and generation fail. Suspiciously low loss is a red flag.
  • A row that is fully masked gives NaN after softmax, because all weights are zero. This happens with all-padding rows. Use a large negative finite value or handle the row.
  • In FP16, minus infinity plus other values can produce NaN. Use the dtype minimum.
  • Left versus right padding matters for batched generation. Check the tokenizer padding side.
  • Do not mix up the attention mask for padding with the causal mask. They are different.

28. Scaling laws (why bigger helps)

In short Scaling laws say that language model loss falls as a smooth power law in parameters, data, and compute. This makes the results of large training runs predictable from small ones. The key lesson from Chinchilla is that model size and data must grow together.

Picture it

  • Plot loss against training compute on log-log axes. The curve is close to a straight line. Teams train many small models, fit the line, and predict the loss of a model 100 times larger before they spend the money.
  • Kaplan et al. (2020) reported $L \propto N^{-0.076}$ for parameters and $L \propto D^{-0.095}$ for data. Doubling the parameters lowers loss by only a few percent, but the gain is steady.
  • Training compute is about $C \approx 6ND$ FLOPs, where N is parameters and D is training tokens. A 7B model on 1T tokens costs 6 x 7e9 x 1e12 = 4.2e22 FLOPs.
  • Chinchilla (2022) found that earlier models were undertrained. A 70B model on 1.4T tokens beat Gopher at 280B on 300B tokens, with the same compute. The compute-optimal ratio is about 20 tokens per parameter.
  • Llama 3 8B trained on about 15T tokens. That is almost 1,900 tokens per parameter. It is far past compute-optimal, but deliberate. A small model trained long is cheap to serve for years.
  • Real decision: a team has a fixed budget. A 70B model costs about 10 times more to serve than a 7B model for every request. If inference volume is high, training a smaller model on more data costs less in total.
  • Failure example: a team extrapolates a loss curve to predict a coding benchmark score. Loss is smooth, but benchmark accuracy can jump or stall. Loss and task skill are not the same.

How it works

  • The fit: run many training runs with different N and D. Record the final validation loss. Fit a function like $L = E + A/N^{\alpha} + B/D^{\beta}$. E is the irreducible loss from the data's own noise.
  • The fit needs a held-out set from the same distribution. Loss on a different set follows a different curve.
  • Hyperparameters matter. Learning rate and batch size must be tuned for each scale. A fixed learning rate can bend the curve and hide the true trend.
  • Data quality changes the constants. Filtered and deduplicated data gives lower loss at the same token count.
  • Repeating data has limits. A few epochs behave almost like new data. Many epochs give diminishing returns and risk memorization.
  • Public text on the web is finite. The 'data wall' pushes work toward synthetic data and better filtering.

When it matters

  • It justifies why labs invest in bigger runs and how they plan budgets.
  • It frames the choice between a big model and a small, long-trained model, which depends on inference volume.
  • Interviewers test whether you know Chinchilla's 20 tokens per parameter rule and its limits.

Watch out

  • Do not extrapolate far beyond the fitted range. Trends can bend.
  • Loss improvement is not task improvement. Evaluate on the task you care about.
  • Compute-optimal for training is not cost-optimal over the product life. Inference cost changes the answer.
  • Apparent emergent abilities can result from a harsh metric such as exact match. Smooth metrics often show smooth gains.
  • Poor data or a bad learning rate can make a large model worse than a small, clean run.

29. Mixture of Experts (MoE)

In short Mixture of Experts (MoE) replaces one FFN with many expert FFNs and a router. The router sends each token to only a few experts. The model gains capacity without a matching rise in compute per token. Total parameters are large, but active parameters per token are small.

Picture it

  • Think of a hospital. A triage nurse (the router) sends each patient to two of eight specialists. The hospital has many experts, but each patient uses only two. Capacity is large and the cost per patient stays low.
  • Mixtral 8x7B: each layer has 8 experts and picks the top 2 per token. Total parameters are 46.7B. Active parameters per token are about 12.9B. It runs at the cost of a 13B model but performs close to much larger dense models.
  • DeepSeek-V3 is far bigger: 671B total, 37B active. It uses 256 routed experts plus 1 shared expert per MoE layer and picks 8 routed experts per token.
  • Memory is the catch. All experts must sit in GPU memory, because any token may need any expert. Mixtral in FP16 needs about 93 GB for weights alone. That is two 80 GB GPUs.
  • The router is a small linear layer. For d=4096 and 8 experts it has 4096 x 8 = 32,768 weights. It scores each expert, takes the top 2, and renormalizes those two scores into gate weights.
  • Output for a token is the gate-weighted sum of its chosen experts' outputs. The other 6 experts do no work for that token.
  • Failure example: expert collapse. Early in training the router sends most tokens to one or two experts. These improve faster and get even more tokens. Other experts stay untrained and the model acts smaller than it is.
  • At batch size 1, a decode step touches only 2 experts per layer and reads little memory. At batch size 64 almost all experts are hit, so the whole weight set is read. The bandwidth advantage fades under large batches.

How it works

  • Stored per MoE layer: attention weights (shared by all tokens), router weights, and E independent FFN weight sets. Attention is usually dense.
  • Router step: logits = x times W_router. Select top-k. Apply softmax over the selected logits to get gates. Dispatch the token's hidden vector to those experts.
  • Load-balancing auxiliary loss: it penalizes uneven token share across experts. It pushes the router to spread tokens. DeepSeek-V3 instead adds a bias per expert and adjusts it during training, with no auxiliary loss.
  • Capacity factor: each expert accepts at most a fixed number of tokens per batch. Extra tokens are dropped or passed through the residual path. This keeps tensor shapes static.
  • Expert parallelism places different experts on different GPUs. Tokens move across GPUs in an all-to-all step before and after the expert computation. Network bandwidth becomes a bottleneck.
  • Shared experts process every token and hold common knowledge. Routed experts specialize.

When it matters

  • Many top open and closed models use MoE, so you will be asked about it.
  • It shows the difference between total and active parameters, and between compute cost and memory cost.
  • It leads into serving questions on expert parallelism and batching.

Watch out

  • MoE saves FLOPs, not memory. Do not say it makes the model fit on a smaller GPU.
  • Load imbalance causes straggler GPUs. The slowest expert sets the step time.
  • Fine-tuning MoE can be unstable. Routers may collapse on a small dataset.
  • All-to-all communication can dominate latency on slow interconnects.
  • Experts are not clean topic specialists. Studies often find them tied to syntax or token type more than subject.

30. Prompting vs fine-tuning vs RAG

In short Start with prompting. Add RAG when the model needs fresh or private knowledge. Fine-tune when you need a consistent style, format, or behavior. Each method fixes a different problem, and they combine well.

Picture it

  • A support bot must answer from policies that change every week. This is a knowledge problem. RAG fits, because you update the document index and not the model.
  • A pipeline needs strict JSON output with 14 fields on every call. This is a behavior problem. Prompting with schema and examples may reach 90 percent validity. Fine-tuning on 5,000 examples can reach above 99 percent.
  • A prototype needs a result by Friday. Prompting needs zero training and has instant iteration. You change the text and run again.
  • Few-shot cost: 5 examples of 200 tokens add 1,000 tokens to every call. At 1M calls per day that is 1B extra input tokens per day. Fine-tuning moves those examples into the weights and removes this cost.
  • RAG cost: retrieval adds 50 to 200 ms and adds 2 to 5 chunks of about 500 tokens to each prompt. Indexing is a one-time and incremental cost.
  • Fine-tuning cost: a LoRA run on 5,000 examples takes roughly an hour on one GPU. The real cost is data curation, evaluation, and keeping the model current.
  • Fine-tuning is poor at adding many new facts. The model may learn the style of the facts but still hallucinate details. RAG gives sources that you can show and verify.
  • Failure example: a team fine-tunes on last quarter's price list. Prices change. The model keeps confident old prices. A retrieval lookup would have been correct.

How it works

  • Prompting changes only the input tokens. No weights change. The model uses in-context learning from the instructions and examples within the context window.
  • RAG changes the input too, with retrieved text. Knowledge lives in an external index. Access control, freshness, and citations are possible.
  • Fine-tuning changes weights, usually through LoRA. Behavior lives inside the model. It cannot be edited per user or per day.
  • Decision order: write a baseline prompt and an evaluation set. If failures are about missing facts, add RAG. If failures are about format or tone after good prompting, fine-tune. Re-evaluate after each step.
  • Combined setup: a fine-tuned model that follows citation format and refuses when evidence is missing, plus RAG for the facts.
  • Always keep an evaluation set of 50 to 200 real cases. Without it you cannot tell if a change helped.

When it matters

  • This is the most common applied-LLM design question. Give a decision framework, not a favorite.
  • It shows cost thinking: tokens per call, latency, training effort, and maintenance.
  • It tests knowledge of what fine-tuning can and cannot do.

Watch out

  • Do not fine-tune to inject facts that change. Use RAG.
  • RAG does not fix tone or output format reliably. Prompting or fine-tuning does.
  • Fine-tuning can cause forgetting of general skills. Test on a general benchmark too.
  • Long prompts raise cost and can hide key instructions. Test shorter versions.
  • Skipping the baseline: teams often fine-tune before they try a good prompt.

31. Embeddings + vector DB + similarity search

In short An embedding model turns text into a vector so that similar meaning gives nearby vectors. A vector database stores these vectors and finds the closest ones to a query vector. Approximate nearest neighbor (ANN) indexes make this fast at millions of vectors.

Picture it

  • A user types 'laptop won't turn on'. A keyword search misses a page titled 'Device fails to power up'. An embedding search finds it because the two phrases map to nearby vectors.
  • Typical sizes: MiniLM gives 384 dimensions. BGE-base gives 768. OpenAI text-embedding-3-small gives 1,536. Storage is vectors x dimensions x 4 bytes in FP32.
  • One million chunks at 768 dimensions in FP32 takes 3 GB. At 1,536 dimensions it takes 6 GB. At 100M chunks the 768-dimension index takes 300 GB, so compression matters.
  • Cosine similarity compares direction: $\cos = a \cdot b / (|a||b|)$. If vectors are normalized to length 1, cosine equals the dot product. Most systems normalize at index time.
  • Exact search compares the query with every vector. For 1M vectors of 768 dimensions that is 768M multiply-adds per query. This is tens of milliseconds on a CPU, but too slow at 100M vectors.
  • HNSW builds a layered graph. A query enters at the top layer, hops to closer neighbors, and descends. It often reaches 95 to 99 percent recall with a few milliseconds of latency.
  • IVF clusters vectors into nlist groups. A query checks only the nprobe closest clusters. PQ (product quantization) splits a vector into parts and stores codes. A 768-dimension FP32 vector (3,072 bytes) can shrink to 96 bytes, which is 32 times smaller.
  • Failure example: a team upgrades the embedding model for new documents but keeps the old index for old documents. Vectors from two models live in different spaces. Search results turn random.

How it works

  • Stored per item: the vector, an ID, the original text or a pointer to it, and metadata such as source, date, and access level.
  • At query time: embed the query with the same model. Optionally apply a metadata filter. Search the index for the top-k neighbors. Return IDs, scores, and text.
  • HNSW parameters: M is the number of links per node, often 16. efConstruction controls build quality. efSearch controls query-time breadth. A higher efSearch gives higher recall and higher latency.
  • IVF parameters: nlist, often near the square root of N. nprobe sets how many clusters to scan. Higher nprobe gives better recall and slower queries.
  • Some embedding models need prefixes, such as 'query:' and 'passage:' for E5. The model was trained with them. Without them quality drops.
  • Hybrid search combines BM25 keyword scores with vector scores. Reciprocal rank fusion merges the two ranked lists. It helps with IDs, names, and rare terms.

When it matters

  • Vector search is the retrieval core of RAG. Interviewers expect you to discuss index types and trade-offs.
  • Memory and recall-latency trade-offs decide cost at scale.
  • Model choice and versioning affect long-term maintenance.

Watch out

  • Never mix embedding models in one index, and never change the model without re-embedding everything.
  • Metric mismatch: if the model was trained for cosine, normalize vectors or use cosine distance.
  • Embeddings handle exact strings, part numbers, and numbers poorly. Add keyword search.
  • Strict metadata filters can cut ANN recall because the graph search skips filtered nodes. Test filtered recall.
  • Check recall on your own queries with exact search as ground truth. Do not trust default settings.

32. Chunking strategies

In short Chunking splits documents into pieces that a retriever can find. Chunk size and boundaries set the balance between complete context and precise retrieval. Good chunks hold one coherent idea and carry enough context to stand alone.

Picture it

  • Imagine a 100-page equipment manual cut into pieces. If you cut every page in half at random, a safety warning may land in one piece and its procedure in another. The model sees only half the story.
  • Numbers: a 60,000-word manual is about 80,000 tokens. With 400-token chunks and 50 tokens overlap, you get about 230 chunks. With 100-token chunks you get about 800 chunks. With 2,000-token chunks you get about 40.
  • Large chunks mix many topics in one vector. The embedding becomes an average that matches no query well. They also waste prompt space on irrelevant text.
  • Small chunks give precise matches but lose context. A 60-token chunk that says 'It must be replaced every 6 months' no longer says what 'it' is.
  • Fixed-size chunking cuts at a token count. It is simple but ignores structure. Recursive chunking tries paragraph breaks first, then sentences, then words. Structure-aware chunking uses headings, tables, and code blocks.
  • Parent-child chunking indexes small chunks for precise search, then returns the larger parent section to the model. This improves both precision and context.
  • Contextual chunking prepends a short header to each chunk, such as the document title and section path. 'Pump P-200 > Maintenance > Seals' makes the chunk clear on its own.
  • Failure example: the embedding model has a 512-token limit. A 900-token chunk is silently truncated for embedding. The index never saw the second half, so questions about it fail.

How it works

  • Stored per chunk: text, embedding, document ID, position, section path, page number, and timestamps. Metadata lets you filter, cite, and rebuild the neighbors.
  • Overlap of 10 to 20 percent repeats the end of one chunk at the start of the next. It protects ideas that cross a boundary. It also adds duplicates and index size.
  • Semantic chunking embeds sentences and cuts where similarity between neighbors drops. It costs extra embedding calls and gives uneven sizes. Gains over recursive chunking are often small.
  • Tables should stay whole or be converted row by row with the header repeated. A row without its column names has no meaning.
  • Tokens should be counted with the embedding model's tokenizer, not by characters or words.
  • Chunk size is tuned by experiment. Build 3 or 4 variants, run your real questions, and compare recall@k.

When it matters

  • Chunking often has more effect on RAG quality than the choice of vector database.
  • It is cheap to change and easy to test, so good engineers tune it first.
  • It ties to parsing, embedding limits, and prompt budget.

Watch out

  • Splitting tables, lists, or code in the middle destroys meaning.
  • Pronouns and references to 'above' or 'Section 4' lose their target when chunks are alone.
  • Silent truncation by the embedding model hides text from search.
  • Overlap duplicates can fill the top-k with near-identical chunks. Deduplicate or use MMR (maximal marginal relevance).
  • Do not use one size for all document types. FAQs, contracts, and code need different strategies.

33. RAG pipeline end-to-end

In short RAG (retrieval-augmented generation) finds relevant document chunks for a question and adds them to the prompt. The LLM then answers using that evidence. It has an offline indexing path and an online query path.

Picture it

  • An HR assistant answers 'How many days of parental leave do I get?'. It searches the policy handbook, finds the leave section, and answers with a citation. The base model was never trained on this company's handbook.
  • Offline path: load files, parse and run OCR, clean, chunk, embed, and store vectors with metadata. This runs when documents change.
  • Online path: rewrite the query, embed it, retrieve candidates, rerank, build the prompt, generate, and check the answer.
  • Typical flow with numbers: retrieve the top 50 by hybrid search. A cross-encoder reranker scores each query-chunk pair and keeps the best 5. Five chunks of 400 tokens add 2,000 tokens to the prompt.
  • Latency budget example: query embedding 20 ms, vector search 30 ms, reranking 50 pairs about 150 to 300 ms, LLM first token about 400 ms. The user sees output after roughly one second.
  • Why rerank: the first-stage embedding compares two separate vectors. A cross-encoder reads query and chunk together, so it judges relevance better. It is too slow to run on millions of chunks, so it runs on the shortlist.
  • The prompt tells the model to answer only from the context, to cite chunk IDs, and to say 'not found' if the context lacks the answer.
  • Failure example: the gold chunk ranks 7th. The system passes only the top 5. The answer is wrong even though search 'found' it.

How it works

  • Index record: chunk text, vector, document ID, page, section, ACL (who may read it), and update time.
  • Query rewrite: an LLM turns 'and what about for contractors?' into a standalone question using chat history. Otherwise retrieval sees an unclear fragment.
  • Retrieval: dense vector search plus BM25. Merge with reciprocal rank fusion. Apply metadata and permission filters before returning results.
  • Prompt assembly: system rules, retrieved chunks with IDs and source names, the question, and output format. The total must fit the context limit with room for the answer.
  • Generation then validation: check that each cited ID exists and that quoted text appears in the chunk.
  • Evaluation splits by stage. Retrieval: recall@k and MRR against labeled gold chunks. Generation: faithfulness (is each claim supported) and answer relevance.

When it matters

  • RAG is the most common production LLM pattern. Expect a design question on it.
  • Stage-level metrics let you find which part to fix. End-to-end accuracy alone does not.
  • Permissions and freshness are real-world requirements that candidates often forget.

Watch out

  • Permission leaks: if the ACL filter is missing, the bot may quote a document the user must not see.
  • Stale index: documents change but the index does not. Set up incremental updates and deletion.
  • No abstention path: without a 'not found' rule, the model invents an answer when retrieval fails.
  • Prompt injection: retrieved text can contain instructions. Treat it as data, not commands.
  • Models often use the start and end of the context best. Important evidence in the middle can be missed.

34. Graph RAG (when to use it)

In short Graph RAG builds a knowledge graph of entities and relations from documents. It retrieves by following links in that graph. This helps with multi-hop and whole-corpus questions that plain chunk search misses. It costs much more to build, so use it only when relations matter.

Picture it

  • Question: 'Which suppliers of the pump hit by the recall also supply the valve in Plant B?' No single chunk holds the answer. It needs a chain: recall to pump, pump to supplier, supplier to valve, valve to plant. Vector search returns pieces. A graph follows the chain.
  • Build step: an LLM reads each chunk and extracts triples such as (Supplier Acme, supplies, Pump P-200). Entities become nodes. Relations become edges.
  • Microsoft's GraphRAG also runs community detection (Leiden algorithm) to group tightly linked nodes. An LLM writes a summary for each community, at several levels.
  • Local search: find the entities in the question, take their neighbors and linked chunks, and answer from that small subgraph. Good for specific questions.
  • Global search: collect community summaries and combine them. Good for 'What are the main themes across all reports?', which no single chunk answers.
  • Cost example: a 1M-token corpus split into 600-token chunks gives about 1,700 extraction calls, often with extra passes to catch missed entities. Plain RAG needs only cheap embedding calls. Graph indexing can cost 10 to 100 times more.
  • Failure example: the extraction treats 'IBM' and 'International Business Machines' as two nodes. The path through the graph breaks, and the multi-hop answer is incomplete.
  • For a simple FAQ where answers sit in one paragraph, graph RAG adds cost and delay with no gain.

How it works

  • Stored: nodes (entity name, type, description), edges (relation, source chunk IDs), chunk text and embeddings, and community summaries with their embeddings.
  • Entity resolution merges duplicates by name similarity, embedding similarity, or an LLM check. It is the most important quality step.
  • Traversal: start from seed nodes found by embedding match, expand 1 to 3 hops, rank by edge strength or relevance, and collect supporting chunks as evidence.
  • The generator gets the triples, the linked text chunks, and sometimes community summaries. Citations point back to chunk IDs.
  • Updates: new documents require new extraction, entity merging, and possibly recomputed communities. Incremental updates are harder than adding vectors.
  • Graph stores can be a property graph database such as Neo4j or a simple edge table. Most corpora of moderate size work with the latter.

When it matters

  • It tests whether you pick tools by problem type, not by hype.
  • It shows the link between multi-hop reasoning needs and retrieval structure.
  • Cost and maintenance trade-offs are a key part of a good answer.

Watch out

  • LLM extraction can invent edges. A wrong edge looks like a trusted fact. Keep the source chunk for each edge and verify.
  • Duplicate entities fragment the graph and break paths.
  • Index cost and refresh effort can exceed the value for single-hop questions.
  • Graph size can explode. Prune weak edges and limit hop depth to avoid noisy context.
  • Evaluation is hard. Build a set of real multi-hop and global questions and compare against plain RAG.

35. RAG failure modes (and fixes)

In short RAG can fail at parsing, chunking, retrieval, ranking, or generation. Diagnose each stage on its own, then fix the weakest. Errors multiply, so a small loss at each stage becomes a large total loss.

Picture it

  • A user asks 'What is the refund window?'. The index holds the 2022 policy (30 days) and the 2024 policy (14 days). The retriever returns the old one. The model answers '30 days' with a citation. The answer is fluent, cited, and wrong.
  • Stage yields multiply. Parsing 95 percent, chunking 95 percent, retrieval 85 percent, generation 90 percent gives 0.95 x 0.95 x 0.85 x 0.90 = about 69 percent end to end. Four good stages still give a mediocre system.
  • Parsing failure: a scanned PDF returns empty text, or a table is flattened into a stream of numbers. No later stage can recover data that never entered the index.
  • Chunking failure: the answer is split across two chunks, so neither one matches the query well.
  • Retrieval failure: the user says 'car', the document says 'vehicle', and an exact-term search misses it. Or the query contains a part number, and dense embeddings blur it.
  • Ranking failure: the right chunk is in the top 50 but not in the top 5 that fit in the prompt.
  • Generation failure: the right chunk is in the prompt, but the model ignores it, mixes it with its memory, or misreads a table.
  • First diagnostic: check recall@20 on labeled questions. If the gold chunk is not in the top 20, changing the prompt cannot help. If it is there but the answer is wrong, focus on ranking and generation.

How it works

  • Parsing fixes: layout-aware parsers, OCR for scans, table extraction to markdown or row text, and keeping headings and page numbers as metadata.
  • Chunking fixes: structure-aware splits, parent-child retrieval, and contextual headers on each chunk.
  • Retrieval fixes: hybrid BM25 plus dense search, query rewriting, multi-query expansion, HyDE (embed a hypothetical answer), domain fine-tuned embeddings, and metadata filters such as date and product.
  • Ranking fixes: a cross-encoder reranker, a larger candidate pool (top 50 to 100) with a smaller final set, and MMR to remove near-duplicates.
  • Generation fixes: strict prompts to answer only from context, quote and cite, order chunks with the best at the edges, and add an abstain rule with a score threshold.
  • Logging per request: query, rewritten query, retrieved IDs and scores, final prompt, answer, and citations. Without logs you cannot debug.

When it matters

  • Interviewers want to see a structured debugging process, not guesses.
  • Stage-level evaluation turns vague complaints into specific fixes.
  • Most real RAG projects spend more time on parsing and retrieval than on the LLM.

Watch out

  • Do not tune the prompt when retrieval recall is low. Measure first.
  • Outdated and conflicting documents give confident wrong answers. Add dates, versions, and deprecation handling.
  • A reranker adds latency. Budget for it and cache where you can.
  • Citations prove the chunk was retrieved, not that the claim is supported. Check faithfulness.
  • Evaluation sets drift. Refresh them with real user queries.

36. Agent harness loop (no framework)

In short An agent harness is the outer program around the LLM. It loops: the model picks an action, the harness runs the tool, adds the result to the history, and asks the model again. The loop stops on a final answer or on a limit for steps, tokens, or time.

Picture it

  • A travel assistant gets 'Book me a flight to Pune next Friday under 8,000 rupees'. It searches flights, checks your calendar, asks for confirmation, and books. Each step is one loop turn. The model decides. The harness acts.
  • The LLM is only a function from messages to the next message. It cannot run code, call APIs, or remember anything on its own. The harness provides tools, memory, safety, and control.
  • Loop steps: build the messages and tool schemas, call the model, check for a tool call, validate arguments against the JSON schema, run the tool with a timeout, append the tool result, and repeat.
  • Stop conditions: the model returns a plain answer, step count reaches a cap such as 10, the token budget runs out, the time limit passes, or a human rejects an action.
  • Cost grows fast. Each step resends the whole history. If each step adds 1,000 tokens, step k sends about k x 1,000 input tokens. Ten steps send about 55,000 input tokens in total, not 10,000.
  • Failure example: a tool returns a 200,000-token web page. It fills the context window and the next call fails. Harness rule: truncate tool output to about 2,000 tokens and add a note that it was cut.
  • Failure example: the agent calls the same failing search 20 times with the same arguments. Harness rule: detect repeated identical calls and stop or change course.
  • Failure example: a booking tool times out and the harness retries. The airline booked twice. Side-effect tools need idempotency keys.

How it works

  • State: a list of messages (system, user, assistant, tool), the tool registry with JSON schemas, a step counter, a token counter, and optional scratch notes or a plan.
  • Each tool has a name, a clear description, an input schema, and a handler. The model sees name, description, and schema. Clear descriptions improve tool choice.
  • Parsing: the model emits a structured tool call. The harness validates it. On invalid arguments it sends an error message back to the model so it can fix the call. It does not crash.
  • Execution: run the handler with a timeout and catch exceptions. Return errors as readable tool results. Run independent tool calls in parallel when the model requests several.
  • Context control: summarize or drop old tool results when the history gets long. Keep the system prompt and the recent turns intact.
  • Safety: allow-list tools, gate destructive actions behind human approval, run code in a sandbox, and treat tool output as untrusted text.

When it matters

  • Agents are common in interviews. A clear loop with limits shows you can build reliable systems, not demos.
  • The harness, not the model, enforces cost, safety, and reliability.
  • It connects to tool design, RAG as a tool, and evaluation of multi-step behavior.

Watch out

  • Infinite or wasteful loops: always set a hard step limit and a token budget.
  • Prompt injection through tool output, such as a web page that says 'ignore your instructions'. Never give the model more power than the user has.
  • Retries on tools with side effects can repeat actions. Use idempotency keys and confirmation steps.
  • Errors compound across steps. A 95 percent per-step success rate over 10 steps gives about 60 percent overall. Keep tasks short and verify results.
  • Evaluate the trajectory, not only the final answer. Log every step.

37. Tool / function calling

In short Tool calling lets a language model ask your code to do something. The model writes a structured request with a tool name and JSON arguments. Your code runs the tool and sends the result back. The model never runs the tool itself. It only predicts text in a fixed format. This keeps your systems under your control.

Picture it

  • Think of a clerk with a phone. The clerk (model) cannot open the warehouse. The clerk calls the warehouse (your code) and reads the answer to the customer.
  • Example: a support bot gets the message 'Where is order 42?'. The model has no order data. It needs a tool.
  • Step 1: you send the model the user message plus a list of tool definitions. Each definition has a name, a description, and a JSON Schema for the arguments.
  • Step 2: the model replies with a tool call instead of normal text. Example: name = get_order, arguments = {id: 42}. The API marks the reply with a stop reason such as tool_calls.
  • Step 3: your code checks the arguments against the schema. It then calls the real order API.
  • Step 4: you append the result as a message with role 'tool'. You also copy the call id so the model can match result to request.
  • Step 5: you call the model again. It reads the result and writes the final answer: 'Order 42 ships on Friday.'
  • This loop can repeat. The model may call several tools before it answers. A harness loop (topic 41) adds step limits to stop endless cycles.

How it works

  • The API turns your tool list into text and puts it in the prompt, often in a special format. The tool names and descriptions use tokens. Ten tools with long schemas can cost thousands of tokens on every call.
  • The model was fine-tuned on many examples of calls. During training it learned when to emit the call format. At run time the call is just next-token prediction, with no special logic.
  • Constrained decoding makes the JSON always valid. The decoder keeps a grammar state. At each step it sets the logit of every token that breaks the grammar to minus infinity. Only valid tokens can be picked.
  • Constrained decoding fixes syntax only. It cannot fix meaning. The model can still output a valid but wrong value, such as id 24 instead of 42.
  • Parallel tool calls: the model can return several calls in one reply. Your code can run them at the same time and return all results together. This cuts latency when the calls do not depend on each other.
  • Tool choice setting: 'auto' lets the model decide. 'required' forces a call. A named tool forces that exact tool. Use 'required' when a step must always fetch data.
  • Good description text is the main control. Write when to use the tool, what each argument means, and an example value. Models pick tools by reading these words.

When it matters

  • Tool calling connects the model to ERP, CRM, databases, and RPA bots. Without it the model can only talk. With it the model can act.
  • It gives fresh and exact data. A model cannot know today's stock level. A tool can return it.
  • Typed schemas make output machine-readable. Your code does not parse free text with regular expressions.
  • Interviewers ask about it because it is the base of every agent. Know the full loop and where validation belongs.

Watch out

  • Never trust arguments. Prompt injection in a document can make the model call delete_all_records. Validate every argument, use allow-lists, give the tool least privilege, and ask a human to approve destructive actions.
  • Too many tools confuse the model. Accuracy of tool choice drops as the list grows. Keep the list short, or select a subset per step.
  • Tool errors need clear messages. Return the error text to the model so it can fix the arguments. A blank error leads to blind retries.
  • Do not send huge tool results back. A 50,000-token JSON dump fills the context. Trim, paginate, or summarise first.
  • Side effects can run twice if you retry. Use idempotency keys for actions such as 'create payment'.

38. MCP (Model Context Protocol)

In short MCP (Model Context Protocol) is an open standard for connecting AI apps to tools and data. An MCP server wraps a system and exposes it in one common format. Any MCP client can then use it with no custom code. It does not make the model smarter. It only makes the connection standard.

Picture it

  • Think of a USB-C port. Before USB-C, each device needed its own cable. With one standard, any device works with any port.
  • The problem before MCP: N apps and M tools needed N × M custom integrations. Example: 4 AI apps and 10 systems means 40 connectors.
  • With MCP, each app implements one client and each system implements one server. The count becomes N + M, so 14 pieces of code.
  • Three roles. The host is the app the user sees, such as an IDE or chat app. The client lives inside the host and holds one connection. The server wraps a system such as files, Slack, or a database.
  • A server offers three kinds of things. Tools are actions the model can call. Resources are data the app can read, such as a file or a record. Prompts are reusable templates.
  • Example: a Postgres MCP server exposes a tool run_query and a resource for each table schema. A coding agent connects, lists them, and starts querying.
  • Discovery is live. The client asks the server what it can do at run time. You add a new tool on the server and clients see it with no app update.
  • Local servers run as a child process on your machine. Remote servers run over the network and use OAuth for login.

How it works

  • Messages use JSON-RPC 2.0. Each message is a request, a response, or a notification. A request has an id, a method, and params.
  • Startup handshake: the client sends 'initialize' with its protocol version and capabilities. The server replies with its own. Both sides then agree on which features to use.
  • Core methods: tools/list returns tool names and JSON Schemas. tools/call runs a tool. resources/list and resources/read give data. prompts/list and prompts/get give templates.
  • Transports: stdio for local servers. The host starts the server process and talks over standard input and output. Streamable HTTP for remote servers. It can stream partial results with server-sent events.
  • Servers can send notifications such as tools/list_changed. The client then fetches the list again. Clients can also offer features back, such as asking the host's model to generate text (sampling).
  • The host converts MCP tool definitions to the model's own tool-calling format. So MCP sits below tool calling (topic 37). The model still just emits a name and arguments.
  • Auth for remote servers uses OAuth. The server states what scopes it needs. The user approves them once.

When it matters

  • It cuts integration cost. Teams write one server per system and reuse it in many agents and IDEs.
  • It separates ownership. The team that owns the CRM owns the CRM server, including its access rules.
  • It keeps agents flexible. You can swap the model or the host app and keep all tools.
  • A strong interview answer names the three server features, the transport types, and the N × M to N + M idea.

Watch out

  • MCP is a protocol. It is not a model, a framework, or a security layer. Say this clearly.
  • A server is code that runs with your permissions. A malicious or hacked server can steal data. Install only trusted servers and give narrow scopes.
  • Tool descriptions come from the server and go into the prompt. A bad server can hide instructions in them (tool poisoning). Review descriptions and pin versions.
  • Each connected server adds tool schemas to the context. Twenty servers can use a large share of the token budget. Connect only what the task needs.
  • Stdio servers can crash or hang without notice. Add timeouts and restart logic in the host.

39. Memory (short-term vs long-term)

In short Short-term memory is everything in the model's context window right now. Long-term memory is data stored outside the model and fetched when needed. An agent needs both to work across long tasks. The model itself keeps nothing between calls. All memory is text that your code puts back into the prompt.

Picture it

  • Think of a desk and a filing cabinet. The desk is small, but you can see everything on it. The cabinet is big, but you must look things up.
  • Short-term memory is the desk. It holds the chat history, tool results, and a scratchpad. Its size is the context limit, for example 32k tokens.
  • Every token on the desk costs money and time on every call. A long history makes each step slower and more expensive.
  • Example: an agent processes a 200-page tender. It cannot keep all pages on the desk. It keeps notes and finds pages when needed.
  • Long-term memory is the cabinet. It lives in a database or a vector store. The agent writes a fact there, then reads it back days later.
  • Three kinds. Episodic memory stores what happened, such as 'last Tuesday the user rejected supplier A'. Semantic memory stores facts, such as 'user prefers EUR'. Procedural memory stores how to do things, such as a saved checklist.
  • Budget rule: system prompt + tool schemas + memory + retrieved documents + the answer must fit in the context window.
  • Example of a bad design: put the whole history into every call. By turn 80 the prompt is 40k tokens and the bot is slow, costly, and confused.

How it works

  • Sliding window: keep only the last N turns. It is simple. It loses early facts, such as the user's goal.
  • Summarisation: when the history passes a limit, ask the model to compress old turns into a short summary. Keep the summary and the newest turns. Facts can get lost or changed in each summary, so keep key facts in a separate field.
  • Tool output trimming: after the model uses a large result, replace it with a short note. A 20,000-token web page becomes 'Page read; price is 49 USD'.
  • Write path for long-term memory: after an event, extract facts with a model or rules. Embed each fact into a vector. Store the text, the vector, the user id, and a timestamp.
  • Read path: embed the current question. Search the store for the top-k similar items. Filter by user id. Rank by similarity, recency, and importance. Put the best few in the prompt.
  • Updates: a new fact can conflict with an old one, such as a new address. The store needs an update or delete rule, or the agent will quote stale data.
  • Thread state versus store: a workflow framework keeps state for one run (a checkpoint). It lets you resume after a crash. A separate store keeps facts shared across runs and users.

When it matters

  • Long workflows, such as a multi-day RFP, need state that survives restarts. Context alone cannot do this.
  • Good memory reduces cost. You send 2k relevant tokens, not 40k old tokens.
  • Memory gives personalisation. The agent remembers the user's format and rules.
  • It is a common interview topic. Be ready to explain what to keep, what to drop, and how to retrieve.

Watch out

  • Long context hurts accuracy. Models often miss facts placed in the middle of a long prompt ('lost in the middle'). More tokens do not always mean better recall.
  • Storing personal data without a policy creates legal risk. Set retention limits, support deletion on request, and keep data per user.
  • Memory poisoning: a bad document or user can write a false or hostile 'fact' that the agent trusts later. Check what you store.
  • Retrieval by similarity can return near-matches that are wrong. Always include the source and date, and filter by user.
  • Summaries drift. After many rounds, numbers and names can change. Keep exact values in structured fields, not only in prose.

40. Human-in-the-loop (VerifyMe idea)

In short Human-in-the-loop (HITL) sends uncertain or risky AI outputs to a person for review. Safe and confident outputs go straight through. Reviewer fixes become new training and test data. It lets a team ship AI in areas where mistakes cost real money.

Picture it

  • Think of a bank cheque desk. A machine reads most cheques. If a number looks unclear or the amount is large, a clerk checks it.
  • Example: an invoice extractor reads vendor, date, and total. Each field gets a confidence score between 0 and 1.
  • High confidence, such as 0.98 on a small invoice: auto-approve. This is called straight-through processing.
  • Low confidence, such as 0.62 on the total, or a payment above a set amount: send to a review queue. A person sees the image and the extracted fields side by side and corrects them.
  • Corrections are saved with the original input and the model's output. They become labelled data.
  • That data trains and tests the next model version. Over time the model improves, more items pass automatically, and the queue shrinks. This is the data flywheel.
  • Two numbers rule the design. Automation rate is the share of items that skip review. Error rate among auto-approved items must stay under a set target, such as 0.5%.
  • Example: at threshold 0.90, 70% pass automatically with 1% errors. At 0.97, 45% pass with 0.2% errors. The business picks the point.

How it works

  • Confidence sources: token log-probabilities of the extracted value, agreement across repeated runs, rule checks, and a separate judge model. Combine several signals.
  • A raw model self-report such as 'I am 95% sure' is poorly calibrated. Models say it when wrong. Prefer log-probabilities, validators, and measured accuracy.
  • Calibration means that a score of 0.9 is right about 90% of the time. Measure it on a held-out set with a reliability curve and expected calibration error (ECE). Fix it with temperature scaling or isotonic regression.
  • Choose the threshold on a validation set. Sweep thresholds. For each one, record automation rate and error rate among auto-approved items. Pick the point that meets the risk target.
  • Use separate thresholds per field and per risk. A typo in a note field is cheap. A wrong bank account number is not.
  • Hard rules override scores. Always review payments above a limit, new vendors, or legal text, whatever the confidence.
  • Queue design: show the model's guess and the source highlight. Prioritise by value and by deadline. Track review time and reviewer disagreement. Audit sample: also review a small random share of auto-approved items. This finds silent errors and drift.

When it matters

  • Enterprises will not accept unchecked AI on invoices, claims, or legal records. HITL is how AI is approved for production.
  • It turns accuracy into a business dial. You trade automation against risk with a clear number.
  • It creates labelled data from daily work, at low cost.
  • Interviewers like it because it shows product thinking, not only modelling.

Watch out

  • Automation bias: reviewers click 'accept' too fast when the model is usually right. Show uncertain fields first, and measure reviewer error with planted test items.
  • Selection bias in feedback: you only get corrections for items sent to review. The auto-approved set has no labels. The audit sample fixes this.
  • Confidence drifts when input changes, such as a new invoice layout. Monitor the score distribution and recheck calibration often.
  • A review queue that is too big defeats the purpose. Track cost per item and queue age.
  • Do not train on reviewer fixes without a quality check. Two reviewers can disagree, and bad labels harm the model.

41. OCR & document AI (TrOCR-level)

In short Document AI turns a scanned page into structured data. It finds where text is, reads the characters, works out the layout, and extracts fields such as total and date. OCR (optical character recognition) is the reading step. TrOCR is a transformer model that reads a text line image and writes the text. Newer vision-language models can read a whole page and output JSON.

Picture it

  • Think of a clerk who types paper invoices into a system. The clerk looks at the page, finds the total, reads it, and checks it against the line items. Document AI copies these steps.
  • Step 1, cleanup: deskew a tilted scan, remove noise, and fix contrast. Scan at about 300 DPI. Very low resolution makes characters merge.
  • Step 2, detection: find where lines, words, and tables are. The output is boxes. Models such as DBNet or CRAFT do this.
  • Step 3, recognition: read each box and output characters. TrOCR does this step.
  • Step 4, layout and reading order: decide which text is a header, a table cell, or a footnote. Two-column pages must be read column by column, not across.
  • Step 5, field extraction: pick the values for vendor, invoice date, and total. Models such as LayoutLM use the text, its position, and the image together.
  • Step 6, validation: check that the line items sum to the total and that the date is valid. Send low-confidence fields to review (topic 40).
  • Example error: the model reads 1,284.50 where the page says 1,234.50. A sum check against the line items catches it.
  • Digital PDFs are different. Many contain a text layer. Read it directly, which is faster and exact. Scans have no text layer and need OCR.

How it works

  • TrOCR has an encoder and a decoder. The encoder is a vision transformer. It cuts the line image into patches, such as 16 × 16 pixels, and turns each patch into a vector.
  • The decoder is a text transformer. It writes one token at a time. Each step uses cross-attention to look at the image patch vectors. It stops at an end token.
  • Decoding often uses beam search. It keeps the best few partial strings at each step, so it is less likely to lock in an early mistake.
  • TrOCR reads one line at a time. A separate detector must first cut the page into lines.
  • Classic engines: Tesseract. Deep learning toolkits: PaddleOCR and docTR. Each combines detection and recognition.
  • Layout models: LayoutLM adds the 2-D position of each word as an input. So the model knows that '1,234.50' sits at the bottom right, next to the word 'Total'.
  • End-to-end option: models such as Donut or Qwen-VL read the page image and output JSON directly. They skip the separate OCR step. They are simple to build, but can invent values and are slower per page.

When it matters

  • Invoices, claims, and KYC forms are core enterprise inputs. Poor OCR hurts every later step, such as search and extraction.
  • Good measurement lets you improve with data. Teams track error per field, not one global score.
  • The trade-off between a classic pipeline and a vision-language model is a common design question. Pipelines are cheap and traceable. Vision-language models are flexible on new layouts.
  • Confidence per field feeds the review queue. This links OCR to HITL.

Watch out

  • Do not assume a PDF has text. Many PDFs are scans. Check for a text layer first.
  • Table structure is easy to lose. Plain text order can mix cells from different columns. Use table-aware models and keep row and column ids.
  • Character error rate (CER) is edits divided by true characters: (substitutions + deletions + insertions) / characters. It hides business impact. One wrong digit in a total is a CER of under 1% but a failed invoice. Also track field-level accuracy.
  • Vision-language models can hallucinate. They may fill a blank field with a plausible value. Require the value to match text found on the page.
  • Handwriting, stamps, and fax noise cause big drops. Test on your real documents, not on clean benchmarks.

42. Perceptron → MLP

In short A perceptron is one artificial neuron. It multiplies each input by a weight, adds a bias, and applies an activation function. A multi-layer perceptron (MLP) stacks many such neurons in layers. A single neuron can only draw a straight boundary. Layers with non-linear activations can learn curved boundaries.

Picture it

  • Think of a judge with a scoring sheet. Each input is a criterion. The weight says how much that criterion matters. The bias is a starting score. The activation turns the total score into a decision.
  • Example: a loan model has inputs income, debt, and age. It computes z = w1·income + w2·debt + w3·age + b. If z is above 0, say 'approve'.
  • Geometry: the equation w·x + b = 0 is a line in 2-D, a plane in 3-D, and a hyperplane in more dimensions. One neuron splits space into two halves.
  • XOR shows the limit. XOR gives 1 when the two inputs differ. The four points cannot be split by one straight line. A single perceptron fails.
  • Fix: add a hidden layer. One hidden neuron can detect 'x1 AND NOT x2'. Another can detect 'x2 AND NOT x1'. The output neuron combines them with OR.
  • Another view: each layer bends and folds the space. After the fold, the next layer can separate the classes with a straight cut.
  • Layer form: h = f(Wx + b). W is a matrix with one row per neuron. A layer with 784 inputs and 256 neurons has 784 × 256 + 256 = 200,960 parameters.
  • Universal approximation theorem: one hidden layer that is wide enough can approximate any continuous function on a bounded range. The theorem does not say how to find the weights or how wide the layer must be.

How it works

  • Perceptron learning rule (1958): if the output is wrong, move the weights toward the input for a missed positive, or away for a false positive. It converges only if the data can be split by a line.
  • Modern MLPs train with gradient descent and backpropagation instead. Hidden units use smooth activations such as ReLU.
  • Without an activation, layers collapse. W2(W1x) equals (W2W1)x. Ten linear layers are the same as one. The activation is what gives depth its power.
  • ReLU hidden layers make a piecewise linear function. The network cuts input space into many flat regions. More neurons give more regions.
  • Depth versus width: deep nets reuse features and need fewer neurons for complex functions. Wide shallow nets need many more.
  • In PyTorch, a Linear layer is exactly Wx + b. It stores W with shape (out, in) and applies x times W transposed.

When it matters

  • Every deep model contains this building block. A transformer feed-forward block is a two-layer MLP applied to each token.
  • In large language models, these MLP blocks hold about two thirds of the parameters.
  • Interviewers use XOR and the collapse of stacked linear layers to test basic understanding.
  • On tabular business data, a small MLP is often a fair baseline, though tree models often win.

Watch out

  • Stacking linear layers with no activation gives one linear layer. State this clearly.
  • Do not say that the universal approximation theorem means MLPs always learn well. It says a good solution exists. It does not promise training will find it.
  • Input scale matters. Unscaled features, such as income in thousands and age in tens, make training slow. Standardise inputs.
  • Zero initial weights make all neurons in a layer identical, so they never differ. Use random initialisation.

43. Forward pass

In short The forward pass sends input through the layers, one after the other, to produce a prediction and then a loss. Each layer reads the output of the previous layer. The network also saves its intermediate values for the backward pass. On a GPU, you process a batch of examples at once as a matrix.

Picture it

  • Think of a factory line. Raw material enters. Each station changes it. The last station gives the product, and a checker scores it.
  • Example: a 3-layer MLP for digits. Input is a 28 × 28 image, flattened to 784 numbers. Hidden layer 1 has 256 units. Hidden layer 2 has 128 units. The output has 10 logits.
  • Layer 1: h1 = ReLU(W1x + b1). Layer 2: h2 = ReLU(W2h1 + b2). Output: logits = W3h2 + b3. Then loss = cross-entropy(logits, label).
  • Shape trace with batch B = 32: input (32, 784). After layer 1: (32, 256). After layer 2: (32, 128). Logits: (32, 10). Loss: one number.
  • Matrix rule: (B, in) times (in, out) gives (B, out). The inner sizes must match. A shape error means a layer size is wrong.
  • Why batches: a GPU has thousands of cores. One example uses a tiny part of them. A batch of 32 or more fills them and gives a more stable gradient.
  • Saved values: the network keeps x, h1, and h2 in memory. Backprop needs them to compute gradients.
  • At inference you only need the logits. You can skip saving values, which saves memory.

How it works

  • Each Linear layer costs about 2 × B × in × out floating-point operations (one multiply and one add per weight). For layer 1 above with B = 32 this is about 12.8 million.
  • Memory for activations grows with batch size and depth. For large models, activations often use more memory than the weights during training.
  • Autograd builds a computation graph during the forward pass. Each operation records its inputs and how to compute its derivative. This is why the pass is slower in training than in inference.
  • Inference mode stops graph building for gradients. It cuts memory and time.
  • Layers that act differently in train and eval mode: dropout and batch norm. Dropout is active only in train mode. Batch norm uses batch statistics in train and running averages in eval.
  • Mixed precision runs most matrix multiplies in 16-bit floats. It is about twice as fast and halves activation memory. The loss and sensitive sums stay in 32-bit.
  • For language models, the forward pass has two phases at inference. Prefill processes the whole prompt at once. Decode makes one token at a time and reuses a key-value cache.

When it matters

  • Tracing shapes through a forward pass is the top skill for fixing PyTorch bugs.
  • It lets you estimate cost. Floating-point operations and memory follow directly from shapes.
  • It explains the difference between training and inference memory.
  • Interview questions often ask you to write the forward pass of a small network on a whiteboard.

Watch out

  • Missing batch dimension. A tensor of shape (784,) fails or silently broadcasts in a layer that expects (B, 784). Use unsqueeze(0) for a single example.
  • Forgetting model.eval() at inference leaves dropout on and batch norm in batch mode. Outputs become noisy and change per call.
  • Applying softmax to outputs and then passing them to a loss that applies softmax again. Pass raw logits.
  • Storing the loss tensor in a list for logging keeps the whole graph in memory. Use loss.item().
  • Broadcasting hides errors. A (32, 1) tensor minus a (32,) tensor gives (32, 32), not (32,).

44. Loss functions (cross-entropy, MSE)

In short A loss function gives one number that says how wrong a prediction is. Training tries to make this number small. Use mean squared error (MSE) for numbers, and cross-entropy for classes. The right loss gives the right gradient. A wrong pairing of loss and output layer is a very common bug.

Picture it

  • Think of a teacher who grades each answer. MSE grades distance. Cross-entropy grades confidence in the correct answer.
  • MSE example: a model predicts house price 300k, true price 350k. Error is 50k. Squared error is 2,500 million. A 100k error costs 4 times more than a 50k error.
  • Because of squaring, MSE is very sensitive to outliers. One bad label can dominate. Mean absolute error or Huber loss is gentler.
  • Cross-entropy example: three classes (cat, dog, bird). The true class is cat. The model gives probabilities 0.7, 0.2, 0.1. The loss is -ln(0.7) = 0.36.
  • If the model gives cat only 0.01, the loss is -ln(0.01) = 4.6. If it gives 0.9, the loss is 0.105. A confident wrong answer is punished hard.
  • Binary cross-entropy (BCE) is for yes or no, and for multi-label tasks. A tag model for a document can predict 'invoice' and 'urgent' at once. Each label is its own yes or no.
  • Language models: the loss is cross-entropy at each token, averaged. Perplexity is e raised to that loss. A loss of 2.0 gives perplexity of about 7.4, which means the model is as unsure as a choice among 7.4 equal options.
  • Gradient of cross-entropy with respect to the logits is p - y, where p is the softmax output and y is the one-hot label. It is simple and bounded. Large errors give large but stable steps.

How it works

  • Softmax turns logits z into probabilities: p_i = exp(z_i) / sum_j exp(z_j). Raw exp can overflow. For z = 1000, exp gives infinity.
  • Log-sum-exp trick: subtract the maximum m from all logits first. log softmax(z)_i = z_i - (m + log sum_j exp(z_j - m)). All exponents are now 0 or negative, so no overflow.
  • PyTorch classification loss fuses log-softmax and negative log-likelihood. It expects raw logits and integer class indices. logit binary loss fuses sigmoid and BCE the same way.
  • Why not softmax then log? A tiny probability underflows to exactly 0, and log(0) is minus infinity. The fused version avoids this.
  • Why not MSE for classification? With sigmoid or softmax output, MSE gradients become tiny when the model is confidently wrong. Training stalls. Cross-entropy keeps a strong gradient.
  • Cross-entropy comes from maximum likelihood. Minimising it is the same as maximising the probability the model gives to the training labels.
  • Label smoothing replaces the one-hot target 1.0 with 0.9 and spreads 0.1 over other classes. It reduces over-confidence. Class weights or focal loss help when classes are very uneven, such as 1% fraud.

When it matters

  • The loss defines what the model learns. A loss that does not match the business goal gives a model that does not help.
  • It controls numeric stability. Many NaN losses trace back to a hand-written softmax and log.
  • Perplexity and loss curves are the main health check for language model training.
  • Interview tip: connect loss to output layer. Regression: linear output with MSE. Multi-class: logits with cross-entropy. Multi-label: logits with BCE.

Watch out

  • Double softmax: apply softmax in the model, then classification loss, which applies it again. Learning slows and probabilities flatten. Same for sigmoid and logit binary loss.
  • Wrong target type. classification loss wants class indices (long integers) or class probabilities. One-hot floats with the wrong shape give errors or wrong loss.
  • Using accuracy as the loss is impossible. Accuracy has no useful gradient because it is a step function. Use it only as a metric.
  • A low loss does not mean a good model on uneven data. A model that always says 'not fraud' gets a low loss at 1% fraud. Check precision, recall, and calibration.
  • Do not compare loss values across different tokenizers or datasets. Perplexity is only meaningful with the same tokens.

45. Backpropagation & the chain rule

In short Backpropagation computes the gradient of the loss with respect to every weight. It uses the chain rule and walks the network from output to input. The gradients then tell the optimiser how to change each weight. It costs about as much as two forward passes, so training is feasible even with billions of weights.

Picture it

  • Think of blame sharing. The loss is high. Backprop asks: how much did each weight contribute? It passes blame backward, layer by layer.
  • Example: a tiny chain. z = w·x, then y_hat = sigmoid(z), then loss L = (y_hat - y)^2. Let x = 2, w = 0.5, y = 1.
  • Forward: z = 1.0, y_hat = 0.731, L = 0.0724.
  • Backward step 1: dL/dy_hat = 2(y_hat - y) = -0.538.
  • Backward step 2: dy_hat/dz = y_hat(1 - y_hat) = 0.197. So dL/dz = -0.538 × 0.197 = -0.106.
  • Backward step 3: dz/dw = x = 2. So dL/dw = -0.106 × 2 = -0.212. A negative gradient means that raising w lowers the loss.
  • Each step multiplies the incoming gradient by a local derivative. This is the chain rule: dL/dw = dL/dy_hat × dy_hat/dz × dz/dw.
  • For a linear layer with output z = Wx: the gradient for W is the outer product of the incoming gradient and x (delta times x transposed). The gradient passed to the previous layer is W transposed times delta.

How it works

  • The forward pass builds a graph. Each node is a simple operation such as matrix multiply, add, or ReLU. The graph stores the tensors needed for derivatives.
  • The backward pass visits nodes in reverse order. Each node receives the gradient of the loss with respect to its output. It returns gradients with respect to its inputs.
  • If a value is used in two places, its gradients add up. This is why weight sharing in CNNs and RNNs works. The shared filter gets the sum of gradients from all positions.
  • Reverse mode is cheap when there is one scalar output and many inputs. That fits a loss and millions of weights. Forward mode would need one pass per weight.
  • Cost: the backward pass is about twice the forward cost. One training step is about three times a forward pass.
  • Memory: backward needs the saved activations. Gradient checkpointing saves only some and recomputes the rest. It trades about 30% more compute for large memory savings.
  • In PyTorch: tensors with learning-enabled record operations. loss.backward() fills the .grad field of each leaf tensor. Gradients add to existing .grad values. Gradient check: compare with the numeric estimate (L(w + e) - L(w - e)) / 2e on a small model. This finds bugs in custom backward code.

When it matters

  • It is the algorithm behind every deep learning model. Optimisers only use its output.
  • It explains vanishing gradients, since gradients are products of local derivatives.
  • It explains memory use in training and why checkpointing helps.
  • It explains bugs with detach, no_grad, and in-place changes.

Watch out

  • Gradients accumulate. If you do not call optimizer.zero_grad() each step, old gradients add to new ones. The effective step becomes wrong. You can use this on purpose for gradient accumulation across small batches.
  • Calling .item(), .numpy(), or detach() cuts the tensor out of the graph. Gradients stop there. Training silently stops for earlier layers.
  • In-place operations can overwrite a value that backward needs. PyTorch then raises an error. Avoid in-place changes on tensors that need gradients.
  • A second backward() call on the same graph fails because the graph is freed. Use retain_graph=True only when you really need it.
  • Non-smooth operations, such as argmax or rounding, have zero or undefined gradient. A model with argmax in the middle cannot learn through it.

46. Gradients: vanishing & exploding

In short In a deep network, the gradient at early layers is a product of many numbers, one per layer. If each number is below 1, the product goes to zero (vanishing). If each is above 1, it grows without limit (exploding). Vanishing gradients stop early layers from learning. Exploding gradients cause NaN loss.

Picture it

  • Think of a message passed along a line of 50 people. If each person repeats only 80% of the volume, the last person hears nothing. If each repeats 120%, the last person is deafened.
  • Number example: the slope of sigmoid is at most 0.25. Through 10 sigmoid layers the gradient shrinks by at most 0.25^10, which is about 0.000001. Early layers get almost no signal.
  • Exploding example: a weight factor of 1.5 over 50 steps gives 1.5^50, which is about 6 × 10^8. One update then throws the weights far away, and the loss becomes NaN.
  • Where it appears: deep plain networks, and especially RNNs. An RNN reuses the same weight matrix at every time step. A 100-step sequence multiplies by that matrix 100 times.
  • Symptom of vanishing: training loss decreases very slowly. Early layers show gradient norms near 0 while late layers look normal.
  • Symptom of exploding: sudden loss spikes, gradient norms of 1e4 or more, then NaN or infinity.
  • Fix summary: pick activations with slope near 1 (ReLU, GELU). Add residual connections. Add normalisation. Use careful initialisation. Clip gradients. Use gated RNNs.
  • Residual connections give the gradient a direct path. A block y = x + F(x) has derivative 1 + dF/dx. The 1 means the gradient cannot vanish across the block.

How it works

  • Backprop gives the gradient at layer 1 as a product: W_n^T · diag(f'(z_n)) · ... · W_2^T · diag(f'(z_2)). Its size scales like lambda^n, where lambda is the typical size of one factor. Lambda below 1 vanishes. Above 1 explodes.
  • More exactly, lambda relates to the largest singular value of the weight matrix times the activation slope.
  • Initialisation keeps lambda near 1. Xavier (Glorot) init uses variance 2 / (fan_in + fan_out) for tanh and sigmoid. He init uses variance 2 / fan_in for ReLU. The factor 2 offsets ReLU zeroing half of the units.
  • Gradient clipping by norm: if the total gradient norm g is above a limit c, scale it: g = g × c / norm. The direction stays the same. The step size is capped. A common value for c is 1.0.
  • LSTM and GRU add a cell state with additive updates: c_t = f_t · c_(t-1) + i_t · c_candidate. When the forget gate is near 1, the gradient passes through almost unchanged.
  • Normalisation layers re-centre and re-scale activations at each layer. This keeps the signal and the gradient in a stable range.
  • Learning-rate warmup starts with a tiny rate and grows it over the first steps. Early updates are the most dangerous because weights and Adam statistics are not yet settled.

When it matters

  • It explains why transformers use residual connections and layer norm. Without them, 100-layer models would not train.
  • It explains why LSTMs replaced plain RNNs.
  • It is a standard interview question with a clear answer: cause, symptoms, and fixes.
  • In practice, it guides debugging. You log gradient norms per layer and act on what you see.

Watch out

  • NaN loss does not always mean exploding gradients. Other causes: log of zero, division by zero, bad data values, learning rate too high, or float16 overflow. Check the data and the loss first.
  • ReLU has its own failure. A neuron with negative input always outputs 0 and has zero gradient. It can die and never recover (dying ReLU). Lower the learning rate or use Leaky ReLU or GELU.
  • Clipping hides a problem. If clipping triggers on every step, fix the cause, such as the learning rate or initialisation.
  • Clip after unscaling when you use mixed precision with a loss scaler. Clipping scaled gradients uses the wrong limit.
  • Vanishing gradients are not the only reason for slow training. Poor learning rate or bad data can look the same.

47. Activation functions (ReLU, sigmoid, tanh, GELU, softmax)

In short An activation function adds a non-linear bend after each linear layer. Without it, a deep network is just one linear map. Use ReLU or GELU in hidden layers, and sigmoid or softmax at the output to make probabilities. The shape of the function controls the gradient, and the gradient controls how well the network trains.

Picture it

  • Think of a light switch versus a dimmer. A linear layer is a plain dimmer. An activation adds a bend, such as a threshold or a soft knee. Many bends together let the network draw complex shapes.
  • Sigmoid: 1 / (1 + e^-z). Output between 0 and 1. Good for a yes or no probability. For large or small z, the curve is flat and the gradient is near 0 (saturation). Maximum slope is 0.25.
  • Tanh: output between -1 and 1. It is centred on zero, which helps training compared with sigmoid. It still saturates.
  • ReLU: max(0, z). Slope is 1 for positive input and 0 for negative input. It is cheap and does not saturate on the positive side. It is the classic hidden-layer default.
  • Leaky ReLU: a small slope, such as 0.01, for negative input. It prevents dead neurons.
  • GELU: z times the probability that a standard normal value is below z. It is a smooth version of ReLU. BERT and GPT models use it.
  • SwiGLU: one linear path multiplied by a swish-activated second path. Llama-style models use it in the feed-forward block. It improves quality at a small cost in extra weights.
  • Softmax: turns a vector of logits into probabilities that sum to 1. Use it for single-label multi-class output. Example: logits 2.0, 1.0, 0.1 become 0.66, 0.24, 0.10.
  • Choice at the output: sigmoid per class for multi-label (a document can be both 'invoice' and 'urgent'). Softmax for exactly one label.

How it works

  • Non-linearity is needed because a composition of linear maps is linear. W2(W1x) equals (W2W1)x. The activation breaks this.
  • ReLU turns a layer into a piecewise linear function. Each neuron's on or off state selects a region. Together, the network cuts the input into many linear pieces.
  • Gradient view: backprop multiplies by f'(z). Sigmoid and tanh have f'(z) below 1 and near 0 at the ends. ReLU has f'(z) = 1 on its active side. That keeps gradients alive in deep nets.
  • Dying ReLU: if a large update pushes a neuron's input below 0 for all data, its gradient is 0 and its weights never change. Leaky ReLU, GELU, and lower learning rates reduce this.
  • Softmax is shift invariant: adding a constant to all logits does not change the output. Implementations subtract the maximum logit for numeric stability.
  • Temperature: divide logits by T before softmax. T below 1 sharpens the distribution. T above 1 flattens it. Language model sampling uses this.
  • Attention uses softmax over the scores of all positions, so the weights sum to 1.

When it matters

  • Activation choice affects training speed, stability, and final quality.
  • Output activation must match the loss and the task. This is a frequent interview check.
  • GELU and SwiGLU show up in modern transformer designs, so you should know why they replaced ReLU.
  • It links to topic 46: activation slope drives vanishing gradients.

Watch out

  • Sigmoid or tanh in the hidden layers of a deep network can stall training because of saturation. Prefer ReLU or GELU.
  • Do not soften scores into probabilities before the classification loss. The loss already includes that step.
  • Softmax for multi-label tasks forces the classes to compete. Use sigmoid per class instead.
  • Softmax outputs are not true confidence. They can be near 1.0 on wrong or out-of-domain inputs. Calibrate before you use them as thresholds.
  • ReLU with a very high learning rate can kill many units at once. Watch the share of zero outputs.

48. Optimizers (SGD, momentum, Adam/AdamW)

In short An optimiser turns gradients into weight updates. SGD steps straight downhill. Momentum smooths the path. Adam also scales the step for each weight, and AdamW is the standard for language models. The learning rate is the most important setting. A schedule with warmup and decay is the normal practice.

Picture it

  • Think of a hiker in fog who feels only the slope under their feet. SGD takes a step downhill each time. In a narrow valley the hiker zig-zags from wall to wall.
  • SGD: w = w - lr × g, where g is the gradient on a mini-batch. The batch gives a noisy but cheap estimate. Noise can help escape sharp minima.
  • Momentum: keep a running average of past gradients. The hiker becomes a rolling ball. Side-to-side wiggles cancel. The steady downhill part adds up. Typical factor: 0.9.
  • Adam: keep two running averages for every weight. The first (m) is the average gradient. The second (v) is the average squared gradient. The step is m / (sqrt(v) + epsilon).
  • Meaning of the Adam step: a weight with big, noisy gradients gets a smaller step. A weight with small, steady gradients gets a larger step. Each weight gets its own scale.
  • Defaults: beta1 = 0.9, beta2 = 0.999 (0.95 for large language models), epsilon = 1e-8. The method often works with no tuning.
  • AdamW: applies weight decay directly to the weights, not through the gradient. In plain Adam with L2, the decay gets divided by sqrt(v) and becomes uneven. AdamW fixes this and generalises better.
  • Schedule: warm up the learning rate for the first 1-5% of steps, then decay by cosine or linear to a small value. Example for fine-tuning: peak 2e-5 for full fine-tuning, 2e-4 for LoRA.

How it works

  • Adam update in detail: m = b1·m + (1 - b1)·g. v = b2·v + (1 - b2)·g². Bias correction: m_hat = m / (1 - b1^t), v_hat = v / (1 - b2^t). Update: w = w - lr × m_hat / (sqrt(v_hat) + eps).
  • Bias correction is needed because m and v start at 0. In the first steps they are too small. The correction divides by a factor that goes to 1.
  • Memory: Adam stores m and v for every weight, two extra FP32 numbers, which is 8 bytes. Add FP32 master weights (4) and gradients (4) for mixed precision with 16-bit weights (2). The total is about 16 bytes per parameter.
  • Example: a 7B model needs about 7 billion × 16 bytes = 112 GB for full training state. This is why LoRA trains a small set of weights and saves the rest. It is also why 8-bit and paged optimisers exist.
  • SGD with momentum uses only one extra buffer. It is common in vision. Adam family dominates transformers.
  • Warmup matters for Adam because v is estimated from few samples early on. Large first steps can wreck a model.
  • Batch size and learning rate link. A common rule is to scale the learning rate with the batch size (linearly for SGD, roughly with the square root for Adam). Gradient accumulation: add gradients over k small batches, then step once. It gives the effect of a large batch with less memory.

When it matters

  • It explains why training needs much more memory than inference.
  • Choosing the learning rate and schedule is the main lever in fine-tuning.
  • AdamW versus Adam is a popular interview question. Say 'decoupled weight decay'.
  • It supports cost planning. You can estimate GPU memory before you start a job.

Watch out

  • Learning rate too high: loss spikes or becomes NaN. Too low: loss barely moves. Run a quick sweep or a learning-rate range test.
  • Order of calls: optimizer.zero_grad(), loss.backward(), optimizer.step(). Calling step before backward uses stale gradients.
  • Weight decay should not apply to biases and norm parameters. Applying it everywhere hurts. Use separate parameter groups.
  • Pass only trainable parameters to the optimiser when you freeze layers. Otherwise it allocates state for weights that never change.
  • Adam can generalise worse than SGD on some vision tasks. Do not assume it always wins.

49. Regularization (dropout, weight decay, early stopping)

In short Regularisation reduces overfitting by limiting how freely a model can fit its training data. Main tools are dropout, weight decay, early stopping, data augmentation, and more data. The goal is lower error on new data, even if training error rises a little. Small enterprise datasets overfit fast, so regularisation matters most in fine-tuning.

Picture it

  • Think of a student who memorises last year's exam answers. The student scores 100% on that exam and fails a new one. Regularisation forces the student to learn the ideas.
  • Sign of overfitting: training loss keeps falling, validation loss turns up. The gap between them grows.
  • Dropout: during training, set a random share p of activations to 0 on each step. Example: p = 0.5. A neuron cannot count on any one neighbour, so the network learns redundant, robust features.
  • Inverted dropout: keep a unit with probability 1 - p and scale the kept values by 1 / (1 - p). With p = 0.5, kept values double. At test time, do nothing. The expected size is the same.
  • Weight decay (L2): add lambda × sum of squared weights to the loss. Large weights cost more. Each step shrinks the weight by a factor (1 - lr × lambda). The function becomes smoother.
  • L1 penalty: lambda × sum of absolute weights. It pushes many weights to exactly 0 and gives sparse models.
  • Early stopping: after each epoch, check validation loss. Keep the best checkpoint. Stop after a patience of a few epochs with no gain.
  • Data augmentation: make new samples from old ones. Images: flips, crops, colour shifts. Text: synonym swap, back-translation. Documents: add scan noise and rotation.
  • More data is the best regulariser. If you cannot get labels, use augmentation, synthetic data, or a pretrained model.

How it works

  • Why L2 works: it prefers small weights. Small weights mean outputs change slowly with inputs. A smooth function fits noise less.
  • Bayesian view: L2 is a Gaussian prior on the weights. L1 is a Laplace prior.
  • Dropout as an ensemble: each step trains a different thinned network. At test time you use the average of all of them, approximately.
  • Dropout rates: 0.1 in transformers, 0.5 in old fully connected layers. Rarely used in the convolution layers of modern CNNs, where batch norm already regularises.
  • AdamW decouples decay from the adaptive step. Plain L2 inside Adam is scaled by the adaptive denominator and acts unevenly.
  • Early stopping works as a regulariser because weights start small and grow during training. Stopping early limits their size.
  • Label smoothing and mixup also regularise. They stop the model from becoming too certain. Capacity control is the other path. Use fewer layers, fewer units, or a low-rank adapter such as LoRA, which limits the number of weights that change.

When it matters

  • Fine-tuning on a few thousand documents overfits quickly. A weak setup gives a model that memorises the training set.
  • Regularisation tools are cheap, so they are the first thing to try before collecting more data.
  • Interviews often ask: 'Training accuracy is 99%, validation is 80%. What do you do?'
  • They link to bias and variance (topic 62). Regularisation trades a little bias for much less variance.

Watch out

  • Leaving the model in train() mode at inference. Dropout stays active and the answers change on each call. Call model.eval().
  • Too much regularisation causes underfitting. If training loss is also high, reduce dropout or weight decay.
  • Early stopping on the test set leaks information. Use a separate validation set.
  • Augmentation must keep the label correct. Flipping the digits 6 and 9, or mirroring text, changes meaning.
  • Using dropout together with batch norm can clash in some layouts, because dropout changes the variance that batch norm measures.

50. Batch norm vs layer norm

In short Normalisation layers rescale activations to zero mean and unit variance, then apply a learned scale and shift. Batch norm computes the statistics across the batch for each feature. Layer norm computes them across the features of each single sample. Batch norm is common in CNNs. Layer norm is standard in transformers.

Picture it

  • Think of marking exams from different classes. Batch norm re-scales each question's scores across all students in the class. Layer norm re-scales each student's scores across all questions of that student.
  • Why normalise: the input to each layer changes as earlier layers change. Normalisation keeps values in a stable range. Training is faster, allows a higher learning rate, and is less sensitive to initialisation.
  • Formula: x_hat = (x - mean) / sqrt(variance + epsilon). Output y = gamma × x_hat + beta. Gamma and beta are learned, so the network can undo the normalisation if needed.
  • Batch norm example: a CNN feature map has shape (B, C, H, W). For each channel c, compute the mean and variance over B, H, and W. Each channel gets its own gamma and beta.
  • Layer norm example: a transformer tensor has shape (B, T, D). For each token, compute the mean and variance over its D features. No batch values are used.
  • RMSNorm: skip the mean. Divide by the root mean square: x / sqrt(mean(x²) + eps), then scale by gamma. It is cheaper and works as well. Llama uses it.
  • Placement in transformers: pre-norm applies the norm before attention and the feed-forward block (x + F(norm(x))). It trains more stably in deep stacks than post-norm.
  • Group norm splits channels into groups and normalises within each group per sample. It works with small batches. Diffusion U-Nets use it.

How it works

  • Batch norm at training time uses the statistics of the current batch. It also updates running averages: running = (1 - momentum) × running + momentum × batch_stat. PyTorch momentum is 0.1.
  • Batch norm at inference uses the stored running mean and variance. The output of one sample then does not depend on other samples.
  • Gap between modes: if the batch is small or unlike the real data, the batch statistics are noisy. The running averages may then not match what the model saw in training.
  • Layer norm gives the same computation in training and inference. No running statistics. This is why it suits variable length sequences and batch size of 1 at serving time.
  • Batch norm adds a mild noise effect, since each sample's output depends on its batch mates. This acts as a small regulariser.
  • Batch norm can be folded into the previous convolution at inference. The scale and shift are merged into the conv weights. This removes the layer cost.
  • Normalisation also helps gradients. It keeps activation scale stable across depth, which reduces vanishing and exploding gradients.

When it matters

  • It explains train versus eval differences in vision models.
  • It explains why transformers use layer norm: sequences have varying length and padding, and batches can be small in large-model training.
  • Pre-norm versus post-norm is a design choice that affects stability of very deep models.
  • It is a very common interview comparison. Be ready to state the axes of the statistics.

Watch out

  • Batch norm with batch size 1 or 2 gives very noisy statistics. Use group norm or layer norm, or freeze the batch norm layers.
  • Forgetting model.eval() makes batch norm use batch statistics at inference. Results then depend on the batch.
  • When you fine-tune with a small batch, running statistics from pretraining can be damaged. Freeze batch norm layers, or keep them in eval mode.
  • Padding tokens must not count in layer norm over the sequence axis if you normalise across time. Standard layer norm normalises over features only, so it is safe.
  • In distributed training, each GPU sees only its slice of the batch. Standard batch norm uses local statistics unless you use synchronised batch norm.

51. CNN: convolution, filters, pooling, stride, padding

In short A convolutional neural network (CNN) slides small learned filters over an image to find local patterns. The same filter is used at every position, so the model has few weights and finds a pattern wherever it appears. Pooling and stride shrink the image step by step. Early layers find edges. Deep layers find parts and whole objects.

Picture it

  • Think of a small magnifying glass moving across a page. It looks for one pattern, such as a vertical edge. It marks every place where the pattern appears.
  • Filter (kernel): a small grid of weights, such as 3 × 3. At each position, multiply the grid with the patch under it and add up the results. The output at that position is one number.
  • Feature map: all outputs of one filter over the image. It shows where the pattern is present.
  • Channels: a layer has many filters. With 64 filters you get 64 feature maps. An RGB image has 3 input channels, and each filter spans all 3.
  • Stride: how far the filter moves each step. Stride 2 halves the width and height. Padding: add a border of zeros so the edges get covered. 'Same' padding keeps the size.
  • Pooling: take the max (or average) of each 2 × 2 block. It halves the size and makes the output a little tolerant to small shifts.
  • Hierarchy: edges in layer 1, textures and corners in the middle, object parts and objects deep. The receptive field is the part of the input that one unit sees. It grows with depth.
  • Example uses: text detection in scans, defect detection on a factory line, medical image segmentation.
  • Famous designs: LeNet (digits), AlexNet (2012 ImageNet win), VGG (stacked 3 × 3), ResNet (skip connections), U-Net (segmentation), YOLO (fast detection).

How it works

  • Output size = floor((N - F + 2P) / S) + 1. Example: N = 224, F = 3, P = 1, S = 1 gives 224. With S = 2 it gives 112.
  • Parameters of a conv layer: F × F × C_in × C_out + C_out. Example: 3 × 3, 64 in, 128 out gives 9 × 64 × 128 + 128 = 73,856. This does not depend on the image size.
  • Compare with a dense layer: a 224 × 224 × 3 image has 150,528 values. A dense layer to 1,000 units needs about 150 million weights. A conv layer uses far fewer.
  • Two assumptions: locality (nearby pixels matter together) and translation equivariance (a shifted input gives a shifted output). These are inductive biases. They work well with images and need less data than a generic MLP.
  • Stacking two 3 × 3 layers gives the same receptive field as one 5 × 5, with fewer weights (18 versus 25 per channel pair) and an extra activation.
  • 1 × 1 convolution mixes channels at each position. It changes the channel count cheaply, as in ResNet bottlenecks.
  • Depthwise separable convolution splits the work into a per-channel spatial filter and a 1 × 1 channel mix. It cuts compute by about 8 to 9 times for 3 × 3. MobileNet uses it. Residual blocks add the input to the output: y = x + F(x). The gradient has a direct path, so 100-plus layers train. A vision transformer (ViT) is the modern alternative. It cuts the image into patches and uses attention.

When it matters

  • CNNs are the base of OCR text detectors, layout models, and defect finders.
  • Parameter sharing is a clear example of how a good inductive bias saves data and compute.
  • The size and parameter formulas are classic interview calculations.
  • Pretrained CNN backbones are the standard start for small vision datasets (topic 61).

Watch out

  • Wrong tensor layout. PyTorch expects (B, C, H, W). Images from common loaders often come as (H, W, C). Permute before use.
  • Pooling can lose fine detail, such as thin strokes in handwriting. Use stride-1 or dilated layers for small text.
  • A CNN is not rotation or scale invariant by default. Use augmentation for rotated scans.
  • Odd kernel sizes (3, 5) keep the filter centred. Even sizes cause half-pixel shifts and uneven padding.
  • Forgetting to normalise input with the same mean and standard deviation used in pretraining gives poor results with pretrained backbones.

52. RNN / LSTM / GRU

In short A recurrent neural network (RNN) reads a sequence one step at a time. It keeps a hidden state that acts as memory and reuses the same weights at each step. LSTM and GRU add gates that control what to keep and what to erase, so they remember over longer ranges. Transformers replaced them in most language work, because transformers train in parallel and link distant words directly.

Picture it

  • Think of reading a sentence word by word while keeping notes on a small card. Each new word updates the card. The card is the hidden state.
  • Plain RNN: h_t = tanh(W_h · h_(t-1) + W_x · x_t + b). The same W_h and W_x apply at every step.
  • Example: predict the next word in 'The invoices from the supplier in Germany were paid in ...'. The word 'Germany' appeared eight words earlier. A plain RNN often forgets it.
  • Reason: during training, gradients pass back through every step. They are multiplied by W_h each time. Over 50 steps they vanish or explode (topic 46).
  • LSTM adds a cell state c_t, a conveyor belt that runs along the sequence. Three gates, each a sigmoid between 0 and 1, control it.
  • Forget gate f: how much of the old cell to keep. Input gate i: how much of the new candidate to write. Output gate o: how much of the cell to show as h_t.
  • Update: c_t = f_t × c_(t-1) + i_t × candidate. h_t = o_t × tanh(c_t). The update is additive, so the gradient can flow back through many steps when f is near 1.
  • GRU: a lighter design with two gates. The update gate blends old state and new candidate. The reset gate decides how much past state to use in the candidate. It has no separate cell state and has about 25% fewer weights than an LSTM.
  • Where they still appear: small on-device models, streaming audio, sensor and time-series data with tight memory limits.

How it works

  • LSTM parameters: four sets of weights (three gates plus candidate). With input size x and hidden size h, the count is 4 × (h × (h + x) + h). Example: x = 128, h = 256 gives 4 × (256 × 384 + 256) = 394,240.
  • Training uses backpropagation through time (BPTT). The network is unrolled for T steps. Gradients flow back through all steps. For long sequences, truncated BPTT cuts the backward path to a window, such as 100 steps.
  • The forget gate bias is often initialised to 1. The cell then keeps information by default at the start of training.
  • Sequential nature: step t needs step t-1. You cannot compute all steps at once. Training a long sequence is slow on a GPU compared with attention.
  • Bidirectional RNN: run one RNN left to right and one right to left. Concatenate the states. It helps tasks where the whole sentence is known, such as tagging. It does not work for live generation.
  • Seq2seq: an encoder RNN compresses the input into one vector. A decoder RNN generates the output. A single vector is a bottleneck for long inputs. Attention was invented to fix this, and then transformers dropped the RNN.
  • Transformer comparison: self-attention links any two positions in one step, and trains in parallel. Its cost grows with the square of the length. An RNN has a constant memory per step, which suits streaming.

When it matters

  • The question 'why transformers over RNNs' is very common. Answer: parallel training and direct long-range links.
  • It shows the idea of gating, which appears again in SwiGLU and in state-space models.
  • Modern efficient sequence models such as Mamba and RWKV revisit recurrence for linear-cost inference.
  • It ties to vanishing gradients, so it tests deeper understanding.

Watch out

  • Some sequence modules expect time first: (time, batch, features). Many shape bugs come from assuming batch is first.
  • Variable length sequences need padding and packing (pack_padded_sequence), or the model reads pad tokens as real input.
  • Clip gradients in RNN training. A norm limit near 1 to 5 prevents explosions.
  • Do not carry the hidden state across unrelated batches by accident. Reset it, or detach it from the graph if you keep it.
  • An LSTM has limits too. It still forgets very long ranges, such as thousands of tokens.

53. Autoencoders (and VAEs)

In short An autoencoder squeezes its input into a small code and then rebuilds the input from that code. It needs no labels. The small code forces the network to learn the main structure of the data. A variational autoencoder (VAE) makes the code a probability distribution, so you can sample new data from it.

Picture it

  • Think of describing a face in 50 numbers to a sketch artist. The artist redraws the face from only those numbers. If the redraw looks right, the 50 numbers hold the key information.
  • Parts: the encoder maps input x to a code z. The decoder maps z back to x_hat. The loss is the difference between x and x_hat, often mean squared error.
  • Bottleneck: z is much smaller than x. Example: a 784-pixel digit compressed to 32 numbers. A linear autoencoder learns the same space as PCA. With non-linear layers it learns more.
  • Denoising autoencoder: feed in a damaged input (noise, masked pixels) and train to rebuild the clean one. It learns to repair, not copy.
  • Anomaly detection example: train on normal machine sensor images only. At run time, a normal image rebuilds well (low error). A cracked part rebuilds badly (high error). Flag high error.
  • A plain autoencoder has gaps in its latent space. Pick a random z and the decoder gives garbage. It is not made for generation.
  • VAE: the encoder outputs a mean and a variance for z. You sample z from this distribution, then decode. A KL term pulls the distributions toward a standard normal. The latent space becomes smooth and filled, so sampling works.
  • Use in modern systems: Stable Diffusion uses a VAE to compress a 512 × 512 × 3 image to a 64 × 64 × 4 latent. That is 48 times fewer values. Diffusion runs in the latent space.

How it works

  • Autoencoder loss: ||x - x_hat||². Use binary cross-entropy for pixels in the 0 to 1 range.
  • VAE loss = reconstruction loss + KL( q(z|x) || N(0, I) ). This is the negative evidence lower bound (ELBO).
  • KL for a diagonal Gaussian has a closed form: -0.5 × sum(1 + log(sigma²) - mu² - sigma²). It is zero when mu = 0 and sigma = 1.
  • Reparameterisation trick: sampling is not differentiable. Write z = mu + sigma × epsilon, with epsilon from N(0, I). The random part is now an input. Gradients flow through mu and sigma.
  • Trade-off: a strong KL weight gives a smooth latent space but blurry outputs. A weak KL weight gives sharper outputs but a messy latent space. The beta-VAE adds a weight to tune this.
  • Blurriness: MSE loss averages over many plausible outputs, which makes soft images. This is why GANs and diffusion give sharper images.
  • Variants: sparse autoencoders (penalty on active units; used to find features inside language models), VQ-VAE (discrete codes from a codebook), and convolutional autoencoders for images.

When it matters

  • It is the base idea of unsupervised representation learning. You learn useful features with no labels.
  • Anomaly detection with reconstruction error is a practical enterprise use, for example fraud or equipment checks.
  • The VAE is a component in latent diffusion, so it explains how image generators can run on modest GPUs.
  • The reparameterisation trick is a favourite theory question.

Watch out

  • A bottleneck that is too wide lets the network learn the identity function. It copies the input and learns nothing useful. Keep z small, add noise, or add a sparsity penalty.
  • A good rebuild of normal data can also rebuild some anomalies, since the network generalises. Check recall of anomalies on labelled examples.
  • Posterior collapse: the decoder ignores z and the KL goes to zero. This happens with strong decoders. Use KL annealing (start with a small weight) or a weaker decoder.
  • Reconstruction error depends on the image. Bright, detailed images give a higher error even when normal. Normalise per sample or per region.
  • A VAE is not a good choice when you need sharp samples. Use diffusion or GANs.

54. GANs (high level)

In short A generative adversarial network (GAN) has two networks that compete. The generator makes fake samples from random noise. The discriminator tries to tell fake from real, and the generator learns from the discriminator's feedback. GANs make sharp images in one forward pass, but training is unstable. Diffusion models have largely replaced them.

Picture it

  • Think of a forger and a detective. The forger paints fake banknotes. The detective checks them. Each time the detective catches a fake, the forger learns what gave it away. Both get better.
  • Generator G: takes a random vector z (for example 128 numbers) and outputs an image.
  • Discriminator D: takes an image and outputs the probability that it is real.
  • Training loop: take a batch of real images and a batch of fakes from G. Update D to label real as 1 and fake as 0. Then update G so that D labels its fakes as real.
  • At the ideal end, G matches the real data distribution and D outputs 0.5 for everything, since it cannot tell the difference.
  • Results: StyleGAN made photo-real faces. Pix2Pix and CycleGAN did image-to-image changes such as sketch to photo. GAN loss also sharpens super-resolution models.
  • Speed: one forward pass makes an image. Diffusion needs many steps. GANs are still used when speed matters, such as real-time upscaling.
  • Why diffusion won for general image generation: stable training, better diversity, and easier text control.

How it works

  • Objective: min over G, max over D of E[log D(x)] + E[log(1 - D(G(z)))]. This is a two-player minimax game.
  • Early in training, D wins easily, so log(1 - D(G(z))) is flat and gives G almost no gradient. The common fix is the non-saturating loss: G maximises log D(G(z)).
  • With an optimal D, the objective equals the Jensen-Shannon divergence between real and generated distributions. This has trouble when the two distributions do not overlap, which gives vanishing gradients.
  • Wasserstein GAN uses the earth mover's distance with a critic instead. Gradient penalty or spectral normalisation keeps the critic smooth. Training is more stable and the loss correlates better with quality.
  • Mode collapse: G finds a few outputs that fool D and makes only those. Example: a face GAN that produces the same ten faces. Diversity is lost.
  • Training balance: if D becomes too strong, G gets no signal. If D is too weak, G does not improve. Teams tune learning rates, update ratios, and use tricks such as label smoothing and instance noise.
  • Conditional GAN: feed a class label or text to both G and D, so you can control what is generated.

When it matters

  • GANs introduced adversarial training. The idea also appears in domain adaptation and in some safety methods.
  • Interviewers ask about them to see if you know what came before diffusion and why it changed.
  • Deepfake and synthetic data risks relate to GANs, so they matter for trust and safety.
  • Synthetic data from GANs can help to balance rare classes, but quality must be verified.

Watch out

  • GAN loss values do not show image quality. D loss and G loss can both look healthy while images are poor. Judge by samples and metrics.
  • Use Fréchet Inception Distance (FID) to compare generated and real feature statistics. Lower is better. Use human review too. FID needs thousands of samples.
  • Mode collapse can hide inside a good FID. Also check diversity by looking at many samples.
  • Training can diverge suddenly after hours. Save checkpoints often.
  • Synthetic images in a training set can leak artefacts. A downstream model may learn GAN fingerprints, not real features.

55. Diffusion models

In short A diffusion model learns to remove noise a little at a time. To make an image, it starts with pure random noise and cleans it up over many steps. Text prompts steer the cleaning so the result matches the description. Diffusion trains stably and gives diverse, high-quality images. The cost is that you must run the network many times per image.

Picture it

  • Think of a photo that fades into TV static over 1,000 steps. A diffusion model learns to play this film backward, from static to photo.
  • Forward process (fixed, no learning): at each step, mix in a little Gaussian noise. After T steps (often 1,000), the image is pure noise.
  • Reverse process (learned): a network takes a noisy image x_t and the step number t. It predicts the noise that was added. We subtract part of it to get a slightly cleaner image. Repeat from t = T down to 0.
  • Training is simple. Pick a real image. Pick a random step t. Add noise of the matching size. Ask the network to predict that noise. The loss is the mean squared error between true noise and predicted noise.
  • Network type: a U-Net with attention, or a diffusion transformer (DiT). The step t enters as an embedding.
  • Text control: a text encoder (CLIP or T5) turns the prompt into vectors. The network reads them through cross-attention at each step.
  • Classifier-free guidance: run the network twice, once with the prompt and once without. Push the result away from the 'no prompt' prediction by a guidance scale (for example 7.5). A higher scale follows the prompt more but reduces diversity.
  • Latent diffusion (Stable Diffusion): a VAE compresses a 512 × 512 × 3 image to a 64 × 64 × 4 latent. Diffusion runs there. The cost drops by about 48 times in values per step. The VAE decoder makes the final image.
  • Speed: the original method needed about 1,000 steps. DDIM and better solvers need 20 to 50. Distillation, consistency models, and flow matching reach 1 to 4 steps.

How it works

  • Noise schedule: beta_t is the noise added at step t. Let alpha_bar_t = product of (1 - beta_s) for s up to t. It says how much of the original signal is left.
  • Closed-form jump: x_t = sqrt(alpha_bar_t) × x_0 + sqrt(1 - alpha_bar_t) × epsilon. You can make any noisy version in one step, with no loop. This makes training fast.
  • Training loss: E || epsilon - epsilon_theta(x_t, t) ||². Predicting noise works well. Some models predict the clean image x_0 or a velocity v instead. They are linked by the same formula.
  • Sampling step (DDPM): x_(t-1) = (1 / sqrt(alpha_t)) × (x_t - (beta_t / sqrt(1 - alpha_bar_t)) × epsilon_theta) + sigma_t × z. A small random term z keeps the process stochastic. DDIM drops it and gives a deterministic path, which allows bigger steps.
  • Cosine schedule keeps more signal in the early steps than a linear schedule. It gives better quality at low resolution.
  • Flow matching trains a network to predict the velocity along a straight path from noise to data. Paths are straighter, so fewer steps are needed. Newer image models use it.
  • Diffusion is related to score matching. The predicted noise is linked to the gradient of the log density of the data. Inference cost = number of steps × cost of one network call (twice that with guidance).

When it matters

  • Diffusion is the base of most modern image, video, and audio generation.
  • Production cost depends on step count. This is why few-step methods are valuable.
  • It shows a pattern: replace one hard task (make an image) with many easy tasks (remove a little noise).
  • Understanding it lets you compare with GANs and VAEs in interviews.

Watch out

  • Diffusion does not write pixels one by one like an autoregressive model. It refines the whole image at every step.
  • High guidance scale gives burnt colours and low diversity. Too low gives weak prompt following.
  • Fewer steps usually cost quality, unless the model was distilled for it. Test the trade-off on your own prompts.
  • Training data copyright and memorisation are real risks. Models can reproduce training images in rare cases.
  • Text rendering and counting objects remain weak points of many diffusion models.

56. Transfer learning & freezing layers

In short Transfer learning starts from a model pretrained on a large dataset and adapts it to a new, smaller task. Early layers hold general features, so you often freeze them. You train only the later layers or a new head. It is the normal starting point for almost all enterprise AI work, since labelled data is usually small.

Picture it

  • Think of hiring an experienced engineer for a new product. They already know the basics. You teach them only the details of your product. That takes days, not years.
  • Why it works: early layers of a vision model find edges and textures. Early layers of a language model learn grammar and word meaning. These are useful in almost every task. Later layers are specific to the original task.
  • Example, vision: take a ResNet pretrained on ImageNet. Replace the final 1,000-class layer with a 5-class layer for invoice, receipt, contract, ID, and other. Train on 2,000 labelled scans.
  • Example, language: take a pretrained language model. Fine-tune it on 3,000 labelled support tickets to classify urgency. Or use LoRA to train a small adapter.
  • Rule of thumb on data size. Very small: freeze the whole backbone, train a new head (feature extraction). Medium: unfreeze the top blocks. Large and similar to the pretraining data: fine-tune everything with a small learning rate.
  • Domain gap matters. ImageNet features help on photos. They help less on X-rays or scanned forms, so you need to unfreeze more layers.
  • Use discriminative learning rates: small rates for early layers, larger for later layers and for the new head. For example 1e-5 for the backbone and 1e-3 for the head.
  • Result: higher accuracy with far fewer labels, a shorter training time, and a smaller bill.

How it works

  • Freezing means setting no-gradient on a parameter. No gradient is computed for it. The optimiser stores no state for it. Memory and time drop.
  • Frozen layers still run in the forward pass. Their activations are still needed to feed later layers. You save the backward work and optimiser memory, not the forward compute.
  • Feature caching: if the backbone is fully frozen and you use no augmentation, compute its outputs once and train the head on stored features. Training becomes very fast.
  • Gradual unfreezing: train the head first for a few epochs. Then unfreeze the top block, then the next, with a lower learning rate for each. This protects pretrained features from large random gradients of a fresh head.
  • Parameter-efficient fine-tuning: LoRA adds small low-rank matrices to chosen weights and trains only those, often under 1% of the parameters. The base weights stay frozen. Adapters can be swapped per task or per customer.
  • Batch norm needs care. Frozen layers with train-mode batch norm still update running statistics. Put frozen batch norm layers in eval mode.
  • Catastrophic forgetting: fine-tuning on a narrow task can erase general skills. Low learning rates, fewer epochs, mixing in general data, and LoRA reduce it.

When it matters

  • Enterprise data sets are small, so almost every shipped model starts from a pretrained one.
  • It cuts cost. Fine-tuning a head takes minutes on one GPU. Training from scratch takes weeks.
  • It lets teams serve many customers with one base model and many small adapters.
  • Interviewers ask when to freeze, when to unfreeze, and how to pick learning rates.

Watch out

  • A large learning rate on pretrained layers destroys the features you wanted to reuse. Use small rates for the backbone.
  • Pass only trainable parameters to the optimiser. Otherwise extra state is created for frozen weights.
  • Use the same preprocessing as pretraining: image size, mean and standard deviation, and the same tokeniser for text.
  • Negative transfer: a pretrained model from a very different domain can do worse than a small model trained from scratch. Compare with a baseline.
  • Check the licence and the pretraining data of the base model. Some licences limit commercial use.

57. What is ML; train/test; overfitting vs underfitting (bias–variance)

In short Machine learning (ML) learns patterns from data to make predictions on new data. The key test is generalisation: how well the model does on data it has not seen. Bias and variance describe the two ways a model can fail to generalise. Underfitting means the model is too simple. Overfitting means it memorised the training data.

Picture it

  • Think of a student preparing for an exam. Study notes are the training set. Practice tests are the validation set. The final exam is the test set. You see the final exam only once.
  • Training set: the data used to fit the weights. Validation set: the data used to choose settings such as learning rate, model size, and stopping point. Test set: the data used once at the end for the final number.
  • Example: 10,000 labelled invoices. Use 7,000 for training, 1,500 for validation, 1,500 for test. Split by vendor or by date if you want to know how the model handles new vendors.
  • Underfitting (high bias): the model is too simple, such as a straight line through a curve. Error is high on both training and test data.
  • Overfitting (high variance): the model fits noise. Training error is very low and test error is much higher. Example: 99% train accuracy and 80% test accuracy.
  • Fix underfitting: a bigger model, better features, longer training, less regularisation.
  • Fix overfitting: more data, regularisation (topic 49), a simpler model, early stopping, data augmentation, and cross-validation to tune.
  • Learning curves help to diagnose. Plot error against training set size. If both curves are high and close, add model power. If there is a large gap, add data or regularise.
  • Types of learning: supervised (labelled pairs), unsupervised (find structure with no labels), self-supervised (labels made from the data itself, as in language modelling), and reinforcement learning (learn from rewards).

How it works

  • Error decomposition for squared loss: expected error = bias² + variance + irreducible noise. Bias is the gap between the average model and the truth. Variance is how much the model changes with a different training sample. Noise is the part no model can predict.
  • Complexity trade-off: as the model grows, bias falls and variance rises. The test error is U-shaped, with a best point in the middle.
  • Modern note: very large networks can show 'double descent'. Test error rises near the point where the model just fits the training data, and falls again with more size. The simple U shape is a guide, not a law.
  • K-fold cross-validation: split the data into k parts. Train on k-1 parts and validate on the remaining one. Repeat k times and average. It gives a steadier estimate on small data.
  • Ensembles lower variance. Averaging many models, as in random forests, cancels their independent errors. Boosting lowers bias by fitting the remaining error step by step.
  • Data leakage happens when information from the test set reaches training. Examples: scaling with statistics from all data, duplicates across splits, and features that contain the answer.
  • Metrics must fit the task. For uneven classes, use precision, recall, and F1, not accuracy alone. For ranking, use metrics such as NDCG. For regression, use MAE or RMSE. Distribution shift: production data differs from training data. A model that generalised to the test set can still fail later.

When it matters

  • Every model review ends with the question: how do you know it will work on new data?
  • It guides what to do next. Is the problem the model, the data, or the settings?
  • A clean split and honest metrics are what separate lab results from production results.
  • These ideas apply to LLM work too: evaluation sets, fine-tuning overfit, and leakage of benchmark data into training.

Watch out

  • Tuning on the test set gives numbers that look good and collapse in production. Touch the test set once.
  • Random splits can leak when records are related, such as many pages from one document, or many rows for one customer. Split by group.
  • For time series, never shuffle. Train on the past and test on the future.
  • Accuracy can mislead on uneven classes. A model that says 'not fraud' for all cases scores 99% when fraud is 1%.
  • Do not fix an underfit model with more regularisation, or an overfit model with more layers. Diagnose first with train and validation error.

58. Supervised vs unsupervised vs self-supervised vs RL

In short The four learning types differ in where the learning signal comes from. Supervised learning uses labels that people wrote, unsupervised learning has none, self-supervised learning builds labels from the data, and reinforcement learning (RL) uses rewards. An LLM uses three of them in order: self-supervised pretraining, supervised instruction tuning, and RL from human feedback.

Picture it

  • Supervised: a bank has 200,000 past loans. Each loan has a label: repaid or defaulted. The model learns the map from loan features to that label.
  • Unsupervised: a shop has 100,000 customers and no labels. K-means groups them into 4 segments by spend and visit rate. A person then names the segments.
  • Semi-supervised: a team has 1,000 labeled invoices and 500,000 unlabeled ones. The model learns structure from all of them and uses the 1,000 labels to name the classes.
  • Self-supervised: take the sentence 'The cat sat on the mat'. Hide the last word. Ask the model to predict 'mat'. The text itself is the label. No human wrote it.
  • Self-supervised at scale: GPT-style pretraining runs this next-token task on trillions of tokens. Each token position gives one free training example.
  • Contrastive self-supervision: CLIP trains on about 400 million image and caption pairs. It pulls matching pairs close in embedding space. It pushes non-matching pairs apart.
  • RL: a robot or a game agent acts. The environment returns a reward, such as +1 for a win. The agent learns a policy, which is a rule for choosing actions.
  • RL in LLMs: the model writes two answers. A person picks the better one. A reward model learns that preference. PPO then updates the LLM to raise the reward.

How it works

  • Supervised loss compares a prediction with a known label. For classification, the loss is cross-entropy. For regression, the loss is mean squared error. Gradient descent lowers the loss.
  • Unsupervised methods optimize a built-in goal. K-means lowers the squared distance to the cluster centers. PCA keeps the directions with most variance. No label enters the loss.
  • Self-supervised learning is supervised learning with automatic labels. The loss is still cross-entropy. Only the source of the label differs. Masked language models (BERT) hide about 15% of tokens and predict them.
  • RL differs in one key way: the data depends on the agent. A different policy produces different states and rewards. So the data distribution moves during training. This makes RL less stable than supervised learning.
  • RL goal: maximize the expected sum of discounted rewards. A discount factor gamma, such as 0.99, makes near rewards count more than far rewards.
  • Reward credit assignment is hard. If a chess game gives one reward after 80 moves, the agent must work out which moves caused the win. Value functions and advantage estimates help with this.

When it matters

  • Interviewers ask this to test if you can pick the right setup for a problem. Fraud with labeled history is supervised. Customer grouping with no labels is unsupervised.
  • The LLM lifecycle question is common. Name all three stages and the loss or signal for each. This shows you understand how a chat model is built.
  • Label cost drives real decisions. If one expert label costs 2 dollars and you need 100,000, that is 200,000 dollars. Self-supervised pretraining removes most of that cost.
  • RL fits problems with delayed outcomes and no single right answer, such as ranking, bidding, and robot control.

Watch out

  • Do not call LLM pretraining 'unsupervised'. The precise term is 'self-supervised'. The data gives its own labels.
  • Do not use RL when supervised learning works. RL needs far more samples and is harder to debug. Use it only when the signal is a delayed reward.
  • Reward hacking: the agent finds a way to get high reward without doing the task. A reward model can reward long, confident answers that are wrong. Add KL penalties and human checks.
  • Weak labels are not free. If 10% of supervised labels are wrong, the model learns that noise. Check label quality before you tune the model.

59. Linear regression

In short Linear regression predicts a number as a weighted sum of input features plus a bias. It finds the weights that make the mean squared error smallest. It is the base model for regression tasks and the core of every linear layer in a neural network.

Picture it

  • House price: price = 50,000 + 3,000 x (square meters) + 8,000 x (bedrooms). Each weight says how much the price moves when that feature rises by one unit.
  • Draw 100 houses as dots on a plot of size against price. The best line is the one where the squared vertical gaps from dots to the line add up to the smallest value.
  • A residual is the gap between the real value and the predicted value. If the real price is 300,000 and the model says 280,000, the residual is 20,000.
  • Squaring makes big misses count more. One miss of 100 costs 10,000. Ten misses of 10 cost only 1,000 in total. So one outlier can pull the line toward it.
  • Matrix view: X has one row per house and one column per feature. The prediction vector is the shadow of the true price vector on the space the columns of X span.
  • Polynomial regression still counts as linear regression. You add columns x squared and x cubed. The model stays linear in the weights, but the curve bends.
  • R squared tells how much variance the model explains. A value of 0.80 means the model explains 80% of the spread in price. A value of 0 means it does no better than the mean.

How it works

  • Model: y-hat = Xw + b. Loss: L = (1/N) x sum of (y - y-hat) squared. We want the weights that make L smallest.
  • Closed form: w = (X^T X)^-1 X^T y. This is the normal equation. Inverting a d x d matrix costs about d cubed operations. For 10,000 features that is about 10^12 operations, which is slow.
  • Gradient descent avoids the inverse. The gradient of L is (2/N) x X^T (Xw - y). Each step is w = w - learning rate x gradient. It scales to millions of rows and works with mini-batches.
  • The loss for linear regression is a convex bowl. It has one minimum. Gradient descent with a good step size always reaches it.
  • Multicollinearity: two columns carry almost the same information, such as size in square feet and size in square meters. X^T X becomes nearly singular. The weights become huge and cancel each other, for example +1000 and -998.
  • Assumptions behind the standard error bars: linear relation, independent errors, constant error variance, and errors close to normal. The predictions still work if these fail a little. The confidence intervals do not.

When it matters

  • It is the first baseline to build. If a gradient boosting model beats it by only 1%, the extra complexity may not be worth it.
  • Weights are easy to explain. A business user can read 'each extra bedroom adds 8,000'. That helps in finance and healthcare reviews.
  • A neural network layer computes Wx + b. If you know linear regression, you know the core of every dense layer.
  • Interviewers use it to test the full chain: model, loss, closed form, gradient, assumptions, and what breaks.

Watch out

  • Outliers dominate MSE. If data has bad sensor spikes, use MAE or Huber loss, or clean the data first.
  • Correlated features make the weights unstable. Use ridge regression or drop one feature.
  • Do not read a weight as cause. A weight of +8,000 for bedrooms may only mean that bigger houses have more bedrooms.
  • Extrapolation is risky. A line trained on houses of 50 to 200 square meters can give nonsense for 1,000 square meters.

60. Logistic regression

In short Logistic regression is a classifier that computes a linear score and passes it through a sigmoid to get a probability. It trains with binary cross-entropy loss. It gives a straight-line decision boundary.

Picture it

  • Spam filter: the model adds up evidence. The word 'prize' adds +2.1. A known sender adds -1.5. The total score z is 0.6. The sigmoid turns 0.6 into a probability of 0.65.
  • Sigmoid values to remember: z = 0 gives 0.5. z = 2 gives 0.88. z = -2 gives 0.12. z = 5 gives 0.993. The curve is flat at both ends.
  • Odds view: probability 0.8 equals odds of 4 to 1. The log of the odds is 1.39. Logistic regression says the log-odds equal a linear sum of features.
  • A weight of 0.7 on a feature means the odds multiply by e^0.7, which is about 2.0, for each +1 in that feature. This is why people call the weights interpretable.
  • In 2D, the decision boundary is a straight line where the score is 0. Points on one side get class 1. Points on the other side get class 0.
  • Loan default: a model gives a 0.12 default chance. The bank can approve at a threshold of 0.20 and decline above it. The threshold is a business choice, not a model choice.
  • Multi-class: use one score per class and apply softmax. This is called softmax regression. It is the same math as the output layer of an LLM.

How it works

  • Model: p = sigmoid(w.x + b), where sigmoid(z) = 1 / (1 + e^-z). The output is the probability of class 1.
  • Loss for one example: -[y log p + (1 - y) log (1 - p)]. If y = 1 and p = 0.9, the loss is 0.105. If y = 1 and p = 0.1, the loss is 2.30. Confident wrong answers cost a lot.
  • Gradient of the loss with respect to w is (p - y) x. That is the prediction error times the input. The formula is simple because sigmoid and cross-entropy cancel each other's messy terms.
  • The loss is convex. There is one global minimum. Mean squared error with sigmoid is not convex and trains slowly when the sigmoid is flat. This is why we use cross-entropy.
  • Perfectly separable data breaks training. The weights grow without limit because a larger weight always lowers the loss. L2 regularization stops this by penalizing large weights.
  • Training uses gradient descent, or Newton-type solvers such as L-BFGS. Each pass costs O(N x d).

When it matters

  • It is a strong, fast, explainable baseline for tabular classification. Banks and insurers often must explain a decision, and this model allows that.
  • It outputs a probability. You can check calibration: of all cases scored 0.7, do about 70% turn out positive?
  • It links to deep learning. The last layer of a classifier network is logistic or softmax regression on learned features.
  • Interviewers like the question 'why cross-entropy, not MSE, for classification'. The answer: convex loss, strong gradient on wrong answers, and it matches maximum likelihood.

Watch out

  • The 0.5 threshold is not special. In fraud with 0.1% positives, a good threshold may be 0.02. Pick it from the precision and recall you need.
  • Class imbalance pushes the probabilities down. A model trained on 1% positives rarely outputs above 0.5. Use class weights or tune the threshold.
  • The boundary is linear. If classes form a ring, the model fails. Add features such as x squared, or use a tree model.
  • Unscaled features slow gradient descent and make L2 penalties unfair. Scale features first.

61. K-nearest neighbours (KNN)

In short K-nearest neighbors (KNN) predicts from the k closest training points. Classification takes a vote and regression takes an average. KNN does no training, so all the work happens at query time.

Picture it

  • Movie taste: to guess if you will like a film, find the 5 users most like you. If 4 of them liked it, predict yes.
  • Small k: with k = 1, one odd neighbor decides the answer. The boundary is jagged and follows noise. This is overfitting.
  • Large k: with k = N, every query gets the majority class. This is underfitting. A middle value, such as 5 to 25 chosen by cross-validation, usually works best.
  • Scaling trap: a customer has salary 800,000 and age 30. Another has salary 810,000 and age 60. The salary gap is 10,000 and the age gap is 30. The distance is almost all salary. Age has no effect.
  • Scale cost: 1 million stored points with 768 dimensions. One query by brute force needs about 768 million multiply-add operations. That is too slow for a live service with many queries per second.
  • Fix: approximate nearest neighbor (ANN) indexes such as HNSW or IVF. They check a small part of the data and return 95% to 99% of the true neighbors in milliseconds.
  • RAG retrieval is KNN. The query is embedded. The system returns the k nearest chunk embeddings. A vector database is an ANN index with filters and storage.

How it works

  • Training stores the data. There are no weights. Memory is O(N x d). Prediction costs O(N x d) per query for brute force.
  • Distance choices: Euclidean (straight line), Manhattan (sum of absolute gaps), and cosine (angle). Use cosine for text embeddings. Use Euclidean for scaled numeric features.
  • Weighted KNN gives closer neighbors more vote, for example weight = 1 / distance. This reduces the harm from a bad far neighbor.
  • KD-trees and ball trees speed up search in low dimensions, below about 20. They help little in high dimensions.
  • HNSW builds a layered graph. A query starts at the top layer, jumps to close nodes, and goes down. Search takes about O(log N) steps. The cost is extra memory for the graph links.
  • Curse of dimensionality: as the dimension grows, the nearest and farthest points get close in distance. The ratio tends toward 1. 'Nearest' then loses meaning for raw sparse features.

When it matters

  • KNN is the simplest model that explains vector search. If you know KNN, you can explain RAG retrieval, recommenders, and duplicate detection.
  • It needs no training, so it suits a quick baseline or a case with few examples per class.
  • It adapts at once when you add data. A new product only needs a new stored point. No retraining needed.
  • The ANN trade-off (speed against recall) is a common system design topic.

Watch out

  • Always scale numeric features, or use a metric that does not depend on scale. Otherwise one large-valued feature controls the result.
  • Do not use KNN on millions of rows with brute force. Use an ANN index and measure recall against exact search.
  • Ties in a vote: with 2 classes, pick an odd k. With more classes, break ties by distance.
  • Class imbalance: with 1% positives, the vote almost always says negative. Weight votes or use a lower vote threshold.

62. Support Vector Machines

In short A support vector machine (SVM) finds the boundary with the widest gap, called the margin, between two classes. Only the nearest points, called support vectors, define that boundary. A kernel lets the SVM draw curved boundaries.

Picture it

  • Many lines can split two groups of points. The SVM picks the line with the widest empty street between the groups.
  • Only the points on the edge of the street matter. If you delete any other point, the boundary stays the same. Often these support vectors are 5% to 20% of the data.
  • Margin width is 2 / ||w||. If w = (3, 4), then ||w|| = 5 and the margin is 0.4. A smaller w means a wider street.
  • Soft margin: real data overlaps. Parameter C sets the price of crossing the street. Large C means strict, with a narrow street. Small C means loose, with a wide street and more errors allowed.
  • Kernel idea: points on a ring cannot be split by a line. Map each point (x, y) to include x squared plus y squared. Now the ring points sit higher than the center points and a flat plane splits them.
  • RBF kernel: similarity falls with distance, like a bump around each support vector. A parameter gamma sets the bump width. Large gamma gives narrow bumps and overfitting.
  • Classic use: a spam or topic classifier on TF-IDF vectors with 100,000 sparse features and 5,000 documents. A linear SVM is fast and strong here.

How it works

  • Goal: minimize (1/2)||w||^2 + C x sum of slack values, with the rule y(w.x + b) >= 1 - slack for each point. Slack measures how far a point is inside the street or on the wrong side.
  • Hinge loss: max(0, 1 - y x f(x)). If a point is on the correct side by more than the margin, the loss is 0. Only points near or past the boundary cost anything. This is why only support vectors matter.
  • Dual form: the weights are w = sum of alpha_i y_i x_i, where alpha_i is nonzero only for support vectors. The prediction uses dot products between the query and support vectors.
  • Kernel trick: replace each dot product x.x' with a kernel K(x, x'). The model works as if in a very high dimension without building those coordinates. For RBF, K = exp(-gamma x ||x - x'||^2), which corresponds to infinite dimensions.
  • Cost: a kernel SVM needs the kernel matrix, which is N x N. At N = 100,000 that is 10 billion entries. Training takes between O(N^2) and O(N^3) time. Linear SVMs with SGD scale far better.
  • SVM outputs a signed distance to the boundary, not a probability. Platt scaling fits a sigmoid on top of that distance to give probabilities.

When it matters

  • SVMs do well on small to medium data with many features, such as text, genomics, and small image sets.
  • Max-margin thinking appears elsewhere. Hinge loss and margin ideas return in ranking losses and contrastive learning.
  • The kernel trick is a standard theory question. Be ready to explain it in two sentences without math.
  • The model is robust when the number of features exceeds the number of rows.

Watch out

  • Scale features before training. A feature with a large range controls the distance in an RBF kernel.
  • Kernel SVM does not scale to millions of rows. Switch to a linear SVM, or use gradient boosting.
  • Do not treat the SVM score as a probability. Calibrate it first if you need real probabilities.
  • Tune C and gamma together with cross-validation on a log grid, such as 0.01 to 100. A wrong pair gives poor results.

63. Decision trees & Random Forest

In short A decision tree splits data with yes or no questions on features, and each split makes the child groups purer. A random forest trains many trees on random parts of the data and averages them. Averaging cuts variance and keeps the low bias of deep trees.

Picture it

  • Churn tree: 'Contract under 6 months?' If yes, ask 'Support tickets over 3?' If yes, predict churn. Each path from root to leaf is a readable rule.
  • Split example: a node has 100 customers, 50 churned and 50 stayed. Gini is 0.50. The question splits them into left 40 (36 churned) and right 60 (14 churned). The weighted Gini drops to 0.287. The gain is 0.213.
  • A deep tree can give each training row its own leaf. Training accuracy hits 100%. Test accuracy is poor. This is high variance.
  • Forest idea: ask 500 different trees and take the vote. Each tree sees a different random sample of rows, so each makes different mistakes. The mistakes partly cancel.
  • Each tree uses a bootstrap sample. This means sampling N rows with replacement. About 63.2% of unique rows appear in each sample. The other 36.8% are 'out-of-bag' and give a free validation score.
  • At each split, a tree looks at only a random subset of features, often the square root of the total. For 100 features, that is 10. This keeps the trees different from each other.
  • Tabular example: a card fraud model on 50 columns, such as amount, merchant type, hour, and distance from home. A forest handles mixed types and needs no scaling.

How it works

  • Training is greedy. For each feature and each possible cut point, the algorithm computes the impurity drop. It takes the best cut and repeats on each child. It stops at a max depth, a min leaf size, or when the gain is too small.
  • Impurity: Gini = 1 - sum of p_c squared. Entropy = -sum of p_c log2 p_c. For regression, use the variance of the target. A 50/50 node has Gini 0.5. A 90/10 node has Gini 0.18.
  • To find the best cut for a numeric feature, sort the values once and scan. Cost is about O(N log N) per feature per node. Cut points sit between neighbor values.
  • Random forest variance: for n trees with variance s^2 and pairwise correlation r, the average has variance r x s^2 + (1 - r) x s^2 / n. More trees remove the second term. Random feature subsets lower r.
  • Prediction for regression is the mean of leaf values across trees. For classification it is the average of class fractions, or the majority vote.
  • Feature importance: sum the impurity drops each feature caused, over all splits and trees. Permutation importance is more reliable. It shuffles one feature on validation data and measures the score drop.

When it matters

  • Forests are a strong default for tabular business data such as churn, fraud, and credit risk. They need little tuning.
  • Trees need no scaling, handle missing values and mixed types in many libraries, and capture feature interactions on their own.
  • Out-of-bag error gives a quick honest estimate without a separate validation set.
  • The bias-variance story is clear here: one deep tree has low bias and high variance. A forest keeps the low bias and cuts the variance.

Watch out

  • Trees cannot extrapolate. If training prices stop at 500,000, the model never predicts 600,000. Use a linear model or add trend features for time series.
  • Impurity-based importance favors features with many unique values, such as an ID column. Use permutation importance for a fair view.
  • A single tree is unstable. A small change in data can change the root split. Do not explain a business rule from one tree without checking stability.
  • Large forests are heavy. 500 trees of depth 20 can use gigabytes and slow low-latency serving. Limit depth or tree count.

64. Gradient boosting (GBM, XGBoost, LightGBM)

In short Gradient boosting builds many small trees one after another. Each new tree learns the errors that the current ensemble still makes. XGBoost, LightGBM, and CatBoost are fast, regularized versions that often win on tabular data.

Picture it

  • House price: the first guess is the mean price, 300,000. A house sells for 400,000. The residual is +100,000. Tree 1 learns to predict residuals like this one from features.
  • Learning rate 0.1: tree 1 predicts +100,000 for that house, but the model adds only 10,000. The new guess is 310,000. A small step makes each tree a gentle correction.
  • If every tree fits the leftover perfectly, the remaining error is 100,000 x 0.9^m after m trees. After 50 trees it is about 520. Real trees fit less well, so you need more trees.
  • Bagging versus boosting: a random forest trains 500 trees in parallel to cut variance. Boosting trains trees in sequence to cut bias. Boosting trees are shallow, often depth 3 to 8.
  • Kaggle and industry: on tables with 10,000 to 10 million rows, tuned gradient boosting beats deep learning in most public comparisons.
  • Click prediction: 100 million rows with 200 features. LightGBM trains in minutes on a multi-core machine by bucketing feature values into 255 bins.
  • Early stopping: watch the validation loss. If it does not improve for 50 rounds, stop and keep the best round. This picks the tree count automatically.

How it works

  • Model: F_m(x) = F_(m-1)(x) + eta x f_m(x). Here eta is the learning rate and f_m is a small tree.
  • Each tree fits the negative gradient of the loss with respect to the current predictions. For squared error, the negative gradient equals the residual y - F. For log loss, it is y - p, which is the error in probability.
  • Why 'gradient': this is gradient descent in function space. We do not update weights. We add a function that points downhill on the loss.
  • XGBoost uses the first and second derivative of the loss for each row. It scores a split with these sums and a penalty on leaf count and leaf weight. This gives a regularized objective and good splits.
  • LightGBM uses histograms. It bins each feature into at most 255 buckets, so a split search scans 255 bins, not N rows. It grows trees leaf-wise, which means it splits the leaf with the biggest gain. This is faster but can overfit on small data.
  • CatBoost encodes categories with ordered target statistics. It uses an order that avoids target leakage. It handles high-cardinality categories well without one-hot encoding.
  • Key knobs: learning rate (0.01 to 0.3), number of trees, max depth, min child weight, row subsample, column subsample, and L2 regularization.

When it matters

  • It is the default answer for structured enterprise data before deep learning. Say it first, then justify any move to a neural network.
  • It handles missing values, mixed scales, and nonlinear interactions with little preprocessing.
  • SHAP values give per-row feature contributions. This supports review in credit and healthcare.
  • Inference is cheap. A model with 500 trees of depth 6 scores a row in well under a millisecond on a CPU.

Watch out

  • Overfitting: too many trees or too deep trees fit noise. Use early stopping on a validation set, and keep a separate test set.
  • Leakage hurts boosting a lot. The model finds any feature that hints at the label and uses it hard. Check suspicious top features.
  • A low learning rate with more trees generalizes better but trains longer. Use 0.05 to 0.1 for tuning, and lower it for the final run.
  • Like all tree models, it cannot extrapolate beyond the training range. Do not use it alone for strong trends.

65. Ridge, Lasso, ElasticNet

In short Ridge, lasso, and elastic net add a penalty on weight size to a regression loss. Ridge (L2) shrinks all weights smoothly, and lasso (L1) pushes some weights to exactly zero. Elastic net mixes the two.

Picture it

  • Think of a budget for weights. A model with a small budget cannot use huge weights. It must stay simple, so it overfits less.
  • Twin features: size in square feet and size in square meters. Plain regression may give weights +1000 and -998. These cancel on the training data but break on new data.
  • Ridge splits the weight about evenly between twins, for example +1 and +1. Lasso keeps one and sets the other to 0. Elastic net tends to keep both with similar values.
  • Genomics or text case: 10,000 features and 500 rows. Plain regression fits the noise perfectly. Lasso may keep only 40 features, so you also get feature selection.
  • Penalty strength lambda: at 0 you get plain regression. At a very large value all weights go to 0 and the model predicts the mean. You pick lambda by cross-validation.
  • Geometry: the loss forms ellipses around the best plain solution. The penalty forms a region around zero. L2 is a circle. L1 is a diamond with corners on the axes. The ellipse often first touches the diamond at a corner, where one weight is 0.
  • Neural nets use the same idea. L2 regularization is called 'weight decay'. AdamW applies it in a clean way.

How it works

  • Ridge loss: sum of squared errors + lambda x sum of w squared. Closed form: w = (X^T X + lambda I)^-1 X^T y. Adding lambda I to the diagonal makes the matrix invertible and stable.
  • Lasso loss: sum of squared errors + lambda x sum of |w|. There is no closed form because |w| has a kink at 0. Solvers use coordinate descent: update one weight at a time with a soft-threshold step.
  • Soft threshold: a weight with a small pull from the data, below lambda, becomes exactly 0. A larger pull is reduced by lambda. This creates sparsity.
  • The gradient of the L2 penalty is 2 x lambda x w. It pulls each weight toward 0 in proportion to its size. The gradient of the L1 penalty is lambda x sign(w). It pulls with constant force, so small weights reach 0.
  • Elastic net loss: squared error + lambda1 x sum of |w| + lambda2 x sum of w squared. With a group of correlated features, lasso picks one at random. Elastic net keeps the group.
  • Bayesian view: ridge equals a Gaussian prior on the weights. Lasso equals a Laplace prior. Both give a maximum a posteriori estimate.

When it matters

  • Regularization is the first tool against overfitting in linear models. Interviewers expect you to name it and explain the L1 versus L2 difference.
  • Lasso gives built-in feature selection. This helps when you must explain which 20 of 5,000 features drive a prediction.
  • Ridge fixes multicollinearity without dropping features.
  • The weight decay link shows that you can connect classic ML to deep learning.

Watch out

  • Scale features before using any penalty. A feature in meters with small values needs a big weight and gets penalized more than the same feature in millimeters.
  • Do not penalize the bias term. It only shifts the output and does not add complexity.
  • Lasso with correlated features is unstable. Different samples can pick different features. Use elastic net, or check stability with bootstrap.
  • Select lambda on validation data inside cross-validation. Never pick it on the test set.

66. Clustering: K-means, hierarchical, DBSCAN

In short Clustering groups unlabeled points that look alike. K-means assigns each point to the nearest center and then moves the centers, again and again. Hierarchical clustering and DBSCAN handle cases where K-means fails.

Picture it

  • Retail: 100,000 customers described by recency, frequency, and spend. K-means with k = 4 might find big spenders, loyal regulars, new buyers, and lapsed buyers.
  • K-means loop: 1) pick k random centers. 2) assign each point to its nearest center. 3) move each center to the mean of its points. 4) repeat until the centers stop moving. This often takes 10 to 50 rounds.
  • Choosing k: plot the total squared distance for k = 1 to 10. It drops fast, then slowly. The bend is the 'elbow'. The silhouette score (from -1 to 1) is a second check. Above 0.5 is a clear structure.
  • Hierarchical: start with each point alone. Merge the two closest groups again and again. The result is a tree called a dendrogram. You cut the tree at the height you want.
  • DBSCAN: a point with at least 5 neighbors within distance eps is a core point. Dense regions grow into clusters. Points in sparse areas are marked as noise. It finds ring shapes and needs no k.
  • Support tickets: embed 50,000 tickets with a sentence model. Cluster the embeddings. Read 5 examples from each cluster. You find the top issue themes without labels.
  • Fraud: DBSCAN on transaction features marks a few lone points as noise. A person reviews them as possible anomalies.

How it works

  • K-means minimizes the sum of squared distances from each point to its cluster mean. Each step lowers this value or keeps it equal, so the loop always stops. It may stop at a local minimum.
  • Cost per round is O(N x k x d). For 1 million points, 50 dimensions, and k = 10, that is about 500 million operations per round. This is fast.
  • K-means++ picks the first center at random. It picks each next center with probability proportional to the squared distance from the nearest chosen center. This spreads centers out and gives better results.
  • K-means assumes round, similar-size clusters because it uses the mean and Euclidean distance. A long thin cluster or a ring breaks this.
  • Hierarchical clustering stores a pairwise distance matrix. For 100,000 points that is about 5 billion pairs, or around 40 GB. So it fits only up to roughly 10,000 to 20,000 points.
  • Linkage rules: single (nearest members), complete (farthest members), average, and Ward (smallest rise in variance). Ward gives compact clusters and is a common default.
  • Gaussian mixture models give soft assignments. Each point gets a probability for each cluster. They fit with the EM algorithm and can model oval clusters.

When it matters

  • Clustering is the usual answer to 'we have no labels'. It supports segmentation, topic discovery, and deduplication.
  • It also helps label data fast. Cluster, then label a few points per cluster, then train a supervised model.
  • Embedding plus clustering is a common modern pattern for LLM data. Examples are grouping chat logs, finding duplicates, and sampling diverse training data.
  • You must say how you check quality when no labels exist: silhouette score, cluster stability, and business review of examples.

Watch out

  • K-means on unscaled features gives nonsense. A feature with a range of 100,000 beats a feature with a range of 1.
  • K-means needs k up front and is sensitive to the start. Run it with several seeds (for example 10) and keep the lowest cost.
  • DBSCAN struggles when clusters have very different densities. One eps cannot fit all. It also suffers in high dimensions.
  • A cluster is not a class. Do not report a cluster as a real-world group until a person checks that it makes sense.

67. PCA & dimensionality reduction

In short Principal component analysis (PCA) finds new axes along which the data varies most. You keep the top few axes and drop the rest. This compresses the data and removes noise with little information loss.

Picture it

  • Picture a long, thin cloud of points tilted at 45 degrees. The first principal component runs along the long side. The second runs across the short side at a right angle.
  • Compression: an image set has 1,000 features per image. The first 50 components may hold 95% of the variance. You store 50 numbers, not 1,000. That is a 20x saving.
  • Embedding storage: 1 million vectors of 768 floats use about 3.07 GB. After PCA to 128 dimensions they use about 512 MB. Search is also faster. Recall drops a little.
  • Variance explained: if the variances along the axes are 5, 3, and 2, the first axis explains 50%, and the first two explain 80%.
  • Noise removal: noise spreads over many small-variance axes. Keeping only the large axes often cleans the signal.
  • Visualization: PCA to 2 dimensions gives a quick plot. For cluster pictures of embeddings, t-SNE and UMAP often show local groups better. Their axis scales and distances between groups carry no exact meaning.
  • Low-rank link: if a weight matrix is well approximated by a few directions, you can store it as two thin matrices. This is the idea behind LoRA.

How it works

  • Step 1: center each feature by subtracting its mean. Step 2: compute the covariance matrix, which is X^T X / N. Step 3: find its eigenvectors and eigenvalues. Step 4: keep the eigenvectors with the largest eigenvalues.
  • An eigenvector is a direction. Its eigenvalue is the variance of the data along that direction. The directions are at right angles to each other.
  • In practice, use singular value decomposition: X = U S V^T. The columns of V are the principal directions. The variance along each is S squared / N.
  • Projection: new coordinates = X x V_k, where V_k holds the top k directions. Reconstruction: multiply back by V_k^T. The reconstruction error equals the sum of the dropped eigenvalues.
  • Cost: the covariance matrix is d x d. For d = 768 this is small. For d = 1 million, use randomized SVD or incremental PCA, which only need the top k directions.
  • PCA is linear. It cannot unroll a curved shape such as a spiral. Kernel PCA and autoencoders can capture curves.

When it matters

  • PCA fights the curse of dimensionality and speeds up downstream models and vector search.
  • It removes correlated features without choosing by hand, which helps linear models.
  • It teaches the low-rank idea that returns in LoRA and embedding compression.
  • A common question: 'how many components do you keep?' Answer: enough for 90% to 99% explained variance, or the elbow of the variance curve, checked on the downstream task.

Watch out

  • Always center the data. Scale features too if their units differ. Otherwise the feature with the largest units takes over the first component.
  • Fit PCA on the training set only. Fitting on all data leaks test information.
  • Components mix original features, so they are hard to explain. If you must explain, use lasso or feature importance instead.
  • High variance is not the same as high signal. A noisy feature can have large variance. A key small-variance feature can be dropped by PCA.

68. Metrics: accuracy, precision, recall, F1, ROC-AUC, confusion matrix, RMSE

In short Metrics turn model errors into numbers that match a business risk. Precision, recall, and F1 describe classification, and RMSE and MAE describe regression. The right metric depends on which mistake costs more.

Picture it

  • Fraud example: 10,000 transactions, 100 are fraud. A model that always says 'not fraud' scores 99% accuracy and catches nothing. Accuracy hides the failure.
  • Confusion matrix for a real model: TP = 70, FP = 30, FN = 30, TN = 9,870. Accuracy is 99.4%. Precision is 70 / 100 = 0.70. Recall is 70 / 100 = 0.70. F1 is 0.70.
  • Precision answers: of the items I flagged, how many were right? It matters when a false alarm is costly, such as blocking a good customer or auto-approving an invoice.
  • Recall answers: of the real positives, how many did I find? It matters when a miss is costly, such as fraud, cancer, or a safety fault.
  • Threshold trade-off: lower the threshold and recall goes up but precision goes down. A precision-recall curve shows the whole trade-off.
  • ROC-AUC is the chance that a random positive scores above a random negative. 0.5 is random. 1.0 is perfect. With 0.1% positives, ROC-AUC can look great while precision is poor. PR-AUC is more honest.
  • Regression: errors of 2, 2, 2, 2, 10. MAE = 3.6. RMSE = sqrt((4+4+4+4+100)/5) = 4.9. RMSE is larger because it punishes the big miss.
  • LLM and RAG: use recall@k for retrieval, faithfulness (is the answer supported by the sources?) for generation, and human review for a sample. BLEU and ROUGE only count word overlap and miss meaning.

How it works

  • Definitions: precision = TP / (TP + FP). Recall = TP / (TP + FN). F1 = 2PR / (P + R), the harmonic mean. The harmonic mean is close to the lower value, so a model cannot hide a weak recall behind a strong precision.
  • F-beta: F2 weighs recall twice as much as precision. Use it when misses cost more than false alarms.
  • ROC curve: plot true positive rate against false positive rate for every threshold. Area under it equals the rank probability above. It does not depend on one threshold.
  • PR-AUC baseline equals the positive rate. With 1% positives, a random model has PR-AUC near 0.01. So 0.30 is a large gain.
  • Log loss = the average of -log(probability given to the true class). It rewards good probabilities, not only good ranking. A model that says 0.99 and is wrong gets a loss of 4.6.
  • Precision at k and recall at k: look only at the top k results. With an analyst team that can review 1,000 alerts per day, precision at 1,000 is the metric that matters.
  • Multi-class: macro average takes the mean of per-class scores and treats rare classes equally. Micro average pools all counts and is dominated by large classes.

When it matters

  • A system design answer must name the metric tied to the business risk. 'We maximize recall at 90% precision' is a strong sentence.
  • The metric sets the threshold, the loss weights, and the monitoring plan.
  • Different stakeholders need different views: finance wants cost saved, operations wants review load, and risk wants miss rate.
  • For LLM systems, no single metric works. Combine retrieval metrics, groundedness checks, and human audits.

Watch out

  • Never report accuracy alone on imbalanced data.
  • Do not compare AUC across different test sets. The score depends on the data mix.
  • A metric computed at one threshold goes stale when the data shifts. Recheck the threshold after drift.
  • LLM-as-judge scores have bias, such as a taste for long answers. Calibrate the judge against human labels on at least 200 samples.

69. Cross-validation, leakage, class imbalance

In short Cross-validation (CV) estimates model quality by training and testing on several different splits of the data. Leakage happens when test information reaches training, and it makes scores look too good. Class imbalance needs special handling in splits, metrics, and loss.

Picture it

  • 5-fold CV with 10,000 rows: split into 5 parts of 2,000. Train on 8,000 and validate on 2,000. Repeat 5 times so each part is the validation set once. Average the 5 scores and report the spread.
  • A score of 0.82 +/- 0.01 across folds is stable. A score of 0.82 +/- 0.08 means the result depends on luck in the split.
  • Leakage 1: you scale all data, then split. The scaler used the mean of the test rows. The effect is small but real. Fit it on the training part only.
  • Leakage 2: to predict customer complaints you include a column 'refund_issued'. A refund happens after the complaint. The model looks perfect and fails in production.
  • Leakage 3: the same customer appears in train and test with different rows. The model memorizes the customer. Use group K-fold so one customer stays on one side.
  • Time series: never shuffle. Train on January to June, validate on July. Then train on January to July, validate on August. Training on the future gives false scores.
  • Imbalance: 1 fraud per 1,000 rows. A class weight of about 1,000 on fraud makes one fraud miss as costly as 1,000 good rows. SMOTE makes new fraud-like rows by interpolating between real ones.

How it works

  • Stratified K-fold keeps the class ratio in each fold. With 0.1% positives and 5 folds on 10,000 rows, each fold has about 2 positives. That is too few. Use more data, repeated CV, or a metric with a wide interval.
  • Leave-one-out CV uses k = N. It has low bias but costs N training runs. Use it only for very small data.
  • Nested CV: an inner loop picks hyperparameters. An outer loop measures the score. This avoids a rosy score from picking the best setting on the same folds.
  • A pipeline object keeps the preprocessing steps (scaler, encoder, PCA) inside each fold. Each fold fits those steps on its own training part only.
  • Imbalance fixes work at three levels. Data: undersample the majority or oversample the minority, only inside training folds. Loss: class weights or focal loss. Decision: move the threshold using validation data.
  • Duplicate detection: hash or embed documents and remove near-duplicates before splitting. Near-duplicate text across train and test inflates scores a lot in document tasks.

When it matters

  • Leakage is the most common reason a '99% offline' model fails in production. Interviewers probe this early.
  • Correct splits decide if your numbers are real. A split that mirrors production use (by time, by customer) gives a trustworthy estimate.
  • Rare-event problems like fraud, defects, and churn all need these tools.
  • CV gives a spread, not only a mean. The spread helps you decide if a 0.5 point gain is real.

Watch out

  • Never apply SMOTE or resampling before the split. Copies of the same row in train and validation inflate the score.
  • Never use a random split on grouped or time-ordered data.
  • Do not tune on the test set. Keep it untouched until the very end, and use it once.
  • Very good scores (above 0.99 on a hard task) are a warning sign. First look for leakage, then celebrate.

70. Feature engineering, encoding, scaling

In short Feature engineering turns raw data into numbers that a model can use well. It covers encoding categories, scaling numbers, filling missing values, and building new features from domain knowledge. On tabular problems, good features often matter more than the model choice.

Picture it

  • Order data: raw columns are order_time, amount, and customer_id. Useful features are hour of day, day of week, amount divided by the customer's average amount, and orders in the last 7 days.
  • One-hot encoding: 'city' with 5 values becomes 5 columns of 0 and 1. With 10,000 cities it becomes 10,000 mostly-zero columns. That is too wide. Use frequency encoding, target encoding, or an embedding.
  • Cyclic time: hour 23 and hour 0 are 1 hour apart, but as numbers they are 23 apart. Use sin and cos of (2 x pi x hour / 24) so the clock wraps around.
  • Standardization: income has mean 60,000 and standard deviation 20,000. An income of 100,000 gives z = 2. Now income and age sit on similar scales.
  • Skewed values: house prices range from 50,000 to 5,000,000. Taking the log squeezes the range and makes linear models fit better.
  • Missing values: a blood test is missing for 30% of patients. Fill with the median and add a column 'test_missing'. Often the missingness itself predicts the outcome.
  • Text and images: use TF-IDF or sentence embeddings for text. Use features from a pretrained CNN or ViT for images.

How it works

  • Standardization: z = (x - mean) / std. Min-max: (x - min) / (max - min). Min-max is sensitive to outliers. One value of 1,000,000 squeezes all other values near 0.
  • Which models need scaling: distance models (KNN, SVM, k-means), gradient-based models (linear, neural), and penalized models (ridge, lasso). Tree models do not need it because they only compare values to cut points.
  • Target encoding replaces a category with the mean target for that category. It is strong but leaks if computed on the same rows. Compute it out-of-fold, and add smoothing: blend the category mean with the global mean based on the category count.
  • Embeddings for categories: a learned vector per category, for example 16 numbers for each of 10,000 products. Similar products end up with similar vectors.
  • Aggregates per entity: for each customer compute the mean, max, count, and trend over a window. Window features must use only past data at prediction time.
  • Feature selection: drop constant columns, near-duplicates, and leaky columns. Use lasso, permutation importance, or recursive elimination. Fewer features give faster, more stable models.

When it matters

  • On a tabular task, a day spent on features usually beats a week spent on model tuning.
  • Domain features carry knowledge the model cannot learn from small data, such as 'days since last payment'.
  • Training-serving skew is a big source of bugs. A feature store computes each feature once, and both training and serving read it.
  • Interviewers use this topic to test if you think about leakage and production, not only notebooks.

Watch out

  • Fit scalers, encoders, and imputers on the training set only. Then apply them to validation and test data.
  • Target encoding without out-of-fold computation leaks the label. The model looks strong offline and fails online.
  • A feature that is easy to compute in training but unavailable at prediction time breaks the system. Check each feature against the serving path.
  • Unseen categories at serving time crash a naive one-hot pipeline. Add an 'unknown' bucket.

71. Scalars, vectors, matrices, tensors

In short A scalar is one number, a vector is a list of numbers, a matrix is a grid, and a tensor is an array with any number of dimensions. Deep learning code is mostly tensors with shapes. Most bugs are shape mismatches.

Picture it

  • Scalar: a loss value such as 0.37. Vector: one embedding with 768 numbers, which is a point in 768-dimensional space.
  • Matrix as data: a table with 1,000 rows and 20 columns has shape (1000, 20). Matrix as action: a 768 x 3072 matrix turns a 768-number vector into a 3072-number vector.
  • Token batch: 32 sequences, 512 tokens each, 768 numbers per token. The tensor has shape (32, 512, 768). That is 12,582,912 values. In 32-bit floats, that is about 50 MB.
  • Image batch: 32 images, 3 color channels, 224 by 224 pixels. Shape (32, 3, 224, 224) holds 4,816,896 values.
  • Matrix multiply shape rule: (m x n) times (n x p) gives (m x p). The two inner sizes must match. If they differ, you get the most common error in deep learning code.
  • A dense layer with 768 inputs and 3072 outputs has a weight matrix of 2,359,296 numbers plus 3072 biases.
  • Rank: a matrix has rank r if it has r independent directions. A 4096 x 4096 matrix has 16,777,216 numbers. A LoRA update with rank 8 uses two thin matrices, 4096 x 8 and 8 x 4096. That is 65,536 numbers, about 0.4% of the full size.

How it works

  • Matrix multiply: C[i][j] = sum over k of A[i][k] x B[k][j]. Each output value is a dot product of a row of A and a column of B. The cost is about 2 x m x n x p operations.
  • A GPU runs matrix multiplies very fast because every output value is independent. This is why deep learning uses matrices everywhere.
  • Broadcasting: when one tensor has a size-1 dimension, it is stretched to match the other. Adding a bias of shape (768) to a tensor of shape (32, 512, 768) works. Broadcasting can also hide bugs when shapes match by accident.
  • Transpose swaps two axes. Attention computes Q x K^T: (T x d) times (d x T) gives (T x T), one score for each token pair.
  • Memory layout: tensors are stored in one flat block. A reshape only changes the view. A transpose may need a copy before some operations.
  • Element-wise multiply (Hadamard product) multiplies matching positions. It is not the same as matrix multiply. The two give different shapes and different results.

When it matters

  • Shape reasoning is the fastest way to debug a model and to check an architecture on a whiteboard.
  • Memory and compute estimates start from shapes. Activation size = batch x length x width x bytes.
  • Many methods, such as PCA, LoRA, and embeddings, are linear algebra facts. Rank and projection give you the vocabulary.
  • Interviewers often say 'what is the output shape?' as a quick check of real experience.

Watch out

  • Do not mix element-wise multiply and matrix multiply. In many libraries they use different operators.
  • Wrong axis in sum, mean, or softmax gives valid shapes and wrong numbers. State the axis out loud.
  • Batch dimension order differs between libraries and layers. Check whether the batch comes first or the channels come first.
  • Mixed precision halves the memory (16-bit floats use 2 bytes), but it can overflow or lose small values. Keep loss scaling in mind.

72. Dot product & cosine similarity

In short The dot product multiplies matching numbers of two vectors and adds the results. A large positive value means the vectors point in a similar direction. Cosine similarity divides out the lengths, so it measures direction only.

Picture it

  • Take a = (1, 2, 3) and b = (4, 5, 6). Dot product = 1x4 + 2x5 + 3x6 = 32. The lengths are 3.74 and 8.77. Cosine = 32 / (3.74 x 8.77) = 0.97. The vectors point almost the same way.
  • Perpendicular vectors have dot product 0, such as (1, 0) and (0, 1). Opposite vectors, such as (1, 0) and (-1, 0), give -1 for cosine.
  • Document search: a short query and a long document may have very different vector lengths. Cosine ignores length, so a long document does not win just by being large.
  • Projection: how much of a points along b. The dot product divided by the length of b gives the signed length of that shadow.
  • Attention: each token's query vector takes a dot product with every key vector. High scores mean 'look here'. Softmax turns those scores into weights.
  • A linear layer: each output number is a dot product of one weight row and the input. A layer with 3072 outputs does 3072 dot products.
  • Vector search: embeddings are often normalized to length 1. Then the dot product equals cosine, and the search can use fast inner-product indexes.

How it works

  • Formulas: a.b = sum of a_i x b_i = ||a|| x ||b|| x cos(theta). Cosine similarity = a.b / (||a|| x ||b||).
  • The cost is d multiply-adds for dimension d. Comparing one query with 1 million vectors of 768 dimensions takes about 768 million multiply-adds. Brute force on a GPU does this in a few milliseconds.
  • If vectors are normalized, cosine distance = 1 - cosine, and Euclidean distance squared = 2 x (1 - cosine). So the three rank results in the same order.
  • Scaled dot product attention: scores = Q K^T / sqrt(d_k). For random vectors with unit-variance entries, the dot product has variance d_k. For d_k = 64, dividing by 8 keeps scores near unit size. Without it, softmax saturates.
  • Embedding models are trained so that related texts have high cosine. Contrastive loss pulls matching pairs together and pushes others apart.
  • Cosine ignores magnitude. Sometimes magnitude carries information, such as how confident or how frequent. Then dot product keeps more signal.

When it matters

  • This one operation sits under attention, retrieval, recommendation, and every linear layer.
  • Interviewers ask 'dot product or cosine for RAG?' Strong answer: normalize the embeddings, then they are the same; check what the embedding model was trained with.
  • It lets you reason about cost: search time grows with the number of vectors times the dimension.
  • Understanding the geometry helps you explain why synonyms land near each other in embedding space.

Watch out

  • Dot product favors long vectors. If you want pure similarity, normalize first.
  • Do not mix embeddings from different models in one index. Their spaces are unrelated, and the cosine values mean nothing.
  • High cosine does not mean the same fact. 'The drug is safe' and 'The drug is not safe' can score above 0.9 in some models. Use a reranker or a cross-encoder for fine meaning.
  • In high dimensions, cosine values cluster in a narrow band. A threshold such as 0.8 must be tuned on your data and not copied from a blog.

73. Softmax as "sharpened probabilities"

In short Softmax turns a list of raw scores, called logits, into probabilities that add up to 1. It raises e to each score and divides by the total. The largest score gets an even larger share, so softmax is a smooth version of argmax.

Picture it

  • Scores (2, 1, 0.1). Exponentials: 7.39, 2.72, 1.11. Sum = 11.21. Probabilities: 0.66, 0.24, 0.10. The top score has a 2-point lead and gets 66%.
  • Temperature 0.5 divides the scores by 0.5 first: (4, 2, 0.2). Probabilities become 0.86, 0.12, 0.02. The output is sharper.
  • Temperature 2 gives (1, 0.5, 0.05). Probabilities become 0.50, 0.30, 0.19. The output is flatter and more random.
  • LLM next-token step: the model gives 50,000 or more scores, one per token. Softmax makes a probability for each. Sampling picks one token from that distribution.
  • Attention: the scores from one query against 512 keys go through softmax. The 512 weights add to 1. The output is a weighted mix of value vectors.
  • Mixture of experts: a router scores 8 experts and uses softmax. The top 2 experts get the token, and their weights come from the softmax values.
  • Adding 100 to every score changes nothing. (102, 101, 100.1) gives the same probabilities as (2, 1, 0.1).

How it works

  • Formula: softmax(z)_i = exp(z_i) / sum over j of exp(z_j). Exponentials are always positive, so every probability is positive and they sum to 1.
  • Shift invariance: softmax(z + c) = softmax(z). So implementations subtract the maximum score first. Then the largest exponent is exp(0) = 1 and nothing overflows.
  • Overflow: in 32-bit floats, exp(89) is already too large and becomes infinity. Logits of 100 are common in real models. Without the max shift you get NaN.
  • Gradient with cross-entropy: the gradient of the loss with respect to logit i is p_i - y_i. That is the predicted probability minus the target. It is simple and strong when the model is wrong.
  • Libraries fuse softmax and log into one stable function (log-softmax). They compute log of probabilities without taking the exponential and then the log, which would lose precision.
  • The full Jacobian is p_i x (delta_ij - p_j). When one probability is near 1, the gradients of the others vanish. This is why very peaked softmax outputs learn slowly.

When it matters

  • Softmax shows up in classifier outputs, attention, routers, and sampling. You can explain four parts of an LLM with one idea.
  • Temperature is a practical knob. Low values give stable, repeatable answers. Higher values give variety.
  • Calibration questions start here. Softmax outputs look like probabilities but are often overconfident.
  • Numerical stability is a classic follow-up question.

Watch out

  • Apply softmax over the right axis. On a tensor of shape (batch, tokens, vocab), use the vocab axis for next-token odds and the key axis for attention.
  • Do not feed softmax outputs into a loss that already applies softmax. This double softmax is a common bug that hurts training.
  • Softmax probabilities are not calibrated. A 0.95 does not mean 95% of such predictions are right. Check with a reliability plot, and use temperature scaling if needed.
  • Softmax forces the classes to compete and sum to 1. For multi-label tasks, where several labels can be true, use an independent sigmoid per label.

74. Derivatives & gradients

In short A derivative tells how much a function changes when you nudge its input. A gradient collects the derivatives for all weights into one vector that points uphill. Training steps in the opposite direction to lower the loss.

Picture it

  • Take L = w squared. The derivative is 2w. At w = 2.2 the slope is 4.4. The loss rises by about 4.4 for each unit of w, so we decrease w.
  • One step with learning rate 0.1: w = 2.2 - 0.1 x 4.4 = 1.76. The loss drops from 4.84 to 3.10. Repeat and w moves toward 0.
  • Learning rate 1.1 on the same function: w = 2.2 - 1.1 x 4.4 = -2.64. The next step goes to 3.17, then -3.8. The weight grows each step. Training diverges.
  • A hiker in fog on a hill feels the slope under the feet and steps downhill. The gradient is the slope. The learning rate is the step length.
  • Chain rule: y = sigmoid(w x). The slope of y with respect to w equals the slope of the sigmoid times x. Backprop applies this rule layer by layer from the output to the input.
  • Vanishing gradient: the sigmoid slope is at most 0.25. Through 10 sigmoid layers, the gradient shrinks by about 0.25^10, which is 0.000001. Early layers barely learn. ReLU and residual connections fix this.
  • Finite difference check: nudge w by 0.0001, measure the loss change, and divide. It matches the formula gradient. Engineers use this to test backprop code.

How it works

  • Derivative: f'(x) is the limit of (f(x + h) - f(x)) / h as h goes to 0. For many weights, a partial derivative changes one weight and holds the others fixed.
  • Gradient: the vector of all partial derivatives of the loss. A model with 7 billion weights has a gradient with 7 billion numbers.
  • Update rule: w = w - eta x gradient. Mini-batch gradient descent estimates the gradient from a small batch, for example 32 to 4096 examples. The estimate is noisy but cheap.
  • Backpropagation: do a forward pass and store the activations. Then go backward and multiply local derivatives by the chain rule. It costs about 2 times the forward pass in compute.
  • Memory: backprop stores activations from the forward pass. This is why training uses much more memory than inference. Gradient checkpointing trades extra compute for lower memory.
  • Momentum and Adam keep running averages of gradients. They smooth the noise and scale each weight's step. Adam stores two extra numbers per weight.
  • Jacobian: the matrix of derivatives for a function with many inputs and many outputs. Hessian: the matrix of second derivatives that describes curvature. Know the names; most deep nets do not compute the Hessian.

When it matters

  • Every optimizer and every training loop rests on this. If you explain gradients clearly, interviewers trust your deeper answers.
  • Many training failures map to gradients: NaN values, loss that does not drop, and slow early layers.
  • Gradient clipping at a fixed norm, for example 1.0, keeps rare huge gradients from wrecking a run.
  • Learning-rate choice is the most important hyperparameter in most runs.

Watch out

  • A large learning rate overshoots and diverges. A tiny one trains too slowly. Use a warmup and a decay schedule for large models.
  • Exploding gradients give NaN loss. Use clipping, lower the learning rate, and check for bad data.
  • Local minima are less of a worry in large nets. Saddle points and flat regions are more common. Noise and momentum help escape them.
  • Do not forget to zero the gradients between steps in frameworks that accumulate them. Stale gradients add up and give wrong updates.

75. Probability basics & Bayes

In short Probability measures how likely events are. Bayes' rule updates a prior belief with new evidence to give a posterior belief. Many ML losses and model outputs come directly from probability.

Picture it

  • Medical test: 1% of people are sick. The test finds 99% of sick people. It wrongly flags 5% of healthy people.
  • Count it for 10,000 people: 100 are sick and 99 test positive. 9,900 are healthy and 495 test positive. Total positives = 594. Only 99 of them are sick, which is 16.7%.
  • So a positive result means a 17% chance of illness, not 99%. The low base rate dominates. This is the base-rate fallacy.
  • Fraud: 0.1% of transactions are fraud. Take 100,000 transactions: 100 are fraud and 99 are caught. 99,900 are good and 1% of them, 999, are flagged by mistake. Precision = 99 / 1,098 = 9%.
  • Spam: Naive Bayes multiplies the chance of each word given spam. It assumes words are independent given the class. This is false, but the model still works as a fast text baseline.
  • Distributions: Bernoulli for yes or no, categorical for one of K choices (the next token), Gaussian for noise and weight initialization, uniform for equal chance.
  • Expected value: a model that gives a 0.3 chance of a 100-dollar loss has an expected loss of 30 dollars. Decisions that use cost and probability together follow this rule.

How it works

  • Bayes: P(A given B) = P(B given A) x P(A) / P(B). In words: posterior = likelihood x prior / evidence. The evidence is a normalizer that makes the result sum to 1.
  • Conditional probability P(A given B) is the chance of A inside the world where B is true. P(A given B) and P(B given A) are different numbers.
  • Independence: P(A and B) = P(A) x P(B). Naive Bayes assumes independence of features given the class, which cuts the number of parameters from exponential to linear in the number of features.
  • Maximum likelihood: choose the parameters that make the observed data most probable. Taking the log of the likelihood turns products into sums. Minimizing the negative log likelihood equals minimizing cross-entropy.
  • Gaussian noise plus maximum likelihood gives mean squared error. Bernoulli labels plus maximum likelihood give binary cross-entropy. So the common losses are not arbitrary.
  • Variance measures spread: the average of (x - mean) squared. Variance of a sum of independent variables is the sum of variances. This explains why averaging n models cuts noise.

When it matters

  • LLM output is a categorical distribution over tokens. Confidence thresholds, sampling, and calibration are probability topics.
  • Base-rate thinking prevents bad system designs. A rare-event detector needs a human review step sized to the false alarm count.
  • Knowing that losses come from likelihoods lets you choose a loss for a new problem, for example count data or heavy-tailed noise.
  • Bayesian updating suits online learning, A/B tests, and risk scores that change as evidence arrives.

Watch out

  • Do not swap P(A given B) and P(B given A). 'Most fraud uses new devices' is not 'most new devices are fraud'.
  • Ignoring the base rate gives wildly wrong confidence. Always ask how common the event is.
  • Do not claim features are independent because Naive Bayes works. It works for ranking, but its probabilities are often extreme and uncalibrated.
  • Model scores are not true probabilities until you check calibration on held-out data.

76. Entropy & cross-entropy

In short Entropy measures how uncertain a distribution is, and cross-entropy measures how well a predicted distribution matches the true one. KL divergence is the extra cost of using the wrong distribution. LLMs train by minimizing cross-entropy.

Picture it

  • A fair coin has entropy of 1 bit. A coin that lands heads 90% of the time has entropy of 0.47 bits. A coin that always lands heads has 0 bits. Less surprise means lower entropy.
  • Surprise of one event: -log2 of its probability. An event with probability 1/2 gives 1 bit. An event with probability 1/1024 gives 10 bits. Rare events are very surprising.
  • Classification loss: the true class is 'cat'. The model gives cat 0.8. The loss is -ln 0.8 = 0.22. If it gives cat 0.1, the loss is 2.30. If it gives cat 0.01, the loss is 4.61.
  • True p = (0.5, 0.5). Model q = (0.9, 0.1). Cross-entropy = 1.74 bits. Entropy of p = 1 bit. KL = 0.74 bits. The model wastes 0.74 bits per event.
  • Language model: a loss of 2.0 nats per token gives perplexity e^2 = 7.4. The model is as unsure as if it picked among about 7 equally likely tokens at each step.
  • A model that guesses uniformly over a 50,000-token vocabulary has a loss of ln 50,000 = 10.8 and perplexity 50,000. A good LLM reaches a perplexity of single digits on typical text.
  • Distillation and RLHF use KL: keep the new model's distribution close to the reference model so it does not drift into odd outputs.

How it works

  • Entropy: H(p) = -sum of p x log p. It is the average surprise. It is largest for a uniform distribution and zero for a certain outcome.
  • Cross-entropy: H(p, q) = -sum of p x log q. This is the average surprise when the world follows p but you predict q. It is smallest when q equals p.
  • With a one-hot true label, only the true class term remains. The loss is -log of the probability given to the correct class.
  • KL divergence: KL(p || q) = H(p, q) - H(p) = sum of p x log(p / q). It is never negative and equals 0 only when p = q. Since H(p) is fixed by the data, minimizing cross-entropy equals minimizing KL.
  • KL is not symmetric. KL(p || q) punishes q for giving low probability where p has mass, so q tries to cover all of p. KL(q || p) lets q pick one mode and ignore the rest.
  • Perplexity = exp(cross-entropy in nats), or 2 to the power of the loss in bits. Compare perplexity only for the same tokenizer and test text.
  • Connection to maximum likelihood: minimizing average cross-entropy on training data is the same as maximizing the likelihood of that data.

When it matters

  • The LLM training loss is cross-entropy over next tokens. This is the most important loss in modern AI.
  • Perplexity and loss curves are the first signals of training progress.
  • KL appears in RLHF, DPO, VAEs, and distillation. Know it as 'distance from a reference distribution'.
  • Decision trees use entropy for information gain, so the idea links classic ML and deep learning.

Watch out

  • KL is not a true distance because it is asymmetric. Do not swap its arguments without thinking.
  • Log of zero is minus infinity. A model that gives probability 0 to the true class has infinite loss. Libraries add a small epsilon or work in log space.
  • Lower perplexity does not guarantee better answers. A model can fit text well and still give wrong or unsafe output.
  • Compare losses only across the same tokenizer and dataset. Different tokenizers split text into different numbers of tokens.

77. Framework: business → data → features → model → serve → monitor

In short A reliable system design answer follows a fixed order: clarify the goal, define inputs and outputs, draw the pipeline, pick the cheapest model that meets the target, plan serving, and plan monitoring. Defend each choice and name how it fails. A clear skeleton in the first minute shows seniority.

Picture it

  • Step 1, clarify (about 60 seconds): who are the users, what is the success metric, what latency and volume, what cost cap, is there personal data, must it run on premises, which languages.
  • Step 2, inputs and outputs: PDFs, emails, and call audio go in. A JSON record, an answer with citations, or an action comes out.
  • Step 3, boxes: ingest, understand (OCR, parse, classify), retrieve or reason, act through tools, human review, audit log. Draw arrows and label them.
  • Step 4, model choice: try rules first, then classical ML, then a small fine-tuned model, then a large LLM. Choose the cheapest one that meets the metric. Keep a baseline to compare.
  • Step 5, serving: online or batch, the latency budget, GPU size, caching, and fallback if the model is down.
  • Step 6, failures and monitoring: what breaks, how you detect it, and how you recover.
  • Back-of-envelope: 100,000 documents per day is 1.2 per second on average. If 80% arrive in 8 business hours, the peak is about 2.8 per second. At 3 seconds each, you need about 8 parallel workers.

How it works

  • Clarify first because the answer to 'what metric' changes the whole design. A support bot judged on resolution rate needs a different system from one judged on cost per ticket.
  • Latency budget: split the total across steps. For a 3-second chat answer: 100 ms guardrail, 300 ms retrieval, 200 ms rerank, 2,000 ms generation, 400 ms margin.
  • Sizing: requests per second x seconds per request = concurrent work. Add a peak factor of 2 to 5. For LLMs, also count tokens per second per GPU and the memory for the KV cache.
  • Model ladder: a regex that catches 60% of cases at zero cost may beat a model for that slice. Route the rest to a classifier, then to an LLM. Each step is more costly and handles harder cases.
  • Human in the loop: set a confidence threshold. Below it, send to a person. Choose the threshold from the review team's capacity and the cost of a wrong automatic action.
  • MLOps basics: version data, models, and prompts. Track experiments. Keep a model registry. Run CI with evaluation gates. Make pipelines reproducible. Monitor and retrain on a schedule or a trigger.

When it matters

  • Interviewers grade structure as much as content. A fixed order lets you stay calm and cover the ground.
  • Numbers show you can size a system. Even rough estimates, stated with assumptions, beat vague words.
  • Naming failure modes and fallbacks shows production experience.
  • Choosing the cheapest model that meets the metric shows judgment and cost awareness.

Watch out

  • Do not jump to 'use GPT-4 and LangChain'. State the goal and metric first.
  • Do not skip the failure path. Every box can fail, and you should say what happens next.
  • Do not leave out a human fallback for risky actions such as refunds, payments, and medical advice.
  • Do not present one design as the only option. Name one alternative per major choice and say why you did not pick it.

78. Offline vs online metrics, drift, A/B testing

In short Offline metrics test a model on held-out data before launch, and online metrics measure real business impact after launch. Drift happens when production data moves away from training data. You must monitor drift and be ready to retrain or roll back.

Picture it

  • Offline for a document bot: recall@5 of 0.92 and faithfulness of 0.95 on a golden set of 500 questions. Latency p95 of 2.1 seconds. A release must pass these gates.
  • Online for the same bot: automation rate, average handling time, CSAT score, cost per ticket, and escalation rate. A model can pass offline gates and still fail here.
  • Data drift: a new vendor sends invoices with a new layout. The inputs look different. The OCR confidence drops from 0.95 to 0.80 in one week.
  • Concept drift: fraudsters change tactics. The same transaction features now mean something different. Input statistics look normal, but precision falls.
  • PSI (population stability index) compares a feature's distribution now with training. Below 0.1 is stable. 0.1 to 0.25 is a moderate shift. Above 0.25 is a large shift and needs action.
  • Rollout ladder: shadow mode (run silently and compare), canary (5% of traffic), A/B test (50/50 with a metric), full rollout. Keep a one-click rollback at every step.
  • A/B sample size: baseline conversion 10%, target lift of 2 points. About 16 x 0.1 x 0.9 / 0.02^2 = 3,600 users per arm. For a 1-point lift, you need about 14,400 per arm.

How it works

  • A golden set is a fixed, labeled test set that represents production. Refresh it with new cases, for example from human corrections, so it does not go stale.
  • Drift detectors: PSI, KL divergence, or a Kolmogorov-Smirnov test on feature distributions. Also track model outputs: confidence histograms, class mix, and judge scores.
  • Label delay: fraud labels arrive after 30 to 90 days. Until then you watch proxies, such as feature drift and score distribution, and sample cases for fast manual labels.
  • A/B test mechanics: randomize by user, not by request, so one user sees one version. Fix the metric and the sample size before the test. Run for full weekly cycles. Test for significance and also check guardrail metrics such as latency and complaints.
  • Required sample grows as 1 / effect squared. Halving the effect you want to detect needs 4 times more users.
  • Online monitoring dashboards: input volume, error rate, latency p50 and p95, fallback rate, human-correction rate, and cost per request. Alert on change from baseline, not only on fixed limits.
  • Retraining triggers: scheduled (monthly), drift-based (PSI above 0.25), or performance-based (human-correction rate above 8%). Every retrain passes the same offline gates before release.

When it matters

  • It shows you think beyond the notebook. Models in production live for years and the world changes.
  • Business teams care about online metrics. Linking a model metric to money or time saved is a strong interview move.
  • A staged rollout limits damage. A bad model on 5% of traffic is a small incident, not a major one.
  • Drift monitoring is the main reason models are retrained. Without it, you learn about problems from angry users.

Watch out

  • A great offline score can become a worse online result. Causes: leakage, mismatch between test and live data, and added latency.
  • Never ship without testing rollback. A rollback that has never been tried may fail when you need it.
  • Do not stop an A/B test the moment it looks significant. Repeated peeking inflates false positives. Use the planned sample size or a sequential method.
  • Drift alerts without an owner and a runbook get ignored. Assign who acts and what they do.

Scenario answer templates

In short Most interview scenarios share one skeleton: ingest, understand, retrieve or reason, act, review by a human, and monitor. You win by using a few reusable answer patterns and fitting real numbers into them. Below are five patterns and four worked scenarios.

Picture it

  • Pattern 1, clarify then skeleton: ask about users, metric, volume, latency, cost, and data rules. Then draw the six boxes. Example: a RAG support bot for 20,000 tickets per day with a 3-second limit.
  • Pattern 2, cheapest-model ladder: rules, then classical ML, then a small tuned model, then a large LLM. Example: in fraud, a rule blocks known stolen cards. A gradient boosting model scores the rest. An LLM only writes the case summary for analysts.
  • Pattern 3, confidence routing: high confidence goes straight through. Low confidence goes to a person. Example: OCR invoices post to the ERP only if every field passes validation and confidence.
  • Pattern 4, metric + failure + monitor triple: for each box say how you measure it, how it fails, and how you detect that. Example: retrieval is measured by recall@k and fails when documents are stale. You detect it by a falling click-through rate on cited sources.
  • Pattern 5, number it: convert volume into per-second load, tokens, memory, and cost. Example: 20,000 tickets x 3,300 tokens = 66 million tokens per day.
  • Scenario A, RAG support bot: 50,000 help articles cut into about 250,000 chunks of 400 tokens. At 768 dimensions in float32 the vectors use about 768 MB. Hybrid search (keyword plus vector) with a reranker feeds the top 5 chunks to the LLM with citations.
  • Scenario B, card fraud: 5 million transactions per day, 0.1% fraud means 5,000 cases. The average load is 58 per second, and the peak is about 290 per second. The decision budget is 100 ms, so use gradient boosting on precomputed features, not an LLM in the path.
  • Scenario C, document OCR pipeline: 20,000 invoices per day, 10 fields each. If each field is 98% correct, all 10 are correct only 0.98^10 = 82% of the time. So the straight-through rate caps near 82% unless you add validation and review.
  • Scenario D, LLM fine-tune on internal docs: first try RAG, because facts change and you need citations. Fine-tune only for style, format, or domain terms. A LoRA run on a 7B model needs about 5,000 to 10,000 good instruction pairs.

How it works

  • RAG bot checks: track recall@5 on 500 labeled questions, faithfulness (answer supported by cited text), p95 latency, cost per query, and escalation rate. Apply permission filters at retrieval time so users only see documents they may read.
  • RAG bot failures: stale or duplicate chunks, a table split across chunks, and questions with no answer in the base. Add an 'I do not know, handing to an agent' path when the top retrieval score is below a threshold.
  • Fraud details: split train and test by time, not at random. Use precision at the review capacity, for example the top 1,000 alerts per day, plus recall of fraud value in dollars. Fraud labels arrive late, so watch score drift as a proxy. Add rules for new attack types while the model catches up.
  • OCR pipeline: ingest, clean and deskew, layout analysis, OCR or a vision-language model, field extraction to a JSON schema, validation (line items sum to the total, tax ID format, vendor in the master list), confidence routing, then post to the ERP by API. Measure field accuracy, character error rate, and straight-through rate.
  • Fine-tune on internal docs: build the eval set first. Split by document, not by sentence, to avoid leakage. QLoRA keeps a 7B model in 4-bit, about 3.5 GB of weights, so one 24 GB GPU can train it. Compare the tuned model with a RAG baseline on the same questions, and check that general skills did not drop.
  • In every scenario say: why this box, one alternative, the failure mode, the bottleneck, and the metric. Say where deterministic rules replace AI, and where a human stays in control.

When it matters

  • These patterns turn a vague prompt like 'design a support bot' into a calm, ordered answer with numbers.
  • Interviewers watch for judgment: use rules where rules work, AI where needed, and humans where the risk is high.
  • Concrete numbers expose your assumptions, and the interviewer can correct them. That makes the talk a discussion, not a lecture.
  • A labeled diagram with arrows and a short failure note on each box is easy to follow and easy to defend.

Watch out

  • Do not design everything as an agent. Agents add cost, delay, and risk. Use a fixed pipeline unless the task needs open-ended tool choice.
  • Do not name tools without reasons. 'Vector database' is not an answer until you say why, how big, and what recall you target.
  • Do not forget data rules: personal data masking, access control, audit logs, and where the model runs.
  • Do not claim a metric without saying how you measure it. 'High accuracy' means nothing without a test set, a threshold, and a number.
